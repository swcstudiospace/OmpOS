# Plan 67-03 summary: API auth hardening

## What changed

- `Security/JwtBearerSetup.cs`: `ValidAlgorithms` from `Api:Auth:Algorithms` (empty means `ES256` only, through `ApiAuthOptions.EffectiveAlgorithms`), `RequireSignedTokens`, `ValidateLifetime`, `ClockSkew` 30 s; `OnTokenValidated` fails a token with no `sub`, with `is_anonymous` true, or whose `role` is missing or not exactly `authenticated`. New public constants `JwtBearerSetup.RoleClaimType`, `AuthenticatedRole`, `AnonymousClaimType` (next to `SubjectClaimType`). OwnerToken handler, its limiter and `AllowedSubjectAuthorizationHandler` untouched.
- `Options/ApiAuthOptions.cs`: `IList<string> Algorithms` (default empty, see deviation 3), `EffectiveAlgorithms`, `ApiAuthClientOptions Client`.
- NEW `Options/ApiAuthClientOptions.cs` (`Autonogrammer.Api.Options`, internal sealed, section `Api:Auth:Client`): `ProjectUrl`, `PublishableKey`, `MagicLinkEnabled` (false), `EmailCodeEnabled` (true), `EmailOtpExpirySeconds` (3600), `ResendCooldownSeconds` (60), `SignupEmailHasCode` (false), `HasAny` (ProjectUrl or PublishableKey set). Plan 67-05 reads these through `IOptions<ApiAuthOptions>.Value.Client`.
- `Options/ApiAuthOptionsValidator.cs`, messages name keys only: Oidc mode now requires `Api:Auth:ValidIssuer` outside Development and absolute https when set; `Api:Auth:Algorithms` limited to `ES256`/`RS256`; Client rows (`sb_secret_` key, JWT key with role `service_role`, non-https or userinfo-bearing or unparsable `ProjectUrl`, `MagicLinkEnabled` without `EmailCodeEnabled`, `EmailOtpExpirySeconds` < 1, negative `ResendCooldownSeconds`). OwnerToken mode refuses `Algorithms` and any non-default Client member (`HasAny`, `MagicLinkEnabled`, `EmailCodeEnabled=false`, `SignupEmailHasCode`, non-default numbers). The "warn when both MagicLinkEnabled and SignupEmailHasCode are false" line is plan 67-05's startup log (D-46).
- `Services/WorkspaceSettings/WorkspaceAccess.cs`: constructor gains `IOptions<ApiAuthOptions>`; `Permits` with empty `Api:Workspace:Owners` returns true only in OwnerToken mode or with `AllowDevelopmentPrincipal`; non-empty owners keep the existing exact-match rule for every caller (the existing "development principal is checked against the owner list" row stays true). `WorkspaceSettingsOptions.Owners` XML doc corrected (file not in `files_modified`; doc-only).
- NEW `OpenApi/SecuritySchemeTransformer.cs` (document and operation transformer, registered in `OpenApiConfig.AddAutonogrammerOpenApi`): `bearerAuth` (http bearer JWT) plus `DispatchDevice` (http bearer, declared for phase 74), document-level `bearerAuth` requirement, `security: []` on operations whose endpoint metadata carries `IAllowAnonymous`, and 401 plus 403 responses (added with `TryAdd`) on all others. Public constants `SecuritySchemeTransformer.BearerSchemeName`, `DispatchDeviceSchemeName`.
- `docs/api/openapi.json` regenerated by the repo's build path (`OpenApiGenerateDocumentsOnBuild`) and committed with exactly the security-related hunks (see deviation 5).
- Rate limits: no product file edited; `Security/RateLimitPartitionTests.cs` gains the unauthenticated-address-partition test and the assembly-scan test (every `IRateLimiterPolicy<string>` implementation's source calls `RateLimitPartitionKey.For(`, except `AuthConfigRateLimiterPolicy` and `AutomationWebhookRateLimiterPolicy`, which must call `ForAddress(`; a new policy is picked up automatically and fails if it uses a constant key).
- Docs, names only: `.env.example` (`Api__Auth__Algorithms__0`, `Api__Auth__Client__ProjectUrl`, `Api__Auth__Client__PublishableKey`, open-sign-up note), `docs/runbooks/hosting.md` (deploy checklist item 2 and 5), `deploy/railway/README.md` (Auth rows, owners default, `Hosting__ForwardedHeaders__Mode=TrustAllSingleHop` note).
- Tests: `JwtTestHost` moved from HMAC to an in-test ES256 `ECDsaSecurityKey` with static metadata. `InjectStaticMetadata(IServiceCollection)` and `ForeignSigningKey()` keep their signatures; `IssueToken(subject, audience, signingKey)` gained optional `role` (default `authenticated`), `anonymous`, `issuer`, `expires`, `algorithm`; new `NewEcKey(kid)`, `HmacSigningKey()`, `InjectStaticMetadata(services, key)`, `RotatingMetadata` and `InjectRotatingMetadata`. `ApiAuthBoundaryTests`: 7 pin-violation rows (HS256, wrong issuer, expired 31 s, anonymous, role anon, role missing, role service_role) plus within-skew acceptance plus kid rotation. `ApiAuthOptionsValidatorTests`: ValidIssuer, Algorithms and Client rows (existing Oidc fixture now carries `ValidIssuer`). `WorkspaceHost.Jwt(workspace, config, owners)` (null = `alice`,`bob` unless config sets owners, explicit empty list = none); `WorkspaceSettingsAccessTests` gains empty-owners deny (all routes), dev-principal and owner-token permit rows. NEW `Security/OpenApiSecurityTests.cs` (schemes, requirement, exactly three anonymous operations `get /auth/config`, `get /source`, `post /hooks/automations/{id}`, 401/403 presence, every other operation inherits the document requirement).

## Deviations

1. AG-67-15 ("unauthenticated callers share one partition") met by per-address partitions (D-47); no policy file edited.
2. AG-67-17 (artifact-render and dispatch routes) met by the metadata rule plus the declared schemes until phases 71 and 74 add those routes (D-51); `OpenApiSecurityTests.ExpectedAnonymous` is the list they must extend.
3. `Algorithms` defaults to an empty list with `EffectiveAlgorithms` falling back to `ES256`, because the configuration binder appends to a non-empty default list (a configured `RS256` would otherwise yield `ES256,RS256`, a configured `ES256` a duplicate).
4. The webhook operation documents its own 401 (bad signature), so `OpenApiSecurityTests` asserts the boundary added no 401 or 403 to the anonymous operations except that pre-existing webhook 401.
5. `docs/api/openapi.json` holds only the 67-03 hunks. The sandbox build also produced lead-68's pending `SessionSurface` / `closedAt` schema additions; those two hunks were left out on purpose, so the committed document equals the served one only once lead-68's Contracts change is also committed (or lead-68 regenerates). GuardTests `OpenApi_ServedEqualsCommitted` therefore passes on the sandbox build (which regenerates its own document) but is not proven on the real tree in this state.
6. `.env.example` rows were swept into lead-68's commit `0afcd3b9` (their `git commit -- .env.example` carried my uncommitted hunk); content verified present once, nothing further to commit.
