# Phase 67: Accounts: Supabase passwordless sign-in - Security audit

Method: static review of the committed code, read-only (no build, no test run, no secret value read). ASVS level 2 depth: each mitigation was checked at the boundary where it must act, not only for presence. `block_on` is taken as `high` (not configured in the plans). Evidence is `file:line` at the worktree HEAD of this audit; lines refer to `src/` or `services/` unless a path says otherwise. [INFERENCE] marks anything not proven by reading or by a test the repository already contains.

## Stage A: plans 67-01 to 67-03

**Verdict: SECURED.** 16 register rows (15 mitigate, 1 accept): all closed, one of them as accepted risk. `threats_open` (blocking) = 0. Two medium findings (F-01, F-02) are open but non-blocking: both are gaps inside a mitigation that is otherwise present, and F-01 has no live exposure yet. Fix both before plan 67-05 wires `GET /auth/config` to the `Api:Auth:Client` block and before the phase ships.

Scope: 67-01 (`Autonogrammer.Accounts`, `Contracts/Accounts`, `Accounts.Tests`, `docs/runbooks/accounts.md`), 67-02 (`Harness.Secrets.Os`, `SecretStoreException` and `SecretStoreFailure`), 67-03 (`JwtBearerSetup`, `Options/ApiAuth*`, `OpenApi/*`, `WorkspaceAccess`). Plan 67-04 (`Accounts.Desktop`) is not reviewed here.

### Findings beyond the register

| ID | Severity | Status | Finding |
|---|---|---|---|
| F-01 | medium | OPEN, non-blocking (no live exposure until 67-05) | **Leading whitespace defeats the secret-key refusal.** `GoTrueOptions.CreateCore` tests `publishableKey.StartsWith("sb_secret_")` on the untrimmed value (`GoTrueOptions.cs:127-132`) and then stores `publishableKey.Trim()` (`:137`), so `" sb_secret_..."` passes and is sent as `apikey`. `ApiAuthOptionsValidator.ValidateClient` has the same untrimmed `StartsWith` (`:132-135`). Once 67-05 serves `Api:Auth:Client` to anonymous callers, a pasted key with a leading space would be published. Secondary: the client JWT check decodes with `Base64Url.DecodeFromChars` (`GoTrueOptions.cs:157`), which rejects padded input, so a padded `service_role` payload returns false client side (the API validator pads and does refuse it, `ApiAuthOptionsValidator.cs:188-190`). Fix: trim before every check, in both places, and add rows with leading and trailing whitespace. |
| F-02 | medium | OPEN, non-blocking | **Sign-out can leave the refresh token in the store.** `TryRemoveStoredAsync` swallows `SecretStoreException` (`AccountSessionManager.cs:779-790`); `SignOutAsync` publishes SignedOut and attempts the revoke regardless (`:282-305`) and sets a notice only when the network revoke fails (`:304`). If the keyring is locked or denied at that moment and the revoke also fails, the next `StartAsync` restores the session from the store (`:166-199`). D-20 and D-22 say the stored secret is cleared. `RecordingSecretStore` has `FailSet` and `FailGet` only (`tests/.../Support/RecordingSecretStore.cs:16,22`), so no test covers a failing remove. Fix: surface a notice (or retry) when the local clear fails, and add a `FailRemove` test row. Same silent path in `DiscardAsync` is harmless because the server already ended that session. |
| F-03 | low | OPEN | **`sub` is checked for presence, not content.** `JwtBearerSetup.cs:56` accepts an empty `sub`; `AllowedSubjectAuthorizationHandler.cs:35-37` maps a missing `sub` to `""` and `WorkspaceAccess.Owners` and `AllowedSubjects` entries are not validated against blank values, so a blank list entry would admit `sub=""`; `RateLimitPartitionKey.cs:25` falls back to address for an empty `sub`. Needs a signed token and a blank config entry, so [INFERENCE] not reachable in practice. Fix: `string.IsNullOrWhiteSpace` on `sub` in `OnTokenValidated`. |
| F-04 | low | OPEN | **Served project URL is not tied to the issuer.** The validator checks https and userinfo only (`ApiAuthOptionsValidator.cs:145-151`): no query or fragment refusal (the client refuses them, `GoTrueOptions.cs:118-125`) and no check that `Client.ProjectUrl + "/auth/v1"` equals `Authority` and `ValidIssuer`. The client trusts whatever host the API serves (no host allow-list, `GoTrueOptions.cs:118-125`; the session issuer check at `AccountSessionManager.cs:414` compares against the same served value). A wrong or foreign URL would send the person's email and code to that host; tokens from it would fail at the API. Operator-controlled, so low. |
| F-05 | low | OPEN | **DPAPI strict encoder throws an unwrapped exception.** `Strict.GetBytes` on a value with a lone surrogate throws `EncoderFallbackException` (an `ArgumentException`), which `RunAsync` deliberately does not wrap (`WindowsDpapiStore.cs:89-90,273`). [INFERENCE] its message names the code unit and index. The libsecret path avoids this with `Utf8.FromUtf16` status (`NativeUtf8.cs:39-47`). The Accounts session JSON cannot contain one [INFERENCE: System.Text.Json refuses invalid UTF-16 on write], but other `ISecretStore` users can. `AccountSessionManager` catches only `SecretStoreException`. |
| F-06 | info | OPEN | **Inner exceptions travel with `SecretStoreException`.** `BlockingSecretStore.cs:103`, `WindowsDpapiStore.cs:283` and `OwnerOnlyFileSecretStore.cs:207-313` keep the original exception as `InnerException`. Messages are value-free; inner messages carry file paths or library names, not secrets. The manager logs only the type name (`AccountSessionManager.cs:797`), but a host that logs `ex.ToString()` would print the chain. |
| F-07 | low | OPEN | **Refresh token, verifier and code live in unzeroed managed strings.** `SecretString` does not clear its string by design (`Harness.Secrets/SecretString.cs` remarks). Further copies: `StoredSession.RefreshToken` (`StoredSession.cs:9`), `_knownStored` for the manager's life (`AccountSessionManager.cs:83,185,525,769`), the serialised JSON (`:767`), `TokenResponse` (`TokenResponse.cs:10`), request bodies (`GoTrueClient.cs:176,194`), verifier ASCII bytes and the random bytes (`Pkce.cs:18,36`). Native copies are zeroed: `NativeUtf8.cs:49-52,70-78`, DPAPI plain and value bytes (`WindowsDpapiStore.cs:100-103,172-175,186-189`), CFData input (`KeychainNativeApi.cs:236-243`). Also, the six internal wire records and `StoredSession` have compiler-generated `ToString` that would print token, code and email if anyone formatted one; no source site does (grep clean), and `AuthFailure` and `AccountState` carry no secret. Fix is hygiene only: override `PrintMembers` or avoid records for these shapes. |
| F-08 | low | OPEN | **Client-side limits are advisory.** The cooldown check (`SignInCoordinator.cs:107-113`) and the write of the new attempt (`:133-136`) have no in-flight guard, so two parallel calls both send; the cooldown only applies to the same address, so alternating addresses never waits; a resend resets `WrongCodes` (`:130`) and concurrent `VerifyCodeAsync` calls all read the counter before any increments it (`:179-181`, `:291-303`).
