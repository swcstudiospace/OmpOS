## Evidence and candidates to present before approval

The current `PostgresAccountErasure.EraseAsync` executes seven separately committed families and finally an arbitrary tenant-key delegate; comments place quiescence on callers. Search of `src` and `tests` found construction and calls in `PostgresAccountErasureTests` only, not a production registration or caller. `AccountsModule.MapAccountEndpoints` maps reads, not erasure. `ITenantKeyEraser` registration alone does not wire an eraser. `AccountDisabledMiddleware` only disables the global route feature; `AccountEnrollmentMiddleware` upserts OIDC subjects and can recreate account rows; it skips OwnerToken. `Program.cs` invokes authentication, authorization, feature-disable middleware and enrollment in that order. M0004 has account status/deleted_at, but these observations do not prove enforcement or revocation. `DragonflyTenantErasure` scans tenant-segment keys after SQL deletion; its failure follows account-row deletion.

Candidate A is a separately authorized operator-triggered entry point, with a narrowly authenticated operator identity, explicit target subject, auditable authorization and no public HTTP route. Candidate B is an explicitly authorized self-service API deriving subject solely from the authenticated principal and never accepting a caller-selected subject. Neither exists as a proven erasure path; the owner must choose and approve one or another evidence-backed design. In either case, the API's existing allowlist, token signature verification, or account feature switch alone is not revocation. Require verified identity-provider session/refresh revocation or a durable application-side denial of every old and newly issued credential for that subject, including OIDC, device JWT and D-72 OwnerToken modes; stop if a mode cannot be denied. No provider endpoint, SDK method or revocation guarantee is assumed.

Candidate fence: additive durable account lifecycle/tombstone plus transaction-scoped per-subject admission locks and state checks. Before deleting, atomically change the subject to erasing under an exclusive lock; all account writers hold compatible admission locks through their actual commit. After existing holders drain, new admissions fail closed until and after SQL deletion and Dragonfly completion. A database-side trigger/gate on every relevant table could cover legacy and direct SQL writers, including `PostgresArtifactStore`, without editing prohibited artifact code; this is a candidate, not established safe behavior. Its feasibility depends on resolving indirect session/device ownership for every operation, deletes and inserts, race-safe lookup, privilege/trigger semantics, lock ordering with M0011/project locks, and enforcement across all database connections. Unresolvable owner, unfenced table, unsupported trigger or bypass blocks activation. Dragonfly writes are outside the PostgreSQL transaction: their independent admission and cross-process in-flight drain must be proven; a process-local mutex, API middleware, expiration or a SQL trigger alone cannot fence them. Stale instances must be denied writes by the actual storage boundary or fully drained, with no possibility of reconnecting as an old writer.

Initial inventory: `PostgresSessionRepository`, `PostgresCloudAgentStore`, `PostgresDispatchStore`, `PostgresMemoryStore`, `PostgresArtifactStore`, `PostgresProjectAccountStore`, `ArtifactAudit`, `AccountService`/enrollment, and `PostgresLedgerOutboxStore`; all API paths, jobs, workers and producers calling them. Dragonfly presence, rate limits, leases, idempotency, nonces and signal writers also require ownership and drain analysis. Enumerate tables, migrations, indirect ownership, every mutation and every caller at execution; this is not an exhaustive finding. Preserve D-11/D-12/D-13 tenant scanning and D-31 family ordering. `dispatch_audit` must remain append-only; inspect actual device/command/correlation values and outbox for identity before asserting retention privacy.

Candidate migration requires separate explicit approval because D-18 closes phase-68 migration ownership. An additive next-unused migration (do not reuse reserved M0010 or modify M0011) would create durable subject lifecycle/progress and necessary database enforcement, with restricted app DML and migrator-only DDL, least privilege and no raw sensitive content beyond approved retention. It must test real upgrade paths with the current registry (currently M0011 registered, M0010 reserved), checksums, grants, idempotence, down/re-up, and active-erasure/old-writer/unsafe-rollback refusal. Rollback must fail closed when it could reopen writes or lose a live tombstone; a safe down is tested only with disposable fixtures. A migration number and file names must be reserved against the then-current tree after approval; neither this plan nor 74.1 authorization authorizes production application.

### Binding design feasibility gate and D-34 decision

The candidate database triggers/functions above are not authorized under D-34: an up migration is limited to `CREATE ... IF NOT EXISTS` and `ADD COLUMN IF NOT EXISTS`, and the proposed trigger/function mechanism has not been shown compliant. Approval for a new migration under D-18 is not approval to change D-34. The owner must separately and explicitly approve a D-34 exception for the exact SQL and guard changes, or approve a demonstrably compliant alternative covering old/direct writers. Without that decision the trigger design cannot be implemented. `MigrationRunner.DownAsync` executes `DownSql` in its transaction and `IMigrationPrecondition` is an up-step interface; neither proves a down guard exists. The approved rollback design must cover the real `Autonogrammer.Api migrate --down` path through `MigrateCommand` and `MigrationRunner`, atomically refuse unsafe down, and test safe and unsafe runner invocations. No production rollback is authorized.

Design feasibility is a pre-implementation review of the candidate, source inventory, ownership mappings, lock order and safe rollout; it is not empirical proof. Post-implementation proof requires real cross-host and cross-store tests after the complete fence is installed. The eraser remains unavailable between those stages and until security review.
