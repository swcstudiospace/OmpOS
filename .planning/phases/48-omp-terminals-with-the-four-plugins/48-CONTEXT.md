# Phase 48 Context: Omp Terminals with the Four Plugins

Milestone v0.14.0. Requirements AL-13, AL-14 (and the terminal half of AL-15 and AL-16 through the steering inbox). Depends on Phases 44, 45 and 33 (the terminal launcher). Decision records: `docs/decisions/ADR-0012-agent-loop-plugins.md` (Update 2026-10-26, DR-2), `44-CONTEXT.md` D44-8. Evidence: `docs/runbooks/evidence/phase-48-omp-plugins-2026-10-26/`.

This context was written after the work (2026-10-26) from the commits `5a2a224` feat(48-01), `3050a71` feat(48-02) and `3603ba4` test(48-02), the code, the tests and the evidence files. It records what was decided in the code, not a discussion.

## Goal

Every omp process the application starts, the engine session behind the Agent Panel and each omp terminal, loads Ultrathink, Substrate, Swarm and GSD-Core exactly once from the pinned submodules. Each plugin's connection, or its failure and fix text, is visible to the user (DR-2).

Success criteria are in `.planning/ROADMAP.md` (Phase 48, criteria 1 to 9). The criteria table with status is in `48-SUMMARY.md`.

## Decisions found in the code

| ID | Decision | Where it is in the code and tests |
|----|----------|-----------------------------------|
| D48-1 | The launch planner plans a terminal launch from the same plan as the ACP launch: `OmpLaunchPlan.ForTerminal(options)` returns an `OmpTerminalCommand` with the argument array after `omp`, the environment and the working directory. The arguments are the plugin `-e` arguments of the ACP plan without `acp`, never `--plugin-dir`, no MCP server (an interactive omp has no `session/new` to carry one), an optional `--resume <reference>` (never `--continue`) and an optional first prompt as the last positional argument. A resume reference or prompt omp would read as a flag or a file is rejected. | `src/Autonogrammer.Harness.AgentLoop/Launch/OmpTerminalCommand.cs`, `OmpTerminalOptions.cs`, `OmpLaunchPlan.cs`; `OmpTerminalCommandTests` |
| D48-2 | Exactly-once loading uses `--no-extensions` plus one `-e` per plugin file, with the real `HOME` and `PI_CODING_AGENT_DIR` (recipe R1 of the probe). Without `--no-extensions` a plugin that is both in the user's global configuration and passed with `-e` loads twice, because omp dedupes by path string. Side effect, accepted: the owner's other global extensions do not load in app-started omp (OQ-83, default in force). | `exactly-once-loading.md`, `OmpLaunchPlannerTests.ArgumentsStartWithNoExtensionsAndNeverUsePluginDir`, OQ-82, OQ-83 |
| D48-3 | `SWARM_GSD_STATE_FILE` is an explicit per-session path, `<session>/swarm/gsd-state.md`, never empty. The pseudo-terminal backend removes a variable whose value is empty; with the old empty value the swarm would have fallen back to the workspace `.planning/STATE.md`. `SWARM_AGENT` and `SWARM_TASK_ID` stay unset. The terminal command carries no empty value for the same reason. | `SessionStateLayout.SwarmGsdStateFile`, `OmpLaunchPlannerTests.SwarmGsdStateFileIsAPerSessionPathNeverEmptyAndAgentIdentityVariablesAreNeverSet`, `OmpTerminalCommandTests.NoEnvironmentValueIsEmptyBecauseThePtyBackendWouldRemoveTheVariable` |
| D48-4 | The PTY child no longer inherits the host environment. `LinuxLocalPtyBackend` gives the command only `PATH`, `HOME`, `LANG`, `TERM`, `PI_CODING_AGENT_DIR` and `OMP_PROFILE` from the host, plus the variables the caller passes in `TerminalSessionOptions.Environment` (the caller wins). Because the pseudo-terminal helper merges the given variables into the inherited environment, the command is started through `/usr/bin/env -u NAME ...`, which unsets each other host variable by name; only names reach the command line, never values. The backend refuses to start when `/usr/bin/env` does not exist. Names and values are validated (a name with `=`, an empty name, a NUL character) and a refused value is never printed. | `src/Autonogrammer.Harness.Terminal/LinuxLocalPtyBackend.cs`, `TerminalSessionOptions.cs`; `LinuxLocalPtyBackendEnvironmentTests` (for example `AHostVariableOutsideTheAllowlistStaysOutEvenWhenOtherVariablesArePassedExplicitly`, `AVariableTheHostProcessInheritedStaysOutOfTheCommand`), `TerminalSessionOptionsTests` |
| D48-5 | The terminal launcher takes an explicit environment in its request (`OmpTerminalLaunchRequest.Environment`, empty by default) and passes it to the backend. An invalid variable name is a typed failure without the value and no terminal is started. | `src/Autonogrammer.Harness.OmpLauncher/OmpTerminalLauncher.cs`, `OmpTerminalLaunchRequest.cs`; `OmpTerminalLauncherEnvironmentTests` |
| D48-6 | Connection evidence comes from the omp side, not from guessing. The `gsd-core-omp` plugin, which loads into every app-started omp, writes a connection report to `AUTONOGRAMMER_CONNECTION_FILE` (`<session>/connection/report.json`): the sorted tool and command names omp has loaded, the omp mode and pid. The plugin lists raw names only. The host owns the table of expected names per plugin and decides. `PluginConnectionStageSource` polls the file (500 ms), gives each launched plugin one stage: Pending until a report exists, Succeeded ("Connected to omp") when every expected name is present, Degraded when some are missing (the missing names are listed, at most eight, in catalog order), Failed when none is, and Degraded after 30 s without a report (a late report recovers the stages). A plugin the planner did not launch gets no stage. The file is capped at 256 KiB and an oversized or unreadable file is Degraded without being parsed. | `plugins/gsd-core-omp/src/connection-report.mjs`, `Connection/PluginConnectionStageSource.cs`, `PluginConnectionStageSourceTests`, `PluginConnectionReportTests` |
| D48-7 | Steering inbox for omp terminals (and the fallback for chat sessions). The plugin serves `AUTONOGRAMMER_STEER_DIR` (`<session>/steer`): Autonogrammer writes a directive file into `inbox/`, the plugin moves it to `done/` and hands the text to omp with `sendUserMessage(text, { deliverAs })` (`steer`, `followUp` or `aside`), and writes an acknowledgement into `acks/` (`delivered`, `rejected` or `failed`, with the idle flag). A heartbeat file `alive.json` is refreshed every 5 s; the host treats a heartbeat older than 15 s as "not serving" and writes nothing. At most 64 directives wait; text is at most 8192 bytes. Delivery is reported as delivered only on an acknowledgement; without one the entry stays "sent, not acknowledged". | `plugins/gsd-core-omp/src/steer-inbox.mjs`, `src/Autonogrammer.Harness.AgentLoop/Steering/FileSteeringChannel.cs`, `FileSteeringChannelTests`, `plugins/gsd-core-omp/test/steer-inbox.test.mjs` |
| D48-8 | A terminal session is a session kind. The registry file records the kind (chat or terminal) without a schema version bump; an older file loads every session as a chat. The head starts omp for a terminal session only when the Agents tab is showing and the session is open (not for a session restored as closed or lost), resumes a known omp session with `--resume`, starts fresh and says so when none is known, ends omp when the session closes, and never leaves an omp child running after the head is disposed. A missing omp fails that session and the head keeps working. | `AgentSessionKindTests`, `TerminalSessionTests` (`TheTerminalStartsOmpWithThePlannedArgumentsAndEnvironment`, `AMissingOmpFailsTheSessionAndKeepsTheHeadWorking`, `ClosingASessionAndDisposingTheHeadLeaveNoOmpChildRunning`, `AKnownOmpSessionIsResumedWithTheResumeArgument`, `AReopenedTerminalWithoutAKnownOmpSessionStartsFreshAndSaysSo`), `AgentPanelTerminalSessionTests` |
| D48-9 | The terminal view hosts the interactive omp in the embedded terminal over a PTY bridge, shows fix text for a missing omp, and its composer steers through the inbox channel. The rail offers `New omp terminal` and `Ctrl+Shift+T`. | `src/Autonogrammer.Native.Views/Views/Terminal/*`, `OmpTerminalViewModelTests`, `OmpTerminalViewTests`, `OmpTerminalPtyBridgeTests`, `AgentPanelTerminalSessionTests.CtrlShiftTCreatesAndShowsATerminalSession`, `TheRailOffersNewOmpTerminalAndTagsTerminalRows` |
| D48-10 | The Substrate plugin extensions are planned only when a Substrate endpoint is configured and its health check passes (D6 of ADR-0012). Without one, the planner leaves both substrate files out and the connection row shows Substrate as off or degraded with its reason. This is a property of the planner, so "the four plugins are connected" in the application holds for the Substrate only when a healthy Substrate is configured. The live evidence tests configure the Substrate endpoint as `http://127.0.0.1:9`, an address nothing listens on, and leave `SubstrateReachable` at its default (true), so that the planner loads the two extension files; the head sets `SubstrateReachable` from its health check (`SessionEngineSet`). | `OmpLaunchPlanner.TryPlanSubstrate`, `OmpLaunchPlannerTests.AnUnhealthySubstrateIsLeftOutEntirelyAndReportedAsDegraded`, `ASubstrateWithoutAnEndpointIsLeftOutBecauseOmpWouldPollTheDefaultPort`, `LivePluginEvidence`, `SessionEngineSetTests.AnUnhealthySubstrateIsOmittedFromThePlanAndTheMcpList` |
| D48-11 | Live evidence tests carry `[Trait("Category", "Live")]`, skip unless `AUTONOGRAMMER_LIVE_OMP=1`, omp is on `PATH`, the OS is Linux and every plugin submodule is initialised, run the real omp in a sandbox (isolated `HOME` and `PI_CODING_AGENT_DIR`, `ULTRATHINK_UPLIFT=0`), never send `session/prompt`, never type a message, and assert that no omp process of the run remains. ## Steering mechanism (cross-reference)

OQ-81 is settled by the code at this commit as follows. Chat (ACP) sessions use omp's native `_session/steering` request when `initialize` advertises `_meta.steering.supported` (Phase 49, commit `16488c5`); omp terminals have no ACP, so they use the inbox of D48-7; the inbox is also the fallback for an omp whose `initialize` lacks the capability; queue-after-turn is the last fallback. Substrate only records the steer note (OQ-66). See `docs/decisions/ADR-0012-agent-loop-plugins.md`, Update 2026-10-26 (implementation).

## Not in scope or not verified

- A live model turn (OD-07): an `injected` steering outcome into a running turn, and what any plugin does when a model answers.
- Windows and macOS terminals (OQ-69), Android and the hosted deployments.
- Plugins in an omp the user starts outside the application: not done by design (OQ-82).
- The omp version in the connection row (OQ-86): the report carries `omp.version` null.
