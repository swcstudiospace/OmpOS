## Goal

The Settings window holds a Runtime section and a Models section, and every model provider is configured without a code change. omp is the engine, so a provider setting is a setting of omp: the window edits what omp reads.

Success criteria are in `.planning/ROADMAP.md` (Phase 40, criteria 1 to 7). The criteria table with status is in `40-SUMMARY.md`. The row-by-row decision against the 34 Cursor rows is `docs/settings-parity.md`.

## Decisions found in the code

| ID | Decision | Where it is in the code and tests |
|----|----------|-----------------------------------|
| D40-1 | omp is the engine, so providers, credentials and the default model live in omp. The Models page reads omp: the model list from `omp models --json`, credential presence from `omp token <provider>`, the default from `omp config get modelRoles`. omp lists only providers it holds a credential for, so an empty list means no credential. OmpOS keeps no second provider database. | `src/OmpOS.Harness.OmpConfig/OmpModelCatalog.cs`, `OmpCredentialStore.cs`, `OmpDefaultModel.cs`; `OmpModelCatalogTests`, `OmpCredentialStoreTests`, `OmpDefaultModelTests`; probe in `omp-provider-surface.md` (omp 18.12.6, fake keys, no model turn). |
| D40-2 | OmpOS edits only blocks it owns in omp's `models.yml`. Each provider is a block between the comment lines `# ompos:begin <id>` and `# ompos:end <id>`; every byte outside the blocks is preserved because the file is spliced line by line. A write keeps the previous file as `models.yml.bak-ompos-<UTC timestamp>` (the newest five are kept), writes a temporary file with owner-only permissions and renames it over the target. Then it asks the real omp (`omp models --json --no-extensions`) to load the file: omp exits 0 on a broken `models.yml` and only warns on standard error, so that warning is the validation, and when it appears, or omp cannot be asked, the previous bytes are restored. A provider id that omp uses for a built-in provider, or one defined outside an OmpOS block, is refused; when `models.yaml` exists OmpOS does not write; layouts the editor does not understand (for example a flow-style `providers` mapping) are refused and left untouched. | `OmpModelsEditor.cs`, `OmpModelsFile.cs`, `OmpModelsLayout.cs`, `OmpManagedBlockReader.cs`, `OmpManagedBlockWriter.cs`, `OmpManagedProviderValidator.cs`; `OmpModelsEditorTests` (for example `UpsertThenRemoveRestoresTheOriginalBytesExactly`, `AnIdDefinedOutsideABlockIsAConflictAndIsNeverRemoved`, `AFlowStyleProvidersMappingIsRefusedWithAnExplanation`), `OmpModelsFileTests`, `ModelsSettingsSourceCustomProviderTests.AProviderOmpsOwnValidationRefusesIsRolledBackInBothFiles`, `AnIdThatOmpUsesForItsOwnProviderIsRefused`; live: `LiveOmpConfigTests.AChangeTheRealOmpRejectsIsRolledBackByteForByte`. |
| D40-3 | A key for a built-in provider goes only through `omp auth import -`: the JSON document travels on standard input, never on the command line, and OmpOS confirms with `omp token`. OmpOS keeps no copy of the key. The page says where omp stores it (omp keeps a stored API key unencrypted in `agent.db`, an owner-only file). omp has no command to remove a credential, so OmpOS never deletes one. | `OmpCredentialStore.ImportAsync`; `OmpCredentialStoreTests.ImportSendsExactlyTheDocumentOnStandardInputAndNeverOnTheCommandLine`, `TheStorageNoteStatesWhereTheKeyGoesAndHowItIsProtected`; `ModelsSettingsSourceKeyTests.AKeyForABuiltInProviderTravelsOnStandardInputAndNowhereElse`; `ModelsApiKeyTests.EachCardNamesWhereItsKeyLives`. |
| D40-4 | A key for a custom provider cannot go to omp's credential store (omp resolves a stored credential only for providers it knows). The block names an environment variable (`apiKey: OMPOS_PROVIDER_<ID>_KEY`), the key is kept in the OmpOS owner-only secret file (`secrets/secrets.json` in the state directory: file mode 0600 in a 0700 directory, plain text, not encrypted) under that variable name, and `ProviderKeyEnvironment` hands it to every omp process the head starts. The key is merged into the environment only after planning, so the launch plan never holds one, and it is read when the process starts, so a key saved after a session was composed still reaches the next omp. | D40-5 | The catalogue rows are templates, not providers. omp knows only its built-in providers and the providers in `models.yml`, so a catalogue row (Ollama, LM Studio, llama.cpp, vLLM, LocalAI, Jan, the model runner, a hosted endpoint, a coding plan) is picked, completed with model ids, saved as a custom provider, and only then gets its key on the saved provider's card. ## Known limits

- A provider change applies to omp processes started afterwards; a running session keeps its engine.
- Keys of custom providers sit in plain text in an owner-only file; anyone who can read the file as its owner or as root can read them (stated next to the key field).
- A first `omp models --json` with a cold cache can take longer than 10 seconds and reaches the network (probe finding; the page shows a loading line).
- Linux only: the owner-only file modes are Unix modes.
