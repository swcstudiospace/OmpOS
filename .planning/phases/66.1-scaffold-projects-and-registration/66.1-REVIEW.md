## Findings

### High

**H1. Hand-patched Android lock uses the wrong entry type for the two pinned packages** (`apps/Autonogrammer.Android/packages.lock.json:57-72`)
`Avalonia.Controls.DataGrid` and `Avalonia.Controls.WebView` were added as `"type": "Transitive"` without `requested`, in the Transitive block. Both packages are in `Directory.Packages.props` and `CentralPackageTransitivePinningEnabled` is true (`Directory.Build.props:28`), so NuGet writes them as `CentralTransitive` with `"requested": "[12.1.2, )"` / `"[12.1.1, )"`. Evidence: the generated Native lock does exactly that (`apps/Autonogrammer.Native/packages.lock.json:551-555` for WebView); in the Android lock all 23 other `CentralTransitive` entries are packages from the props file (e.g. `Avalonia.AvaloniaEdit` line 952-955), and these two are the only props-pinned packages typed `Transitive`. They also sit in the wrong place (the CentralTransitive entries are the tail group from line ~950). `RestoreLockedMode` is true (`Directory.Build.props:38`), so the Android CI restore is exposed to a lock mismatch (NU1004) or to a lock rewrite on the first unlocked restore. [INFERENCE] that NuGet's validity check compares the type; the deviation from the generator's output is certain. `66.1-01-SUMMARY.md` lists the patch as UNVERIFIED, and the slnf excludes Android, so nothing in the Linux gate exercises it.
Fix: retype both entries to `CentralTransitive` with the `requested` ranges and move them to the CentralTransitive group in sorted order (the `contentHash` and `dependencies` values are already identical to the Native lock); re-verify in the Android CI job or on a host with the Android workload.

### Medium

**M1. `PluginsContractIsolationTests` has no vacuity guard and no negative control** (`tests/Autonogrammer.Contracts.Tests/PluginsContractIsolationTests.cs:19-30`)
The test walks real types, so it is not a no-op, but it passes silently if the `Autonogrammer.Contracts.Plugins` namespace is renamed, moved or emptied (the `Where` at line 19 then yields nothing) or if `WalkReferencedTypes` stops following references. Nothing asserts that at least the five ADR-0008 types (`PluginDescriptor`, `CommandContribution`, `PanelContribution`, `ToolContribution`, `AgentModeContribution`) were visited, and no in-memory fixture proves the walker reaches a `Contracts.Ui` type (the repo's own convention: `ProjectGraphTests.cs:48-56` "checker must fire on an in-memory violation", the negative proof in `ArchUnitLayerTests.cs:55-59`). This test is the D-17 guard on which the 1.6.0-vs-2.0.0 decision rests.
Fix: assert the five expected type names are found; add a fact that runs the walker (made `internal`) over a local type with a `Contracts.Ui` member and expects a hit; match sub-namespaces (`StartsWith("Autonogrammer.Contracts.Ui")`) so a future `Ui.*` child namespace is covered.

**M2. The walk descends without bound into BCL types** (`PluginsContractIsolationTests.cs:33-104`)
`DirectReferences` pushes every base type, interface, field, property, method return and parameter type of every visited type, including `System.*` ones (every record reaches `object`, `Type`, `StringBuilder`, then most of `System.Reflection` and beyond). It can only hit `Contracts.Ui` through Contracts types, so the BCL traversal is pure cost and a platform-dependent failure surface (`GetMethods` on exotic BCL types can throw `TypeLoadException`/`FileNotFoundException`). [INFERENCE] on the run time and on any flakiness: the summary reports 142/142 green on Linux only. A failure also names only the root type and the offending Ui type, not the path. `GetConstructors()` (line 92) uses the default public-only flags while every other member kind uses public+non-public.
Fix: do not push types whose `Assembly` is not the Contracts assembly (still unwrap generic arguments and array element types); record the parent so the message prints the chain; use the same `BindingFlags` for constructors.
