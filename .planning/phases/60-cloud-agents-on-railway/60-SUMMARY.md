## Phase status after the staged worker (2026-10-28)

The rule used in this milestone: a phase is ticked when every criterion is Met, or when the unmet remainder needs only an external prerequisite named in an open question and the built deliverable exists with tests. Phase 60 does not qualify, so it stays Partial:

- Criterion 4 is Partial: the worker half is Met with evidence, the API half is Blocked by OD-03 (an external prerequisite, OQ-100).
- Criterion 3 is Partial for a reason that is not external: the web head has no cloud agent list, form or test (a missing deliverable).
- Criterion 2 is Partial: no schema introspection and no control-plane provisioning against Railway (a Railway API token, OQ-142); the staged worker was created by hand and does not stand in for either.
- The worker has no clone bootstrap, so no agent could work on a repository, and the worker hooks are not wired end to end (see Partial above). These are missing code, not external prerequisites.

The staged worker proves the image builds on Railway, the entrypoint copes with a root-owned volume, the health check passes and the JWT-gated bridge works there. It does not prove the control plane, a prompt turn, a clone, sleep and wake, or the private network between two services.

## What the phase delivered

- The worker service and its image: `/acp` WebSocket bridge, JWT checks, frame guard, health endpoints, secret redaction, entrypoint with volume ownership (`60-01-PLAN.md`, units 1 to 3).
- The Railway client over the GraphQL API with an explicit VERIFIED or UNVERIFIED status per operation, a static-pool client, and a readiness probe (unit 4).
- The control plane in the API and the Postgres store: create with repositories, branch, secrets by name and idle time; caps; idempotency keys; owner scoping; wake, stop, delete, prompt, pull request (GitHub App or PAT); orphan scanner; metrics (units 5 and 6). Contract version is now 1.5.0 (`src/Autonogrammer.Contracts/ContractVersion.cs`).
- Hooks inside cloud workers (unit 7): worker side only; see Partial.
- The desktop Cloud agents page, form, hand-off and host; rail rows for cloud agents (units 8 and 9).

## Deviations

- The route is `/acp` with the session as the token subject (no session in the URL); a duplicate subject is HTTP 409 before the upgrade.
- The worker uses `Worker__*` configuration keys (repo style) where the brief said `AUTONOGRAMMER_*`.
- Secrets travel as Railway service variables of the session's service (ADR-0020 D7), not the 0600 file of the ssh path.
- The hooks addendum is `docs/decisions/addendum-ADR-0020-hooks.md` (the `ADR-*` glob of `DecisionRecordTests` would otherwise demand a second number).
- The `agents` compose profile of the first commit is no longer in `deploy/compose.yaml`; the podman commands are in the header of `deploy/worker.Containerfile`.
- `docs/runbooks/hosting.md` said "Worker. None" for the hosted API topology when this phase ended (it predated the cloud worker); the staged-worker sweep of 2026-10-28 reworded it and added a section "Staged worker on Railway (2026-10-28)".
- The form applies one branch and one base branch to every repository (the API takes them per repository).

## Partial

- Worker-side bootstrap is not built: no clone of the repositories, no branch, no run of `AUTONOGRAMMER_ENVIRONMENT`, no git credential helper, no push guard, no commit-message redaction (`docs/runbooks/cloud-agents.md`; no `AUTONOGRAMMER_REPOSITORIES` reader exists in `services/Autonogrammer.AgentWorker` or `deploy`). The control plane sets the working directory to a checkout that nothing creates, so `session/new` would fail until the worker owns that step.
- Cloud hooks are not wired end to end: no `autonogrammer_hooks_consent` claim is minted by the API, `AcpAgentSession.HookNotificationReceived` has no consumer in the API, `Worker__Hooks__*` is not set by the control plane and the image does not carry `plugins/autonogrammer-hooks-omp`; until then every cloud session reports `untrusted` and runs no project hook (the safe default).
- Git token for a worker awake longer than an hour is stale (installation token, delivered once at provisioning).
- GitHub only: GitLab, Bitbucket and Azure DevOps are not supported.
- The web head has no cloud agent list or form (criterion 3).
- Orphan workers cannot be listed through `ICloudEnvironmentClient` (the interface has no list operation); the scanner works through the `ICloudWorkerCatalog` port, whose `SupportsInventory` is false for the Railway and static clients (CloudControlPlane report), and orphan removal is off by default.
- Deleting a cloud agent keeps its transcript (`ISessionRepository` has no delete).

## Blocked (OQ/OD)

- Criterion 4 and the live half of criterion 2: a Railway API token, the deploy refusal of 2026-10-21 (it did not recur on 2026-10-28), OQ-100 (staged private deploys only), OQ-73 (acceptable use), OD-03 (no sign-in authority, so no public API) and HOST-04 (no model credential). Exact unverified Railway items (ADR-0020 D8 and `RailwayOperations`): `serviceCreate.input.environmentId` (not sent); return types of `serviceInstanceUpdate`, `serviceInstanceDeployV2`, `variableCollectionUpsert`, `volumeInstanceUpdate`, `volumeDelete`, `serviceInstanceRedeploy`; newest-first order of `deployments(first:1)` and the statuses `INITIALIZING`, `REMOVING`, `NEEDS_APPROVAL`; where `traceId` sits in an error; whether `serviceInstanceDeployV2` starts an image-sourced service; whether the private DNS name equals the service name (`http://{label}.railway.internal:8080/`); the per-environment volume lookup; and that no stop-service operation is used, so `RequestIdle` cannot command sleep.
- The Railway Sandbox tier (`sandboxCreate`) stays fail-closed (`RailwaySwarmProvider`; Q-SB-RAILWAY).

## Known limits

- Idle depends on Railway Serverless (`sleepApplication`) acting on its own; the client cannot command it. Whether `deploymentStop` keeps the volume, bills nothing and can be woken by `deploymentRestart` is UNVERIFIED and the operation is not used.
- The Railway `BootGeneration` counter is lost when the control plane restarts.
- Cancel and the run tracker are per API instance; a cancel on another instance answers `409 no_run_in_flight`.
- The environment file reader treats a bare `.` build path as the repository root; this is UNVERIFIED against Cursor's published schema (`curl https://www.cursor.com/schemas/environment.schema.json`).
- A 256-hash consent token is about 23 KiB against Kestrel's 32 KiB header limit: UNVERIFIED.
- The new-agent form has no model or environment lists (no API endpoint exists for them) and the details page shows "No history yet."
- `docs/runbooks/cloud-agents.md` still reads "Not run by the author" in its table; the recorded runs above supersede that wording for the test rows.
