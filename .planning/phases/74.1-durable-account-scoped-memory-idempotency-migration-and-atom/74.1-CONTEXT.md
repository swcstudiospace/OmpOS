# Phase 74.1: Durable account-scoped memory idempotency — context

## Boundary and authority

The user explicitly authorizes a separate additive migration, rollback design and tests for durable memory idempotency; production application is not authorized. This phase is independent of completion of 75-12, which remains responsible for enabled-production PostgreSQL composition. It may use the existing M0009 tables and present partially implemented PostgreSQL store, with its own explicit test injection. No shared roadmap/state edit, deployment, production database connection, production rollback or commit is authorized by this planning assignment.

ROADMAP phase 74.1 records this prerequisite. The phase supports the memory portions of AG-75-2, AG-75-4 and AG-75-6; these are cross-phase traceability, not a claim that the whole requirements are completed here. Phase 75's D-08, D-13, D-15–D-18, D-20 and D-21 remain applicable. The separate migration authorization specifically supersedes phase 75's no-migration boundary only for this phase; 75 itself must not author a migration.

## Decisions

- **D-01:** An optional valid `Idempotency-Key` for authenticated POST `/cowork/memory` is scoped to token subject and operation; no key preserves existing behavior. For 24 hours from a database timestamp recorded immediately before commit, equal keys and equal versioned semantic request fingerprints replay the original 201 and equivalent original response; a different fingerprint returns non-disclosing 409. Validation and authenticated subject derivation precede claim/replay. Paused memory returns its existing refusal without reading or replaying memory. Unkeyed creates remain outside the guarantee.
- **D-02:** Claim, policy/cap/owned-project checks, memory insertion and durable completion happen in one PostgreSQL transaction; concurrent requests on different instances serialize. Only successful creates are retained; refusals, cancellation, abort and pre-commit crashes leave no durable claim or insert. Ambiguous commit outcome fails closed and a retry with the same key resolves it; never retry as unkeyed. Existing scoped account advisory lock and project-row lock order must be preserved consistently.
- **D-03:** Expand with a new separately numbered table and index, no edit to shipped M0009, no runtime DDL or new package. `autonogrammer_app` uses DML only, every lookup binds account; the migration runner uses migrator rights. Preserve the existing M0010 source reservation and never reuse version 10. Migration registration/readiness and rollout compatibility must be explicitly tested.
- **D-04:** Never store a second copy of memory content or serialized response in the idempotency table. Store request digest and the successful entry identifier and reconstruct the initial response only from that account's still-existing entry. If deleted or reset or project-cascaded within the window, the matching key returns a stable non-disclosing 410 rather than recreating or revealing erased content; mismatched request remains 409. Account erasure removes all account claims. Digests and keys are sensitive metadata, not logged. Expired keys may be reused as new requests; cleanup is bounded and has an explicit operational execution path.
- **D-05:** Before enforcing durable claims, expand migration must exist, all instances must use the durable path, and old writers must be drained or memory creates disabled. Mixed old/new writers do not provide exactly-once behavior. Application rollback keeps the expanded schema and must not resume old keyed writes while promising durability; destructive down is a separately authorized, quiesced operation that loses replay history. No production action is authorized now.
- **D-06:** Verify real concurrent independent store/HTTP hosts, controlled crash and ambiguous-commit outcomes, privacy/erasure and role privileges, schema up/down/re-up, cap and project deletion races using a uniquely run-owned disposable PostgreSQL database and per-test schemas. Nonzero tests are required; absent service or unsupported failure injection means blocked, not passed.

## Existing evidence and hazards

- `MemoryEndpoints.SaveAsync` checks process-local `CoworkIdempotencyCache` before reading the body, then stores a successful response after the memory commit; this permits conflicting payload replay, independent-instance duplicates and crash-window duplicates.
- `PostgresMemoryStore.SaveAsync` applies policy before `InsertAsync`, which holds a transaction-scoped account advisory lock for cap checks and `FOR KEY SHARE` for owned projects. Preserve these protections and extend the same transaction, not a second connection or post-commit cache.
- `M0009` has project-id-only FK; ownership must be checked against subject. `PostgresAccountErasure` deletes memory family in a separate transaction. Race with new authenticated writes during account erasure is an existing cross-family safety risk: account disablement/session revocation and quiescence must be established before claiming whole-account erasure race safety.
- `MigrationRegistry` currently ends at 9 although `M0010_DispatchDeviceState.cs` exists unregistered; `MigrationRunner` loops over missing registered versions, but readiness uses head. Reserve 11, test both 9→11 and 9→10→11 paths with actual registry state and coordinate any future registration of 10; do not mutate 10 to make this work.
- `deploy/data-plane/bootstrap.sql` grants table DML to app via creator-specific default privileges; tests must exercise real creator/role grants rather than assume them.
- Existing phase 75-12 is not complete; it must consume this phase's durable interface and retain its host-restart, project ownership and fail-closed composition tests. Parent controls any change to that plan.
- Controller gate (parent instruction): 75-12 is partially executed but stopped; the controlling scheduler must prevent its resumption until all 74.1 plans and phase verification have passed. This is a scheduling hold, not a 75-12 frontmatter dependency, and the parent owns enforcing it. Afterward, before accepting 75-12, its actual enabled-production DI registration must be exercised on a freshly migrated run-owned schema by two independent hosts: same account/key/payload replays one record across restart; changed payload conflicts; another account is isolated. Preserve its existing project ownership, cap, restart and no-fallback checks. Injected-store tests in 74.1 do not substitute for this production-composition proof. 75-12 cannot be marked complete without that evidence.
- Readiness risk: highest-version comparison alone can report ready while a registered step is missing. Plan 04 requires membership and checksum checks against every migration in the running binary, including 9→11→registered 10 and an ahead ledger missing 11.

## Research and exclusions

Discovery: existing .NET/Npgsql/runner patterns plus official PostgreSQL INSERT documentation, https://www.postgresql.org/docs/current/sql-insert.html ; no package install. PostgreSQL unique constraints and transactional rollback are required, not an external cache. No 74.1 RESEARCH.md was supplied. Phase 75 deferred ideas (sharing, cloud scheduling, memory in Code) remain excluded. Retention for memory itself remains until deletion; the 24-hour limit applies only to idempotency metadata. The 24-hour choice is a planning default, not an existing product promise.
