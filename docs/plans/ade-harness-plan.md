# ADE Harness Plan

Status: planned, not started. Decision basis: ADR-0004 (accepted 2026-10-21, amended: the web head stays Blazor WebAssembly; G-WEB failed on Avalonia 12.1.4). Requirement IDs and phase numbers follow `.planning/REQUIREMENTS.md` and `.planning/ROADMAP.md`.

## 1. Purpose and scope

The ADE harness is a Cursor-class agentic development environment built on the Autonogrammer engine, which runs omp through ACP and RPC, and on the hosted API. Following ADR-0004 decision 5, its capabilities are modelled as a plugin harness: UI-framework-neutral contracts live in the contracts layer, in-process plugins come first, and out-of-process tools arrive later through MCP. v0.10.0 (Phases 20 to 25) covers the cross-platform UI: the Avalonia native project and shared presentation layer, the plugin host contracts, the parity surface for session chat, tool approvals and steering (ADE-01 to ADE-03), the five Avalonia native heads (Linux, Windows and macOS in Phase 22; iOS and Android in Phase 24), the Blazor WebAssembly web head on the shared presentation layer (Phase 23), and the cutover in Phase 25. v0.11.0 (Phases 26 to 30) covers the remaining ADE capabilities, ADE-04 to ADE-22.

No Avalonia browser head exists in v0.10.0. G-WEB failed on Avalonia 12.1.4: no controls reach the Chromium accessibility tree, so the web head stays Blazor WebAssembly. Avalonia.Browser is reconsidered only after a recorded G-WEB pass on a later Avalonia release (section 3, row "Avalonia.Browser").

The engine itself is not changed by this plan; ADE behaviour that depends on omp is bounded by the ACP and RPC contracts already in the repository.

Platform codes used below: "All six" means the five Avalonia native heads (Linux, Windows, macOS, iOS, Android) plus the Blazor WebAssembly web head (Web). For v0.11.0 rows, "Web" means the Blazor web head is a target only where the row says so, and each such feature is subject to R-14.

## 4. Plugin harness outline

Host contracts live in the contracts layer (XP-09). Contracts never reference UI-framework types: no Avalonia, MAUI, ASP.NET Core Components or `Autonogrammer.UI` type or assembly is referenced by any contract assembly. The architecture test in `tests/Autonogrammer.Contracts.Tests` runs in the gate and fails on such a reference. The shared presentation layer (Phase 20) follows the same rule: its view models and state reference no Avalonia, MAUI or ASP.NET Core Components assembly.

**Contribution points.** A plugin can contribute these points, and nothing else:

- Commands: named actions the command palette and key bindings invoke.
- Panels: views the host places in a layout. A panel contributes a contract-level model; each head renders it.
- Tools: callable operations exposed to agent runs. Tool calls go through the ACP approval path.
- Agent modes: named run configurations built from rules and skills (ADE-17).
- Editor providers: providers that supply an editor document model for a document type (ADE-09). The control itself is supplied by a head adapter.
- Terminal providers: providers that supply a PTY session (ADE-14).

**Lifecycle.**

1. Discover: the host scans the plugin directory for manifests. A manifest declares the plugin identity, its contract version range, its contribution points, and its requested permissions.
2. Load: the host checks the version range against the supported contract versions. A plugin outside the range is not loaded and the reason is logged.
3. Activate: a plugin activates on a declared activation event (first use of one of its contributions, or workspace open). Activation registers its contributions with the host.
4. Deactivate: the host calls the plugin's dispose hook and removes every contribution it registered. A plugin that fails to deactivate cleanly is marked faulted and its contributions are removed.

**Permissions.** Plugins request permissions in the manifest, and the host enforces them. No plugin can bypass ACP approvals: a plugin tool, terminal command or MCP call that requires approval goes through the same ACP permission path as an omp tool request (ADE-02). The existing permission resolver in the API harness (`services/Autonogrammer.Api/Harness/SessionPermissionResolver.cs`) is the path to extend, not replace. Output from plugin tools is untrusted data, not instructions.

**Contract versioning.** Each contract assembly carries a version. The host declares the range of contract versions it supports. A breaking change raises the major version; a new contribution point or optional member raises the minor version. Contract tests in the gate assert that the host supports the range that the built-in plugins declare. The versioning policy is written before Phase 21 starts (R-11).

**In-process first.** Plugins load as .NET assemblies in the host process for v0.10.0 and the early v0.11.0 phases. In-process plugins are trusted code under the permission model above; process isolation is not provided by this model.

**MCP for out-of-process tools (ADE-16).** Tools that run in another process, or on another machine, arrive through MCP servers over stdio or HTTP. They are registered in the tool registry like any other tool, enabled or disabled per session, and their calls go through the ACP approval path. MCP is the only out-of-process extension route in this plan.
