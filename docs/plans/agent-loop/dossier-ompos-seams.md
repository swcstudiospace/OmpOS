## 0. Top findings (ranked)

1. **`omp acp` accepts the top-level launch flags.** `omp-src/commands/acp.ts`: `static strict = false`; `run()` calls `parseArgs(this.argv)` then `runRootCommand(parsed,args)` with `mode="acp"`. Runtime-verified (omp 18.12.5, stdin `</dev/null`):
   - `omp acp --plugin-dir /tmp/nonexistent -e /tmp/nonexistent.ts` exits 0.
   - `omp acp --config /tmp/nonexistent.yml` exits 1 with `error: Config overlay not found: /tmp/nonexistent.yml`. `--config` is therefore consumed by acp and fails fast.
   - `omp acp --not-a-flag` exits 0. Unknown flags are silently ignored, so a typo will not be reported.
   - `omp acp --help` prints only `USAGE $ omp acp`; the help text does not list the flags.
2. **`--plugin-dir` is not the TypeScript-extension loader.** Source: `omp-src/discovery/helpers.ts:1501-1560` (`injectPluginDirRoots`) builds synthetic Claude-plugin-format roots (skills, commands, agents, hooks, mcp.json, via `.claude-plugin/plugin.json` or `plugin.json`). Extension factories come from `omp-src/extensibility/extensions/loader.ts:592-665`: ambient discovery, installed/linked plugins (`getAllPluginExtensionPaths`, which `omp plugin link` feeds), and **explicit `-e`/`--extension` paths**. For a directory, `-e` resolves the package.json `omp`/`pi` manifest (`extensions/directory-resolution.ts:102`, `resolveExtensionDirectory`), so `-e <submodule dir>` should load `package.json "omp":{"extensions":[...]}`. **Recommendation: launch with `-e <abs plugin dir>` for each sibling, and add `--plugin-dir` only for roots shipping Claude-format skills/agents.** `-e` also injects the package's `skills/ hooks/ tools/ commands/ rules/ prompts/ .mcp.json` (`omp-src/discovery/omp-extension-roots.ts:1-20`). Whether `--plugin-dir` also binds `omp.extensions` is not shown by source: `UNKNOWN: omp acp --plugin-dir <ultrathink> and check that its extension loads (needs a session; omp status/ext list)`. `omp plugin link <path>` (alias `omp install <path>`) is the persistent alternative and writes to `~/.omp`, so avoid it for host-run sessions.
3. **`session/new` always sends `mcpServers: []`.** `src/OmpOS.Harness.Acp/AcpAgentSession.cs:407` (`new AcpFrames.NewSessionParams(cwd, [])`) and `:423` (`LoadSessionParams(resumeSessionId, cwd, [])`). `AcpFrames.NewSessionParams(string Cwd, IReadOnlyList<JsonElement> McpServers)` already types the list (`AcpProtocol/AcpFrames.cs`, doc "This client attaches none"). omp's ACP mode forces `enableMCP:false` (`omp-src/main.ts:537-580`), so **substrate-mcp reaches omp only through `session/new.mcpServers`** (ADR-0010). No on-disk `.mcp.json` fallback exists in ACP sessions. `--config` overlays cannot declare MCP servers (ADR-0010 Q1).
4. **The launch seam is two hard-coded places.** `src/OmpOS.Harness.Acp/AcpStdioTransport.cs:191` is `startInfo.ArgumentList.Add("acp")`, with no extra args and no environment control: the child inherits the full parent environment (no `Environment.Clear()`). `AcpClientOptions` (`AcpClientOptions.cs:4-34`) has no extra-args, env or MCP property. `OmpOS.Harness.OmpLauncher` (allowlisted env `PATH HOME LANG TERM`, `OmpProcessStarter.cs:25`) is **not used by ACP** and is referenced only by its tests.
5. **`initialize` advertises only fs capabilities.** `AcpAgentSession.cs:319-324` sends `ClientCapabilities(Fs(read,write))`, with no `terminal`, `elicitation` or `auth` capability. omp reports `loadSession`, `mcpCapabilities{http,sse}`, `promptCapabilities{embeddedContext,image}`, and `sessionCapabilities{list,fork,resume,close}` (`omp-src/modes/acp/acp-agent.ts:661-679`), plus the ext method `_omp/sessions/listAll` (`:1140-1160`), which can back a multi-session list.
6. **Most ACP `session/update` kinds are dropped.** `AcpWireMapping.MapSessionUpdate` (`AcpWireMapping.cs:18-30`) maps only `agent_message_chunk`, `agent_thought_chunk`, `tool_call`, `tool_call_update` and `plan`. Everything else returns null: `user_message_chunk`, `available_commands_update` (omp's plugin slash commands), `current_mode_update`, `config_option_update`, `usage_update` and `session_info_update`. Plugin output from sibling extensions arrives as `agent_message_chunk` text, so there is no structured stage channel in ACP. Stage events must be projected from side channels (`.swarm/events.jsonl`, the substrate ledger via MCP or HTTP, ultrathink state files) by a new adapter (section 8).
7. **The "Agent Panel" is mostly the existing `MainView`, which already has an Agents toggle.** Live: transcript, composer, run controls (tool approvals), steering scheduler, Agents window (`AgentRunRegistry`), side chats, search, editor, terminal and MCP tool list. Gaps: `AgentRunRegistry` is never populated (no `Add` call in the product), the session list is hard-coded empty (`MainView.axaml.cs:131-132`), one engine and one session exist (`SessionId = "shell-session"`, `:66`), and `EngineComposition.Compose` ignores the workspace root (the child cwd defaults to `Environment.CurrentDirectory`, `AcpClientOptions.cs:10`).
8. **`OmpOS.Harness.Plugins` is an OmpOS-own declarative hook manifest** (id, version, apiVersion, capabilities, permissions, hooks run as consented commands). It is **not** omp's `package.json` and not a panel/extension model. `OmpOS.Presentation.Plugins.PluginHost` plus the `PanelContribution` records are metadata-only and **nothing in apps/src/services reads `PluginHost.Panels`** (verified by grep). Panels can be contributed only as descriptors today; no render hook exists.
9. **Adding a HarnessEvent subtype ripples widely** (a test pins the union at exactly 10 types, `HarnessContractShapeTests.HarnessEventUnionHasTenClosedCases`). Lowest-risk route: stage events are a separate `OmpOS.Contracts` data type delivered through a new presentation model, not through StreamEvent (section 2.4 lists the exact steps if a stream kind is wanted later).
10. **Repo hygiene gate will fail a submodule checkout.** `tests/OmpOS.ArchitectureTests/TodoMarkerScanner.cs:40-44,120-145` scans the whole tree for `TODO|FIXME|HACK|XXX` in `.ts/.js/.json/.yml/...`, skipping only segments `.git bin obj node_modules TestResults output .planning docs TestData .nuget`. All three siblings contain such tokens (e.g. `claude-ultrathink/src/decisions/questions.ts`, `agent-swarm/omp/src/bridge.ts`). Either add the submodule parent directory name to `TodoExcludedScanSegments`, or use a dir name already excluded. `git ls-files` based tests (`NoDockerfileOrComposeFileNamed`) only see the gitlink, so they are safe. CI `actions/checkout` (`.github/workflows/ci.yml:33,133`) needs `submodules: recursive` and pinned-SHA discipline (`WorkflowPinTests`).

### 1.2 Where flags/env/config overlay can be injected for `omp acp`
Current chain: `AcpClientOptions` then `OmpAcpClient.SpawnOmpAcp` then `new AcpStdioTransport(path, cwd)` then `ArgumentList.Add("acp")`. Three options in order of preference:

1. **Extend `AcpClientOptions` plus `AcpStdioTransport` (minimal, consistent).** New init-only members on `AcpClientOptions`:
   - `IReadOnlyList<string> ExtraArguments = []` (appended after `"acp"`, one `ArgumentList.Add` each; `-e <dir>`, `--plugin-dir <dir>`, `--config <file>`, `--cwd`, `--add-dir` all work, runtime-verified above).
   - `IReadOnlyDictionary<string,string> EnvironmentVariables = {}` (for `startInfo.Environment[name]=value`).
   - `IReadOnlyList<AcpMcpServer> McpServers = []` (typed; serialised into the `session/new` and `session/load` frames).
   `OmpAcpClient.SpawnOmpAcp` passes them to an `AcpStdioTransport` overload `(ompPath, workingDirectory, arguments, environment, logger)`. `AcpStdioTransport.cs` is in `OmpOS.Harness.*`, so `Process` is allowed (`Directory.Build.props:39` applies `BannedSymbols.NoProcess.txt` to every project **not** named `OmpOS.Harness.*`/`OmpOS.Sandbox`/`*Tests`; `Process.Start(string)` is banned everywhere by `BannedSymbols.txt`, so keep `Process.Start(ProcessStartInfo)`).
   Tests: `tests/OmpOS.Harness.Acp.Tests/AcpStdioTransportTests.cs` (real child with a stub), `AcpAgentSessionTests.cs` (assert frame contents via `ScriptedAcpTransport.Sent`).
2. **Add `OmpLaunchPlan` (new type, new AgentLoop library) that *produces* the options.** Pure function `OmpLaunchPlanner.Plan(AgentLoopSettings, PluginRegistry, workspaceRoot) -> OmpLaunchPlan{ExtraArguments, Environment, McpServers, ConfigOverlayPath, WorkingDirectory}`; `EngineComposition.Compose` maps the plan onto `AcpClientOptions`. Keeps process code in Harness.Acp and policy outside it. This is the recommended split.
3. Rewire onto `OmpOS.Harness.OmpLauncher` (allowlisted env). Not recommended: it exposes the raw process (`OmpSession`) rather than an ACP transport, so it would need a new `IAcpTransport` adapter. If a stricter environment is wanted, reuse `OmpProcessStarter.AllowedEnvironmentVariables` as the env allowlist inside `AcpStdioTransport`. Note this would then strip e.g. `OPENAI_API_KEY`/`ANTHROPIC_API_KEY`; omp reads provider auth from `~/.omp` or env, so changing it is a behaviour change to decide separately.

**Generated `--config` overlay.** A YAML mapping merged into omp *settings* only (ADR-0010 Q1: `src/config/settings.ts:2489-2509` deep-merge; missing file is a hard error, runtime-verified). Usable for omp settings (for example `mcp.enableProjectConfig: false`, extension toggles), **not** MCP servers and not plugin registration. Write it under a per-session temp dir owned by the host (the repo has `src/OmpOS.Sandbox/OwnerOnlyFiles.cs`, untracked, for owner-only file modes) and delete it on session end. `PI_CONFIG_FILES` env is the same overlay list (ADR-0010 Q3).

**MCP (substrate-mcp).** Add to the `session/new` body: stdio server `{ "name": "...", "command": "...", "args": [...], "env":[{"name":"X","value":"Y"}] }`, or HTTP `{ "type":"http", "name":"substrate", "url":"http://127.0.0.1:7410/mcp", "headers":[{"name":"...","value":"..."}] }` (shape verified at `omp-src/modes/acp/acp-agent.ts:2733-2760`, `#toMcpConfig`: `"command" in server` means stdio; `type:"http"` means http; `type:"sse"` means sse; anything else throws). Behaviour to design for: `#configureMcpServers` (`:2668-2731`) **throws if any server fails to connect**, which fails `session/new`, so health-check the gateway first (ADR-0010 Consequences). omp advertises `mcpCapabilities{http:true,sse:true}` and stdio always works.

**Env vars.** Sibling extensions read their own env (for example the substrate `/brief` URL, Graph ID). Inject through `AcpClientOptions.EnvironmentVariables`. Never print values; reference variable names only.

**`--cwd`.** `omp acp --cwd <dir>` exists (`omp-src/cli/flag-tables.ts:119`) but `session/new.cwd` (absolute, asserted by `#assertAbsoluteCwd`) is the real per-session cwd; keep using `AcpClientOptions.WorkingDirectory`.

## 6. (f) Architecture and registration checklist

### 6.1 Layers (`tests/OmpOS.ArchitectureTests/LayerMap.cs:12-47`)
L0 Contracts; L1 Parser, Harness.Abstractions, Sandbox.Abstractions, Coordination; L2 Harness.{Acp, Rpc, InMemory, Worktrees, Terminal, Workspace, Mcp, Completion, Plugins, Registry, OmpLauncher, Providers, Secrets, Herdr, Agent}, Coordination.Dragonfly, Sessions(.Postgres), SessionRuns, GenUi, Sandbox, Workflows, UI, **Presentation**; L3 Harness.Automations, EngineHost, Api, **Native.Views**; L4 Web, Native, Android. Rule (`ProjectGraphChecker.FindViolations`): a ProjectReference must target a **strictly lower** layer, or a same-layer pair in `SameLayerAllowed` (currently Sessions->GenUi, UI->GenUi, UI->Presentation, Presentation->GenUi, Sessions.Postgres->Sessions, SessionRuns->Sessions/Workflows, Parser->Harness.Abstractions/Sandbox.Abstractions); an assembly missing from the map is a violation. Also every `LayerMap` key must have a csproj on disk (`ProjectGraph_RejectsUpwardReference`).
- **Consequence:** a new L2 library cannot be referenced by Presentation (L2) unless a `SameLayerAllowed` entry is added; Presentation currently references only Contracts, GenUi, Parser (`OmpOS.Presentation.csproj`). Keep shared data types in Contracts (L0) or Presentation; keep process/IO code in an L2 `OmpOS.Harness.*` project; wire both in Native.Views (L3) or Native (L4).
- Process rule: `BannedSymbols.NoProcess.txt` bans `System.Diagnostics.Process` in every project that is not `OmpOS.Harness.*`, `OmpOS.Sandbox` or `*Tests`. Native/Native.Views/Presentation cannot spawn processes directly. `BannedSymbols.txt` bans Newtonsoft, `Task.Result`, `Task.Wait()` and `Process.Start(string)` everywhere.

- `UNKNOWN:` whether omp passes extension-emitted custom messages through ACP as `agent_message_chunk` only (source shows `agent_message_chunk` for replayed text and `_meta` only on session info). Resolve: `grep -n "extensionUserMessageTasks\|customMessage\|sendMessage" omp-src/modes/acp/acp-agent.ts`.

- Risk: in-flight uncommitted edits in the same files (logger plumbing) will conflict with P0; sequence P0 after they are committed.
- Risk: `AcpStdioTransport` inherits the entire environment today (not the launcher's allowlist), so the child already sees all parent env vars; adding env injection should not silently change that unless intended.
- Risk: omp ignores unknown flags in `acp` mode (strict=false); a mistyped flag will not fail. Add a transport-level test that asserts the exact argv, and consider probing `omp acp --config <overlay>` (fails fast on a bad path) as the only validating flag.
- Risk: omp fails `session/new` when any supplied MCP server cannot connect; the host must health-check substrate first and fall back to no MCP with a visible diagnostic.
- Risk: single-session assumptions in `MainView` (`SessionId` const, `_nextSeq`, `_stopRequested`, readonly view models) mean the multi-session switch is a refactor of `MainView.axaml.cs`, not an add-on.
- Risk: `HarnessEventUnionHasTenClosedCases`, `ContractVersionTests` and the parity inventory pin the current shapes; plan the test edits with any contract change.
