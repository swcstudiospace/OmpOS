## K. What Cursor's cloud agent actually runs (architecture facts)
- **Compute**: one dedicated VM per agent. 'Runtime workspaces run on Firecracker-based microVM infrastructure'; VMs live in a separate AWS account from Cursor production; agents cannot see each other's code/env/state (https://cursor.com/docs/cloud-agent/security.md). Ubuntu machines (setup.md), x86_64 only (https://cursor.com/docs/cloud-agent/self-hosted/choose-runtime.md). Docker runs 'inside another container layer' with edge cases, hence fuse-overlayfs + iptables-legacy (setup.md).
- **Desktop**: full desktop environment; agent drives mouse/keyboard and browser; user can take remote control (capabilities.md). Self-hosted Linux workers use X11 + tigervnc + xfce4 + xdotool + ffmpeg (https://cursor.com/docs/cloud-agent/self-hosted.md).
- **Run lifecycle** (security.md): Start (web/IDE/CLI/API/Slack/issue/PR) -> Provision isolated VM and clone authorized repo -> Run (code and tools in VM; progress, output, artifacts streamed back) -> Persist (conversation state, metadata, artifacts in Cursor-managed storage, resumable) -> Hand off (push branch, open PR, ready for review unless draft requested) -> Recycle (hibernate then delete on idle timers).
- **How the repo gets in**: Cursor GitHub/GitLab App installed by an admin plus per-user account connection; access inherited, never widened (security.md, github.md). Cloning happens at Build time: Build starts from base image, clones every repo in the environment at default branch, runs install, snapshots the disk with env version + commit SHAs; agents boot from a pre-warmed copy; feature-branch runs check out the requested branch on top; default-branch runs begin at the Build's commit unless Update stale builds pulls latest (builds.md). Snapshots deleted after 30 days idle (security.md). Before the first successful Build agents start on Cursor's default image (builds.md).
- **Config precedence**: personal env, team env, then .cursor/environment.json (setup.md). install runs to completion in the Build; start + terminals (tmux shared with user) run on each boot.
- **Secrets**: KMS-encrypted at rest, TLS in transit, injected as env vars at agent start; Runtime Secrets redacted from transcript, tool output, commits; Build Secrets only at Docker build; HTTP MCP configs never enter the VM (calls proxied via backend) while stdio MCP runs inside the VM (security-network.md, capabilities.md). Per-agent AES-256 keys (security.md).
- **Network**: allow-all / default+allowlist / allowlist-only per user, team, environment; fixed-IP git egress proxy; private nets via userspace Tailscale or Cloudflare Tunnel, PrivateLink for source control (settings.md, setup.md, security-network.md).
- **Results back**: signed commits (HSM Ed25519) pushed to a separate branch (webhook example uses branchName cursor/add-readme-1234), PR opened, artifacts (screenshots, video, logs) attached to the PR or fetched via 15-minute presigned S3 URLs, per-run SSE stream, webhook statusChange on FINISHED/ERROR, status messages in Slack/Linear/Jira (security-network.md, capabilities.md, api/endpoints.md, api/webhooks.md).
- **Follow-up loop**: agent subscribes to CI/review/Slack events and is re-awakened as follow-ups in the same conversation; CI auto-fix capped at 10 follow-ups per PR (capabilities.md).
- **Tooling inside the VM**: shell + files, git and gh, browser + desktop, MCP, oathtool, optional Docker, tmux terminals, local Unix socket /run/cursor/api.sock for OIDC tokens and agent metadata, hooks from .cursor/hooks.json, AGENTS.md rules (setup.md, identity.md, hooks.md).
- **Inference**: agent loop and inference run in Cursor's cloud for cloud and self-hosted alike; self-hosted workers only execute tool calls (file edits, terminal, browser, local MCP) over an outbound HTTPS connection, no inbound ports (self-hosted.md, my-machines.md, pool.md). SDK 'local' = local loop, still hosted inference (typescript.md).
- **Worker protocol facts (useful for an Autonogrammer remote worker)**: long-lived outbound HTTPS from worker to control plane; control plane sends tool calls down it; pools queue requests until a worker claims them (list / SSE watch / claim / release / fail endpoints); per-claim session tokens; routing by git-remote labels (--worker-dir registers roots with their git remote); 200 workers/user, 1000/team (pool.md, my-machines.md, endpoints.md).
- **Not public**: VM CPU/memory sizes, hibernation timers, microVM image contents, orchestration internals. Do not assume them.
- [INFERENCE for Autonogrammer on Railway]: Railway has no per-task microVM; closest mapping is one Railway service/deployment per agent with a volume for the workspace, Railway variables for secrets, a public or TCP domain for preview ports, and an image-build step to emulate Builds/snapshots. Worker-over-outbound-HTTPS (as in Cursor My Machines) is the pattern that gives needs-ssh-free remote environments.
