## 9. Per-mode state isolation: what exists, what could be done

Facts - where state lives today (one of each per head):
| State | Owner | Location |
|---|---|---|
| Session registry (persisted) | `AgentSessionRegistry` | `<stateRoot>/sessions.json` (`SessionEngineSet.cs:53,1080`), per-session dirs `<stateRoot>/sessions/<id>` (`AgentSessionStateFile.cs:69`); cap 200 sessions (`AgentSessionRegistry.cs:17,121`) |
| Live engines / slots | `SessionEngineSet._slots` (`:78`), `SessionSlot` | in-memory, one `omp acp` child per opened session |
| Catalog snapshot | `ReloadableSessionCatalog` -> `SessionCatalogModel` | follows the registry (`ReloadableSessionCatalog.cs:Attach`) |
| Agent Panel state | `AgentPanelViewModel` (`_sessions` dictionary of `AgentSessionViewModel`, selected session, panel state Loading/Empty/Error/Ready) | one per head (`AgentPanelViewModel.cs:27-35`) |
| Kanban | `KanbanBoardModel` | derived from the catalog, section 10 |
| Views | `MainView._panes` per session id (`MainView.axaml.cs:111`) | UI |
| Shared services | `HeadServices` (hooks, MCP, run mode hub, checkpoints, worktrees, cloud host, automations) | shared by all sessions; run mode applies to all open sessions (`RunModeHub.cs:5-9`) |
| User settings | `FileSettingsStore` | `<stateRoot>/config/settings.json` |

How isolation could be done [INFERENCE, built from existing seams]:
- Strongest: a second, independent session stack for Cowork: its own `AgentSessionRegistry` file (e.g. `<stateRoot>/cowork/sessions.json`), its own `SessionEngineSet`/`SessionCatalogModel`/`AgentPanelViewModel` built by a second `AgentHead.Build`-style call (the `Build` method takes all roots through `SessionEngineSetOptions.Loop.StateRoot`). Because the Kanban model only reads `SessionCatalogModel.Sessions`, a Cowork catalog that is never given to a `KanbanBoardModel` cannot produce cards. It also separates the 200-session cap, `RecoverAfterRestart`, lifecycle sweeper and selection state.
- Cost: `AgentHead` today builds exactly one engine set and `HeadServices` (hooks, run mode, MCP, cloud) must be shared or duplicated deliberately; `HeadServices.Automations.Attach(new HeadAutomationSessions(host, dispatch))` (`AgentHead.cs:323`) binds automations to one host.
- Weaker: keep one registry and add a mode field on `AgentSessionRecord`/`SessionSummary` like `SessionKind` (`Contracts/Agents/SessionKind.cs`: `Chat`, `Terminal`; persisted as `Kind` in `AgentSessionEntry`; unknown name loads as chat `AgentSessionStateFile.cs:251`). Rejected as the Kanban-bypass mechanism because the board takes every row (see 10).
- Web: `WebWorkbench` is one-per-tab and owns catalog+panel+board; a Cowork workbench would be a second instance or second catalog built with its own `WebAgentPanelHost`, over distinct API routes.

## 10. Where one Kanban card per session is created, and the seam Cowork must bypass

There is no card-creation call. A card is a projection of a catalog row:
1. `AgentSessionRegistry.Create(title, workspaceRoot, kind)` (`src/Autonogrammer.Harness.AgentLoop/Sessions/AgentSessionRegistry.cs:111-145`) is the only writer of rows. Callers in the head: `SessionEngineSet.CreateSessionAsync` (`:167-174`), `CreateTerminalSessionAsync` (`:182-192`), `CreateAutomationSessionAsync` (`:203-211`, used by `HeadAutomationSessions.cs:29`), `AddForkedSessionAsync` (`:664`, used by `SessionForker.cs:36`).
2. `AgentSessionRegistry : ISessionCatalog` (`:14`); `Snapshot()` (`:321`) -> `ReloadableSessionCatalog.Snapshot()` (`apps/Autonogrammer.Native/Agents/ReloadableSessionCatalog.cs`) -> `SessionCatalogModel` (`Rebuild` builds one `AgentRow` per distinct `SessionSummary.Id`: `SessionCatalogModel.cs:306-336`; cloud and remote status are overlays on existing rows, `:228,252`).
3. `KanbanBoardModel.SyncEntries()` (`src/Autonogrammer.Presentation/Kanban/KanbanBoardModel.cs:328-355`): for each `_catalog.Sessions` row it adds or updates an entry, `Rebuild()` turns entries into `KanbanCard`s; the class doc says "one task card per chat" (`:9`). The board is built over the same catalog as the rail (`AgentHead.cs:310-318`; `WebWorkbench.cs:74-83`). Test pins: `tests/Autonogrammer.Native.Tests/AgentLoop/KanbanHeadTests.cs:18-37` (one card per chat and per terminal), `tests/Autonogrammer.Presentation.Tests/Kanban/KanbanBoardModelTests.cs:22`.
4. Server side: `CatalogEndpoints.BoardAsync` (`services/Autonogrammer.Api/Endpoints/CatalogEndpoints.cs:79-113`) builds `BoardCard`s from `LoadOwnedAsync(registry, repository, user)` (`:271-285`): ids from the in-memory `SessionRegistry` (`services/Autonogrammer.Api/Services/SessionRegistry.cs:9-23`, populated by `SessionEndpoints.CreateSessionAsync` `SessionEndpoints.cs:109-110`; the file's own comment: the session store has no list operation), hydrated by `ISessionRepository.GetAsync` and filtered by `OwnerId == IUserContext.Name`. `GET /sessions` uses the same loader (`:60-77`). The web head's board is not read from `GET /board`: `GetBoardAsync` exists in the client but only tests call it; the web board is `KanbanBoardModel` over `WebSessionCatalog` (`WebWorkbench.cs:74-83`).
5. The stored `Session` contract has no kind or mode: `src/Autonogrammer.Contracts/Sessions/Session.cs` (Id, OwnerId, CreatedAt, UpdatedAt, Status, SandboxId, Messages, Events); Postgres `sessions` table `(id, owner_id, created_at, updated_at, status, sandbox_id, messages jsonb)` (`src/Autonogrammer.Sessions.Postgres/PostgresSessionSchema.cs:37-47`).

The exact seam for "Cowork sessions never get a Kanban card, enforced at the data-access layer":
- Native (`AgentSessionRegistry` / `ISessionCatalog.Snapshot()`): the only way to guarantee that no consumer (board, rail, web mirror, any future listing) emits a Cowork card is that Cowork rows never appear in the `ISessionCatalog` the Code board reads. Either a separate registry file/instance (section 9) or a mode discriminator in `AgentSessionRecord` with `Snapshot()` filtering by mode (a `Snapshot(mode)` overload, or `SessionKind` extension) AND `KanbanBoardModel.SyncEntries` filtering as defence in depth. The test `KanbanHeadTests.cs:18` pins one-card-per-session, so any change must keep Code behaviour identical.
- API (`ISessionRepository` / `SessionRegistry` / `CatalogEndpoints.LoadOwnedAsync`): add the discriminator in the repository contract (new column in `sessions`, e.g. migration through `PostgresSessionSchema.EnsureAsync` [INFERENCE: name of the ensure method not read]) and filter in the single loader `LoadOwnedAsync`, which feeds both `/sessions` and `/board`. Note `SessionRegistry` is in-memory only (lost on API restart) - a gap for any Cowork/Dispatch listing that must survive restarts; see `docs/plans/v0.16.0-research/03-api-auth-backend.md` / `04-data-plane.md` for the backend side.
- Other writers that also make rows: automations (`CreateAutomationSessionAsync`), forks, cloud-agent sessions (`CloudAgentService` takes `SessionRegistry`, `services/Autonogrammer.Api/Cloud/CloudAgentService.cs:24,57`). Each caller of `Registry.Create` / `SessionRegistry.Add` must state its mode.

## 11. What happens to running sessions on a mode change TODAY

- There is no mode concept to change. Closest existing behaviours (facts):
  - Agents|Kanban tab switch: hides rail+thread, keeps all state; sessions keep running (`MainView.axaml.cs:923-945`, class doc `:62-64`).
  - Theme change: applies live via `RequestedThemeVariant` (`HeadSettings.cs:281-283`), nothing restarts.
  - Run mode (Allowlist / Run Everything) save: refreshes every policy holder so the next tool call is decided under the new mode; an already running omp keeps the approval mode it started with until its engine is composed again (`RunModeHub.cs:5-9`).
  - Custom "modes" (`src/Autonogrammer.Presentation/Modes/*`, `ActiveMode`) and Motion preference are per-session/app unrelated concepts; the word "mode" is already overloaded (run mode, custom mode, approval mode, motion): avoid it in new type names.
  - Closing a session stops its engine but keeps the row (`SessionEngineSet.CloseSessionAsync` `:357-391` -> lifecycle `Paused`, can reopen); app shutdown stops every engine, running turns are found Lost at next start (`AgentHead.cs:250`, `RecoverAfterRestart` `SessionEngineSet.cs:1085-1089`).
- Consequence for design: since the switch can be a pure visibility change (precedent above), running Code sessions can stay alive in the background while Cowork is shown, if the Code head is not disposed; the Dispatch/Cowork stack must not share `SessionEngineSet` disposal or the 200-cap registry. Policy decision needed (section 13).

## 13. Key findings and risks

1. A card is a catalog row; nothing creates cards. The bypass must be the catalog/data layer (separate Cowork registry or discriminator + filtered `Snapshot`/`LoadOwnedAsync`), never a UI hide. `KanbanHeadTests` and `KanbanBoardModelTests` pin one card per chat and terminal.
2. One `AgentHead` = one registry (200-session cap), one panel, one board, one engine set; there is no DI container on Native. Mode isolation = second stack (best) or a discriminator (weaker).
3. `HeadSettings.Attach` requires `owner.Content is MainView`; `HeadMotionTests` scans `new MainView(` for a motion argument. A window-level mode host touches both.
4. `MainView` is 1705 lines with keyboard/focus logic hard-wired to Agents|Kanban; adding a third top-level surface inside it is higher risk than wrapping it.
5. Contrast and token gates: new colour roles need both Light and Dark values, a `ThemeContrastTests` classification, a `tokens.css` mirror and `CssContractTests` parity; no colour literals in `Views/**`.
6. NoProcess ban: `System.Diagnostics.Process` is banned outside `Autonogrammer.Harness.*`/`Autonogrammer.Sandbox`; Browser Use/Computer Use implementations that launch anything must live in a project named `Autonogrammer.Harness.*` (or the equivalent after the rename; the condition string in `Directory.Build.props:55` must then be renamed too).
7. API `SessionRegistry` is in-memory only and `Session` has no kind/mode; Dispatch (cross-device listing) needs persistent listing (see 03/04 reports).
8. Secrets: no OS keychain store exists; tokens would land in plain text 0600 JSON; web has no token storage; CSP `connect-src` is limited to one generated API origin.
9. Rename (Autonogrammer -> Autonogrammer) touches `LayerMap`, resource URIs, `InternalsVisibleTo`, `Directory.Build.props` name conditions, state/config folder names (data migration), env vars, CSS tokens, localStorage keys, tests' token names and brand docs.
10. Project/process hygiene gates: `.slnx` + `.slnf` + lockfile + `LayerMap` + ArchitectureTests reference + SUP ledger + OQ-linked TODOs + ADR record fields.
