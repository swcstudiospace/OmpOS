## SEC-77-07 fence design notes (68-10 style)

Where plans 68-09 to 68-11 were silent or only gave candidates, the conservative choice was taken and is recorded here for the independent reviewer.

1. **Gate in the database, not in each store.** Plan 68-09 offered a trigger gate as a candidate that needs a D-34 exception for `CREATE OR REPLACE FUNCTION` and `CREATE OR REPLACE TRIGGER`. The owner approved the all-writer fence design in chat; no D-34 text was amended, and the up steps contain no `DROP`, so the additive-migration test still applies unchanged. Only a database gate covers `PostgresArtifactStore` (protected from edits), direct SQL and an older binary. Every store write fails closed even if a store forgets the check.
2. **Names and versions.** M0012 `account_erasure_fence` (reserved by the owner); the unreleased memory idempotency migration became M0013 with an unchanged checksum; M0014 `memory_idempotency_fence` puts the same trigger on `cowork_memory_idempotency`, which M0013 creates after M0012. SQLSTATEs: AE001 account erasing or erased, AE002 owner cannot be resolved, AE003 transaction not at READ COMMITTED, AE004 fence row altered, AE005 rollback refused.
3. **Admission lock, then state check.** The check takes `pg_advisory_xact_lock_shared` on the account and then looks for the fence row; the eraser takes the same lock exclusively, then inserts the row. A fence row that does not exist yet is therefore safe: a writer that checked before the row exists holds the shared lock, so the eraser waits for it. This avoids provisioning a lifecycle row for every account (and a backfill), at the price that an account with no fence row is writable, which is correct for an account that was never erased.
4. **Fail closed.** An owner that cannot be resolved (a session event whose session is gone) is refused (AE002). A transaction at REPEATABLE READ or SERIALIZABLE is refused (AE003), because its snapshot could miss a fence row that committed while the check waited for the lock; no store uses either level today.
5. **Tombstone privacy.** The fence row holds a SHA-256 digest of a namespaced account identifier, a state and two timestamps, never the identifier; a test checks the row text. The digest of a guessable identifier is linkable by someone who already knows it; it holds nothing else. The row is permanent: delete and any change other than erasing to erased is refused by a trigger (AE004), and runtime roles cannot drop the table or the functions (42501).
6. **Least privilege.** The check and the session-owner lookup are `SECURITY DEFINER` with the search path pinned at migration time, so a runtime role with grants on one table is still fenced and needs no right on the fence table; the eraser's role needs DML on `account_erasure_fence`, which the bootstrap default privileges grant. A test covers both a full runtime role and a single-table role.
7. **Families stay separate transactions behind the fence.** One transaction for every family could outrun the 30-second background command timeout for a large account and then never complete. D-31 family order is kept; the fence stays `erasing` until the last transaction deletes the account row and marks the fence `erased` together, and a repeated call resumes. A call on an `erased` account skips the SQL and re-runs the tenant-key deletion, so a failed Dragonfly deletion is retried and the call completes only when the keys are gone.
8. **Lock wait.** The eraser waits at most 20 seconds for admitted writers, then raises `AccountErasureBusyException` with nothing changed. While it waits, new writers for the same account queue behind it; they are refused once the fence commits.
9. **Rollback.** M0012 and M0014 down run inside the runner's revert transaction, so a guard that raises (AE005) refuses atomically on the real `migrate --down` path; M0014 carries the guard too so a rollback that starts at the head is refused before M0013 drops the claim table.
10. **Not fenced on purpose.** `dispatch_audit` and `ledger_outbox` hold the keyed tenant hash and payload digests only, are append-only and retained by design. Dragonfly keys, the entry point and credential revocation are tracked in SEC-77-09.
11. **Mixed versions.** The gate applies as soon as M0012 is applied, whichever binary writes. An older binary sees a raw PostgresException (AE001) for an erased account. A database that applied the unreleased build where version 12 was the memory claim table fails the version 12 checksum and must be rebuilt.
12. **Test-suite repairs forced by the renumbering.** `DataPlaneStatusTests.SchemaProbe_RequiresEveryRegisteredVersionAndChecksum` and the Live `DataPlaneStartupGateTests.SchemaWait_RequiresActualRegisteredMigrations_InNonContiguousLedgers` used version 12 as their "future" migration, which collided with the registry; they now use a version beyond the head.

## Verification
- The architecture audit tests passed before the High findings above were added and fail while one is open. After SEC-77-07 was fixed, the architecture suite (non-Live) passed 107/107 with `SecurityReviewScopeAndFindingsAreCompleteAndClean` and the suppression ledger included.
- SEC-77-07 evidence ran against a run-owned TimescaleDB 2.13.1 / PostgreSQL 16 container: Sessions.Postgres 148/148 (including `AccountErasureFenceTests` 10/10 and `AccountErasureFenceMigrationTests` 7/7), Resilience 62/62, Cowork.Artifacts.Stores 13/13, Cowork.Memory 35/35, Api.IntegrationTests 1556/1557 (the one failure, `DesktopHubIntegrationTests`, needs an OS keyring that this host lacks and is unrelated). Removing the shared admission lock from the check makes the admitted-writer and busy cases fail, so those tests do detect the race. No production database, deployment or Dragonfly erasure was exercised.
- `DefaultConfigTests` passed 15/15. Account, board, authentication and client compatibility suites passed 85/85 in focused local runs. Pairing-store tests passed 7/7 and reconnect tests 28/28; actual OS keyrings and native pairing remain unverified. A valid enabled-production Dispatch baseline remains blocked by its in-memory-store validator.
- No live model turn or external provider was used (OD-07). Two PostgreSQL test classes tagged `Category=Live` were explicitly run against a run-owned local database; this does not satisfy the final gate's Live-exclusion rule.
