# ADR-0035: Cowork Computer Use: backend abstraction, policy gate and per-OS backends

- Status: Proposed 2026-10-28
- Date: 2026-10-28
- Owner: autonogrammer-maintainers
- Deciders: autonogrammer-maintainers
- Scope: the Computer Use capability of Cowork mode in milestone v0.16.0 (brief 73, requirements AG-73-1 to AG-73-24): the screen and input backend abstraction `IComputerUseBackend`, the single policy gate `IComputerActionGate`, the tool family `computer.*`, the four OS backends, permission recovery, the vision loop, Dispatch use and the threat model. The research is [07-browser-computer-use-feasibility.md](../plans/v0.16.0-research/07-browser-computer-use-feasibility.md) (sections 3 to 5, D3 and D4), [06-cowork-parity-and-references.md](../plans/v0.16.0-research/06-cowork-parity-and-references.md) (C17, C18, D4, D8), [08-dispatch-relay-prior-art.md](../plans/v0.16.0-research/08-dispatch-relay-prior-art.md) (risks 1 and 2), [02-ui-architecture.md](../plans/v0.16.0-research/02-ui-architecture.md) and [09-project-recipe-and-conventions.md](../plans/v0.16.0-research/09-project-recipe-and-conventions.md). The `ICoworkToolProvider` contract, the Cowork session and the shell belong to ADR-0032 and are not redesigned here; the relay belongs to ADR-0036; Browser Use belongs to ADR-0034. Names in this file are the post-rename spellings (`Autonogrammer` is `Autonogrammer`, so `src/Autonogrammer.Harness.Mcp` is written `src/Autonogrammer.Harness.Mcp`); the repo on disk still carries the old names until the rename tool is applied, and file and line references below were read under the old names.
- Owner decisions applied (settled, not reopened): Computer Use is part of Cowork, so it needs sign-in (ADR-0030) and Code mode never reaches it; it is off by default; a Computer Use command always needs local approval on the desktop; offline Dispatch commands queue for 5 minutes and then expire (ADR-0036); the Cowork agent is local omp over ACP; Windows and macOS code is compile-checked only.

## Context

Cowork parity (report 06, C17) asks for screenshots plus click, type and scroll in approved applications, with per-app permission, tiers by app category, a blocklist and a prompt-injection scan; Anthropic ships it for macOS and Windows only and states "no sandbox between Claude and your applications". Report 07 section 3.0 found that omp 18.12.5 already contains a native desktop session behind `computer.enabled=false` (X11 XTEST, Wayland portal, Win32, macOS quartz). That path has no host approval UI per action, no way to route a desktop that is not where omp runs, and no audit, so it cannot be the governed path (report 07 section 3.0, last paragraph). Facts about this repository that shape the design:

- Process spawning is banned outside projects named `Autonogrammer.Harness.*`, `Autonogrammer.Sandbox` and tests (`Directory.Build.props:52`, `BannedSymbols.NoProcess.txt:1`). Code that must run a process (macOS capture, test oracles) therefore lives in `Harness.*` projects. A project must be listed in `tests/Autonogrammer.ArchitectureTests/LayerMap.cs` (layers at `:15-54`; a same-layer reference needs a `SameLayerAllowed` tuple with an `// intentional:` comment, precedent `:78`).
- The host-owned MCP gateway exists but is wired into no head; a tool call passes `McpToolInvoker.InvokeAsync`, which refuses tools not enabled for the session and then calls an injected approval delegate before contacting the server (`src/Autonogrammer.Harness.Mcp/McpToolInvoker.cs:33-50`). `AcpApprovalPolicy` denies by default (`src/Autonogrammer.Harness.Acp/AcpApprovalPolicy.cs:6-11`). Whether omp reaches the gateway through `session/new.mcpServers` is feasible by source and unverified live (ADR-0010; report 07 section 4.3 and D5; OD-07).
- Tool-result images are dropped by the UI contract: `ToolUpdateContent` carries output text and file edits only (`src/Autonogrammer.Contracts/Ui/ToolUpdateContent.cs:5-24`). Prompt images are capped at 8 images, 10 MiB each and 25 MiB total (`src/Autonogrammer.Harness.Acp/AcpImageLimits.cs:7`). Showing what the agent saw needs the contract extension that report 07 lists as D7; it is delivered with the Cowork shell (ADR-0032) and is a dependency here, not a decision here.
- No OS keychain store exists; `ISecretStore` has file and memory implementations only (`src/Autonogrammer.Harness.Secrets/ISecretStore.cs:18-21`). Nothing in this record stores a secret.
- No PNG or image-resize code exists in `src`, `apps` or `services` (grep for `ZLibStream`, `PngEncoder`, `SKBitmap`, `SixLabors` returned nothing, 2026-10-28). The only P/Invoke precedent is `DllImport` with `DefaultDllImportSearchPaths` in `src/Autonogrammer.Sandbox/PosixProcessSignal.cs:15-16`; no project sets `AllowUnsafeBlocks`.
- Only X11 under Xvfb has ever been run on this host; Wayland is `BLOCKED (NOT RUN)` (`docs/runbooks/phase-20-avalonia-foundation.md:45`) and ADR-0009 measured Linux only. Railway deploys are paused and cloud desktops are an open policy question (OQ-73; report 07 D10), so cloud agents get no Computer Use.

## Decision

### D1. Placement, layers and default state

No new service and no new NuGet package. Computer Use runs only in the desktop head's process on the user's machine; the API, the web head and the cloud worker never load it (`Autonogrammer.Web` may not reference process-spawning assemblies, `ProjectGraphTests.cs:12,36-41`). New projects, all plain `net10.0` so Windows and macOS code compiles on Linux (P/Invoke is resolved at run time only):

| Project | Layer | Contents |
| --- | --- | --- |
| `Autonogrammer.Harness.ComputerUse.Abstractions` | L1 | `IComputerUseBackend`, `IComputerActionGate`, ports, records, enums, denial codes, `CoordinateMap`, `ComputerUseOptions`. No process, no I/O. |
| `Autonogrammer.Harness.ComputerUse` | L2 | gate, grants, app catalogue, sensitivity classifier, rate limiter, kill-switch coordinator, executor, frame pipeline, audit log, `computer.*` provider, `FakeComputerUseBackend`, DI. Does not reference any OS backend. |
| `Autonogrammer.Harness.ComputerUse.X11` | L2 | Xlib and XTest backend, global hotkey. |
| `Autonogrammer.Harness.ComputerUse.Windows` | L2 | SendInput and GDI backend, `RegisterHotKey`. |
| `Autonogrammer.Harness.ComputerUse.MacOS` | L2 | CGEvent backend, `screencapture`, hotkey. |

The head (L3 and L4) references the backend for its own OS and registers it. UI (approval dialog, indicator, grants page) lives in `Autonogrammer.Presentation` (view models) and `Autonogrammer.Native.Views` (views). `ComputerUse` references `Autonogrammer.Cowork.Abstractions` (L1, ADR-0032 D7), which owns `ICoworkToolProvider`, so no `SameLayerAllowed` entry is needed. `ComputerUseOptions` (section `Cowork:ComputerUse`, `ValidateOnStart`, validator naming keys never values, as `CloudOptionsValidator`) defaults `Enabled=false`. The feature also needs an account session (ADR-0030) and the Cowork mode; with any of the three missing, the `computer` provider reports `Unavailable` and no `computer_*` tool is offered.

### D2. `IComputerUseBackend`

One interface per OS adapter. Every I/O member is `ValueTask`, ends in `Async` and takes `CancellationToken` last, no default. Coordinates crossing it are native virtual-desktop pixels (the unit the OS injects in); scaling belongs to `CoordinateMap` in the core.

```csharp
public interface IComputerUseBackend
{
    ComputerPlatform Platform { get; }              // X11, Windows, MacOS
    ComputerBackendCapabilities Capabilities { get; } // flags: WindowEnumeration, FocusedElementInspection, ClipboardText, ...
    ValueTask<ComputerAvailability> GetAvailabilityAsync(CancellationToken cancellationToken);
    ValueTask<ComputerPermissionStatus> GetPermissionStatusAsync(CancellationToken cancellationToken);
    ValueTask<ComputerPermissionStatus> RequestPermissionAsync(ComputerPermissionKind kind, CancellationToken cancellationToken);
    ValueTask<IReadOnlyList<DisplayInfo>> ListDisplaysAsync(CancellationToken cancellationToken);   // id, native bounds, scale factor, primary
    ValueTask<IReadOnlyList<WindowInfo>> ListWindowsAsync(CancellationToken cancellationToken);     // bottom-to-top z-order: id, pid, AppIdentity, title, bounds, minimized, focused, isOwnProcess
    ValueTask<PointerState> GetPointerAsync(CancellationToken cancellationToken);
    ValueTask<RawFrame> CaptureAsync(CaptureRegion region, CancellationToken cancellationToken);    // native pixels, BGRA, one display or sub-rectangle
    ValueTask InjectAsync(InputPrimitive primitive, CancellationToken cancellationToken);           // PointerMove, PointerButton(down/up), Scroll, Key(down/up), TypeText
    ValueTask ReleaseAllInputAsync(CancellationToken cancellationToken);                            // lifts every held button and key
    ValueTask<string?> ReadClipboardTextAsync(CancellationToken cancellationToken);
    ValueTask WriteClipboardTextAsync(string text, CancellationToken cancellationToken);
}
```

`InjectAsync` takes primitives only (move, button down, button up, scroll, key down, key up, a short text run). The semantics of a click, a drag or a chord belong to the executor, so each OS adapter stays a thin translation and the gate sees every primitive's target. Clipboard text goes through a head-provided `IClipboardTextPort` (the Avalonia clipboard, as `AvaloniaClipboardImageSource` does for images, `src/Autonogrammer.Native.Views/Views/Attachments/IClipboardImageSource.cs`) so no backend implements OS clipboard protocols. A backend never decides policy and nothing outside the executor may hold it (D3). Failures are typed: `ComputerBackendException` with a `ComputerFailure` category (`PermissionMissing`, `Unavailable`, `TargetGone`, `Elevated`, `SecureDesktop`, `Timeout`), a message free of window titles and text.

### D3. `IComputerActionGate`: the one choke point

```csharp
public interface IComputerActionGate
{
    ValueTask<ComputerGateDecision> AuthorizeAsync(ComputerActionRequest request, CancellationToken cancellationToken);
}
// ComputerGateDecision = Allowed(ComputerActionTicket) | Denied(DenialCode, UserMessageId)
```

`ComputerActionExecutor` (internal to `Autonogrammer.Harness.ComputerUse`) is the only type that calls `IComputerUseBackend` for anything except status reads. Every `computer.*` tool call becomes a `ComputerActionRequest` (host-built; model text is only data inside it), the executor calls `AuthorizeAsync`, and injection needs the returned single-use ticket (bound to the action hash, valid 2 s). An architecture test (`ComputerUseBoundaryTests`) fails the build if any other assembly or type references `IComputerUseBackend` or `InjectAsync`. Evaluation order, first failing step wins, each denial has a stable `DenialCode`:

1. Feature enabled, signed in, session opted in (`Disabled`, `NotOptedIn`); a kill-switch trip or revocation (`Revoked`).
2. Platform available and permissions present (`PlatformUnavailable`, `PermissionMissing`), kill switch registered and indicator visible (`KillSwitchUnavailable`, `IndicatorUnavailable`).
3. Frame still valid: the action's `frame_id` is the session's latest frame and the display layout is unchanged (`StaleFrame`); coordinates inside the frame (`OutOfBounds`).
4. Host-observed target: window under the point (pointer actions) or the foreground window (keyboard actions), taken from `ListWindows` at decision time, never from the model.
5. Denylist and own windows (`DeniedApplication`, `OwnWindow`), grant lookup (`NoGrant`), tier against action class (`TierTooLow`), forbidden chords (`ForbiddenChord`), elevated target on Windows (`ElevatedTarget`), secure desktop (`SecureDesktop`).
6. Rate limit and step limit (`RateLimited`, `StepLimit`), user takeover (`UserTookOver`), image budget for capture (`ImageBudget`).
7. Sensitivity classification; if sensitive or the grant demands it, ask the local user through `IComputerApprovalPrompt` (`ApprovalDenied`, `ApprovalTimeout`, `NoLocalApprover`).
8. Write-ahead audit record; if it cannot be written, deny (`AuditUnavailable`). Then inject; then the outcome record.

Actions are serialised by one process-wide lock, so no injection happens while an approval prompt is open (D5). Time comes from an injected `TimeProvider`; nothing reads the clock directly. The gate fails closed: an exception inside `AuthorizeAsync` is `Denied(InternalError)`.

### D4. Per-application grants, tiers and the denylist

A grant is (session, `AppIdentity`, tier, origin, expiry, `AutoApproveTyping`). `AppIdentity` is the platform's stable id: bundle id (macOS), executable file name plus signer where available (Windows), `WM_CLASS` plus the basename of `/proc/<pid>/exe` (X11). The model cannot create a grant: `computer.request_access` only shows the user a request labelled as an agent statement. Tiers:

| Tier | Allowed actions |
| --- | --- |
| `ViewOnly` | screenshot, zoom, window listing for that app |
| `ClickOnly` | `ViewOnly` plus pointer move, click, drag, scroll; no keyboard, no clipboard |
| `Full` | `ClickOnly` plus type, key chords, clipboard |

Default tier comes from the application category in a data catalogue (`computer-use-apps.json`, source-generated JSON, rows as data like ADR-0019): browsers `ViewOnly` (Browser Use, ADR-0034, is the browser path), IDEs and code editors `ClickOnly` (their integrated terminals run commands), mail and messaging `ViewOnly` and, if the user raises it, every click and key asks, everything else `Full` after the grant dialog. The built-in denylist has no override in v0.16.0: terminals and shells, password managers and keychains, OS settings and policy prompts (polkit agents, UAC, Keychain Access, System Settings, Control Panel, registry editors), trading and crypto-wallet applications, and the Autonogrammer process itself. A user may add entries and may never remove built-in ones. Deny wins over grant. A grant ends with the session, after 8 hours, or when the application's window set changes identity; Dispatch-origin grants last 30 minutes (D12). `computer.list_windows` returns titles only for granted applications; other windows appear as category counts, so the model learns nothing about applications it cannot use. Hard-denied chords (launchers and run dialogs bypass the denylist): Win+R, Win+X, Alt+F2, Ctrl+Alt+T, Cmd+Space, Ctrl+Alt+Del, Ctrl+Alt+Backspace, virtual-terminal switches and the kill chord. The catalogue ships with identifiers read from each product; rows for Windows and macOS products are unverified on this host (OQ-388).

### D5. Sensitive actions and approval integrity

A `SensitivityReason` set is computed from host-observed facts only: foreground or target window title and application category, the key chord, the action kind, and focused-element traits where the backend reports them. No backend reports traits in v0.16.0 (`FocusedElementInspection` is off on all three; OQ-384), so credential fields are detected by title patterns (sign in, log in, password, passcode, one-time code, token, secret, unlock; data in the catalogue, English first) and, where unknown, by policy: typing into an application asks unless the user ticked "allow typing in this application for this session" when granting, and credential-titled windows always ask. Always confirmed: file deletion (Delete, Shift+Delete, Ctrl+Delete, Cmd+Backspace in file managers or in windows titled delete, empty trash, recycle bin), purchase windows (checkout, payment, pay now, order, subscribe, billing), mail or messaging applications raised above `ViewOnly`, any clipboard read or write, every first action for an application, and every action whose grant has Dispatch origin. This is heuristic and is stated as such: tiers, the denylist, the kill switch and local approval are the guarantees; title patterns reduce risk and miss cases.

`IComputerApprovalPrompt` is the only UI port. The dialog shows host-observed facts: application display name and identity, the window title (sanitised: control characters and bidirectional overrides removed, quoted, 80 characters), the action in host words, a 160 by 120 crop of the host-captured screen around a click point with a crosshair, or the character count and first 40 sanitised characters of typed text labelled "agent text", the origin (local or Dispatch with the controller device name) and a user-chosen security phrase. Choices: Deny (default focus), Allow once, Allow for this session. No timer ever allows; the prompt times out to deny after 120 seconds (the approval default of report 08 section 4.7; ADR-0036 owns relay expiry). Integrity measures:

- While a prompt is open no primitive is injected anywhere (D3 serialisation), so the model cannot click Allow.
- Own-process windows are hard-denied as targets: the executor re-resolves the window under the pointer after the move and before button-down and aborts on any change or on `isOwnProcess`.
- Own-process windows are masked in every frame the model receives (D9), so the model cannot read the security phrase.
- The dialog and the indicator are keyboard operable, named for screen readers, announce through a polite live region, use text and shape as well as colour, and respect high-contrast and reduced-motion settings (the contrast and token gates of report 02 section 13, finding 5, apply to any new colour role).
- A remote approval of a Computer Use request is not accepted from any channel (D12).
- ADR-0036 (D15, row 8) asks that approval needs a trusted input event. This record cannot provide that: an XTest or `SendInput` event is indistinguishable from hardware input to the dialog, and no portable provenance check exists. The defence is the combination above (serialisation, own-window denial, masking), and that gap is recorded in Open risks and tested only at unit level.

### D6. Rate limits, kill switch, indicator, user takeover

- Limits (options, validated): 60 actuating actions per minute (token bucket, burst 10), 300 actions per session then a "continue" prompt that adds 100, 5 consecutive failures pause the loop, `computer.wait` at most 5 s, `type` at most 2000 characters per call, sent in runs of 16 with a token check and a foreground-window re-check between runs.
- Global hotkey kill switch, default Ctrl+Alt+Shift+Escape (options; the validator requires at least two modifiers and refuses chords in the forbidden list; OQ-386). Each backend implements `IGlobalHotkeyRegistrar` on its own thread and its own OS connection, independent of the UI thread and of the injection connection. Registration must succeed and be confirmed before the first actuating action of a session; failure is `KillSwitchUnavailable` and Computer Use refuses to arm (fail closed). A trip cancels the session's revocation token, calls `ReleaseAllInputAsync`, sets the state to `Revoked` (the gate denies everything until the user re-arms in the UI), cancels the Cowork turn through the session service, updates the indicator and writes an audit record. The executor checks the token between primitives and no sleep is uncancellable, so injection stops before the next primitive. The same trip is reachable from the indicator's Stop button, the Cowork session Stop and the tray menu.
- Persistent on-screen indicator: a top-most, non-focusable, always-visible window on every display edge, text "Autonogrammer is controlling this computer" with the session name and the kill chord, a distinct "armed, idle" label, and a "Remote (Dispatch): <device>" label for Dispatch origin. Before each action the gate confirms the indicator window is in the window list and not minimised; if not, `IndicatorUnavailable`. Full-screen exclusive applications and macOS full-screen Spaces may cover it (OQ-386 and Open risks).
- User takeover: the executor stores where it left the pointer; before each pointer action a displacement over 24 px (option) means the user moved the mouse and the loop pauses with `UserTookOver` until the user resumes in the UI. This is portable and needs no idle counters.

### D7. Local append-only action audit log and screenshot redaction

`ComputerAuditLog` writes JSON Lines under the application state directory, `computer-use/audit/YYYY-MM-DD.jsonl`, created owner-only (0600 or owner ACL), opened append-only with `FileShare.Read`, flushed per record. Each record has `seq`, UTC time, session id, tool, a host-built action summary, `AppIdentity`, window title truncated to 80 characters, decision and denial code, approval origin (`Local` or `Dispatch`), outcome, frame SHA-256 and a `prev` field holding the SHA-256 of the previous line, so truncation or edit of a prefix is detectable (tamper-evident, not tamper-proof: the user owns the file). A record is written before injection and a second after it; if the write fails the action is denied (D3). Typed text is recorded as length and SHA-256 only (`Audit:TypedText=Off`; `On` stores it after redaction of credential-titled contexts). Clipboard contents are never recorded. Optional frame thumbnails (`Audit:Thumbnails`, default off, 320 px long edge, PNG) use the `AuditView` redaction profile: the model view (D9) plus credential-titled windows blacked out. The log stays on the device; it is never uploaded and no computer event is written to `cowork_events` or the ledger (the hub keeps its own `dispatch_audit`, report 08 section 4.12). Retention 30 days, rotated daily; deletion by retention is logged.

### D8. Tool family `computer_*` as an `ICoworkToolProvider`

One provider, `ProviderId = "computer"`, registered with the `CoworkToolHost` of ADR-0032 (D5, `Autonogrammer.Cowork.Abstractions`) only when D1 conditions hold; the contract (descriptor, `Describe`, `GetStateAsync`, `PreviewAsync`, `InvokeAsync`, `EndSessionAsync`, `CoworkImageBlock`, session taint, `ICoworkApprovalBroker`, `ICoworkGrantStore`, `ICoworkToolAudit`) is ADR-0032's and is not redesigned here (read 2026-10-28 from ADR-0032 D5 and D6). Naming: descriptor names follow `^[a-z][a-z0-9]*(_[a-z0-9]+)*$` and start with `computer_`, so the tools are `computer_status`, `computer_list_displays`, `computer_list_windows`, `computer_screenshot`, `computer_zoom`, `computer_request_access`, `computer_mouse_move`, `computer_click`, `computer_drag`, `computer_scroll`, `computer_type`, `computer_key`, `computer_clipboard_read`, `computer_clipboard_write`, `computer_wait`, and omp shows them as `mcp__cowork_computer_<name>`. Elsewhere in this record and in brief 73 the family is written `computer.*` and a tool as `computer.<name>`; read that as the logical name of the same descriptor. The omp settings `computer.enabled` and `browser.enabled` keep their dotted spelling.

Descriptor mapping: observe tools (`status`, `list_displays`, `list_windows`, `screenshot`, `zoom`, `wait`) are `Effect=ReadOnly`, `Approval=ByPolicy`, `Results=Text|Image` for `screenshot` and `zoom`; `computer_request_access` is `Effect=Actuating`, `Approval=EveryCallOnExecutingDevice` (its prompt is the per-application grant dialog of D4 and D5, answered only on the desktop); pointer, keyboard and clipboard tools are `Effect=Actuating`, `Approval=ByProviderGate`, the value ADR-0032 D5 and D6 added at this record's request (accepted by its author 2026-10-28, OQ-394): the host policy returns Allow once the provider is `Available` and never asks, so the provider must ask itself. Consequences for this design: the `computer` provider receives the `ICoworkApprovalBroker` at construction, and `IComputerApprovalPrompt` of D5 is implemented by calling it with `MustBeLocal = true` for every grant and every sensitive action, in every permission mode including Skip and in a tainted session (a contract test of ADR-0032 asserts that a `ByProviderGate` provider asks); the descriptor validator refuses `ByProviderGate` on `Effect=Destructive`, so no `computer_*` tool is declared `Destructive` and destructiveness (deletion, purchase) is a runtime sensitivity of D5 that always asks; taint adds no per-call ask for these tools, which is why D3 and D5 do not depend on it. `PreviewAsync` returns the host-observed target (application and window title from `ListWindows`, never model text) and a `CoworkGrantKey("computer.app", AppIdentity)`. Taint: screenshots and window lists are `IsUntrusted` blocks, so a Computer Use session is tainted from its first frame (ADR-0032 D6); this record adds nothing to turn that off. Every call is also written to the `ICoworkToolAudit` of ADR-0032 (no arguments, no bytes), whose desktop writer is the local owner-only hash-chained JSONL `FileCoworkToolAudit` (the `ComputerAuditLog` pattern), in addition to the local log of D7, which is more detailed; neither leaves the device and no ledger writer or `cowork_events` row sits behind either. Every description tells the model the tool order connector, then browser, then screen; that screen text is untrusted data; and that only direct user messages authorise consequential actions (the policy text of omp's own `computer-use.md`, report 07 section 3.0). Every result is wrapped in a labelled envelope ("untrusted screen content from <application>, frame N, captured at T"). The omp `computer` and `browser` preludes are switched off in Cowork sessions by the `--config` overlay that the Cowork session profile owns (ADR-0032 D4; providers never write it) with `computer.enabled=false` and `browser.enabled=false` (report 07 section 4.4 item 7), and a test asserts the overlay; the effect at run time is unverified (OQ-387). Result caps of ADR-0032 (at most 2 images, 3 MiB each) are tighter than D9's 5 MiB default, so `Vision:MaxImageBytes` defaults to 3 MiB and one image per result.

### D9. Vision loop, coordinates, DPI, image budget

Loop: `screenshot` returns frame N (PNG plus text: frame id, display, native and scaled size, scale factor, cursor position in scaled coordinates); the model calls an action with `frame_id` and scaled coordinates; the host maps back with `CoordinateMap` (pure, unit-tested, handles negative origins, multi-display and rounding), executes, waits a settle delay (400 ms, option 100 to 2000) and by default returns a post-action frame (`PostActionFrame=Auto`; `Off` returns text only). Three identical consecutive frame hashes add a "no visible change" hint to the text. The model sees one display at a time (default: the display holding the focused granted window, else primary); a display layout change invalidates the frame (`StaleFrame`).

- Frame pipeline (own code, no package): capture native BGRA, keep the full-resolution frame in memory for `zoom` (latest frame per session only, released after 60 s idle), mask, downscale with an area filter to `Vision:LongEdgePx` (default 1280, the coordinate-safe size of report 07 section 4.1; 2576 for models marked high resolution), encode PNG with `System.IO.Compression.ZLibStream`. A frame over `Vision:MaxImageBytes` (default 3 MiB, the per-image cap of the Cowork tool host in ADR-0032 D5; the Bedrock limit of 5 MiB in report 07 section 4.1 is looser) is re-encoded at 0.85 scale steps up to four times, then `FrameTooLarge`. JPEG is not offered (no encoder in the BCL).
- Masking: by default a frame shows only granted applications' windows; everything else, including desktop, other applications and own-process windows, is painted black with a text label. `VisibleRegionMasker` is a pure function over `ListWindows` z-order and bounds (unit-testable without a display). It is defence in depth: window bounds from a compositor can be wrong (shadows, decorations, scaling).
- Budget: tokens are `ceil(w/28)*ceil(h/28)` per image, so 1280 by 720 costs about 1,200 tokens (report 07 section 4.1, read from the Claude vision documentation; other providers not read, so sizing is a per-model option `Vision:ModelOverrides` keyed by omp model id, OQ-385). The host controls image size and count per call (at most one image per result); it cannot rewrite the omp or model context, so history trimming belongs to omp's compaction [INFERENCE: not read]. The host adds a per-session image cap (`Vision:MaxImagesPerSession`, default 80) after which `ImageBudget` tells the model to continue with text tools or ask the user.
- DPI: backend coordinates are physical pixels on X11 and Windows (the Windows backend wraps each call in per-monitor-v2 DPI awareness, `SetThreadDpiAwarenessContext`); on macOS CGEvent uses points and capture uses pixels, so `DisplayInfo.ScaleFactor` carries the ratio and the backend converts; `CoordinateMap` is the only place scale is applied.

### D10. Backends

**Linux X11 (decided, verifiable here).** Calls to the system libraries `libX11.so.6`, `libXtst.so.6` and `libXrandr.so.2` through `DllImport` with `DefaultDllImportSearchPaths` and `Marshal` (the exemplar of `PosixProcessSignal.cs:15-16`; no unsafe blocks). Debian packages on this host: libx11-6 2:1.8.7-1ubuntu0.1, libxtst6 2:1.2.3-1.1ubuntu0.1, libxrandr2 2:1.5.2-2build1. They are loaded from the system, never bundled or redistributed. No managed library is adopted: `ScreenCapture.NET.X11` is LGPL-2.1-only and the author calls it slow and fragile (report 07 section 3.1), and SharpHook bundles a `libuiohook` whose licence is unresolved (same section); both rejected.
- Connection: one `X11Connection` owns a dedicated thread and a command queue, because Xlib is not thread-safe and the process must not depend on who called `XInitThreads`; `XOpenDisplay` uses `X11BackendOptions.DisplayName` (null reads `DISPLAY`), so tests pass an explicit private display and never touch the user's.
- Capture: `XGetImage` on the root window, ZPixmap, all planes, for a display rectangle (XRandR monitors via `XRRGetMonitors`; single-screen fallback `XDisplayWidth`/`XDisplayHeight`); window captures are crops of the root capture, so occluded content is never read from a window drawable. Full-frame `XGetImage` cost is the accepted price; XShm would be a pure optimisation with no behaviour change and is not part of this record.
- Input: `XTestFakeMotionEvent`, `XTestFakeButtonEvent` (buttons 1 to 3, scroll 4 to 7) and `XTestFakeKeyEvent`; presence is checked with `XTestQueryExtension` (absent: `InputInjectionUnavailable`). Text: character to keysym (`XStringToKeysym`, Unicode keysyms `0x01000000 | cp`), keysym to keycode and shift level through `XKeysymToKeycode` and the table from `XGetKeyboardMapping`; a character with no mapping uses a scratch keycode remapped with `XChangeKeyboardMapping` and restored after `XSync`, and a failed restore is logged and reported. Pointer motion is stepped in at most 8 moves so window managers see enter events.
- Windows list: `_NET_CLIENT_LIST_STACKING`, `_NET_WM_NAME`, `_NET_WM_PID`, `WM_CLASS`, `XGetWindowAttributes` plus `XTranslateCoordinates`; without a window manager (bare Xvfb) fallback to `XQueryTree` children of the root with `stackingSource=XQueryTree` reported.
- Hotkey: a second connection and thread with `XGrabKey` on the root for the chord over the lock-modifier combinations, an error handler to turn `BadAccess` into `KillSwitchUnavailable`, shutdown by closing the connection. XTest events pass grabs, so an agent-pressed chord would only stop itself, and the chord is in the forbidden list anyway.
- Availability: `DISPLAY` unset or `XOpenDisplay` fails, `NoDisplay`. Under SSH or containers this is the normal answer.

**Linux Wayland (decided: unavailable in v0.16.0).** A session is Wayland when `XDG_SESSION_TYPE=wayland` or `WAYLAND_DISPLAY` is set, even if `DISPLAY` points at XWayland. Calls into XWayland see and move only XWayland clients; a root capture of a Wayland desktop is black or partial, so silent use would look like a working tool that acts on the wrong windows. The backend reports `ComputerAvailability.WaylandUnsupported` with the message id `computer.unavailable.wayland` ("Computer Use needs an X11 session. You are signed in to a Wayland session. Sign out and choose the Xorg (X11) session on the login screen.") and no tool is registered. The portal route (`org.freedesktop.portal.RemoteDesktop` with `ScreenCast`, EIS for input, a PipeWire node for frames, report 07 section 3.2) needs a user dialog on every start, a libei and PipeWire binding that has no known maintained .NET option, and a compositor to test on; it is deferred (OQ-380).

**Windows (compile-checked only).** Input: `SendInput` with `MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_VIRTUALDESK` (normalised 0 to 65535 over the virtual desktop; the conversion is a pure function with tests), `KEYEVENTF_UNICODE` for text, scan codes for chords. UIPI: `SendInput` fails silently against a higher-integrity window (Microsoft Learn, report 07 section 3.3), so before injecting the executor asks the backend whether the target process is elevated (`OpenProcess` with `PROCESS_QUERY_LIMITED_INFORMATION`, `GetTokenInformation` `TokenElevation`) and denies with `ElevatedTarget`; a failed `OpenInputDesktop` means the secure desktop (UAC, lock screen) and denies with `SecureDesktop`. Capture: GDI `BitBlt` from the screen DC with `SRCCOPY | CAPTUREBLT` into a DIB section. `Windows.Graphics.Capture` is not used in v0.16.0: it draws a yellow border on Windows 10 and needs a Windows TFM or WinRT interop for no gain in this design; `ScreenCapture.NET.DX11` is LGPL-2.1-only (report 07 section 3.3). GDI cannot read hardware-overlay or protected video and returns black there; that is stated to the user, not worked around (OQ-381). Windows and displays: `EnumWindows`, `GetWindowTextW`, `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`, `EnumDisplayMonitors`, `GetDpiForMonitor`. Hotkey: `RegisterHotKey` on a message-only thread.

**macOS (compile-checked only).** Input: `CGEventCreateMouseEvent`, `CGEventCreateKeyboardEvent`, `CGEventKeyboardSetUnicodeString`, `CGEventCreateScrollWheelEvent2` posted with `CGEventPost` (`kCGHIDEventTap`) through `DllImport` to `ApplicationServices`; windows via `CGWindowListCopyWindowInfo` with a minimal CoreFoundation marshaller (titles need Screen Recording permission, [INFERENCE]). Capture: the system `screencapture -x -t png` run by the backend through the harness process abstraction (allowed because the project name starts with `Harness.`), because ScreenCaptureKit (`SCScreenshotManager`, macOS 14.0 and later, Apple documentation read 2026-10-28) has no maintained .NET binding and an Objective-C block bridge or a Swift helper cannot be compile-checked here. That `screencapture` is attributed to the Autonogrammer app for the Screen Recording grant when launched as its child is [INFERENCE] and the first thing a Mac run must check (OQ-382). Hotkey: Carbon `RegisterEventHotKey`, which needs no Input Monitoring permission [INFERENCE]. Mac App Store distribution can be refused for synthetic input (report 07 section 3.4, secondary source), so macOS builds are direct-distribution only.

**Elsewhere.** The Android and iOS heads, the web head, the API and cloud workers register `NullComputerUseBackend`, whose availability is `UnsupportedPlatform` with the message id `computer.unavailable.platform`; `computer.*` is not registered and Cowork says why in `computer.status` and in settings. Typed availability states: `Available`, `Disabled`, `UnsupportedPlatform`, `WaylandUnsupported`, `NoDisplay`, `PermissionMissing(kind)`, `InputInjectionUnavailable`, `KillSwitchUnavailable`, `IndicatorUnavailable`, `AuditUnavailable`, `SecureDesktop`; each maps to one `Remediation` id resolved to text in Presentation.

### D11. OS permission recovery flows

`IComputerPermissionAdvisor` (Presentation) turns `ComputerPermissionStatus` into a guidance panel. macOS: Screen Recording (`CGPreflightScreenCaptureAccess`, `CGRequestScreenCaptureAccess`, macOS 10.15 and later) and Accessibility for posting events (`AXIsProcessTrustedWithOptions` with the prompt option, macOS 10.9 and later, plus `CGPreflightPostEventAccess` and `CGRequestPostEventAccess`, 10.15 and later; availability read from Apple documentation 2026-10-28). The panel states what each permission allows, offers "Open System Settings" at the Privacy pane, then polls the status every second for at most 5 minutes while the panel is open, and says a restart of the application may be needed after granting Screen Recording and that macOS may ask to renew it periodically on recent versions (report 07 section 3.4, secondary). Windows has no capture or input permission, so the states are `ElevatedTarget` ("the application runs as administrator; restart Autonogrammer as administrator or use another application") and `SecureDesktop` ("a system prompt is showing; finish it, then resume"). Linux X11 has no prompts: `NoDisplay`, `InputInjectionUnavailable` ("the X server does not offer the XTEST extension") and Wayland as above. A missing permission never falls back to another mechanism.

### D12. Remote use from Dispatch

The relay carries commands, status and text, not screens (report 08 risk 1; OQ-73). ADR-0036 (D4 operations, D7 approval table) defines the relay side; this record fixes what the desktop does with it:

1. No relay operation reaches the executor or a backend primitive: the closed operation set of ADR-0036 has no `computer.*` operation, and `computer_use` is a tool class named in the `toolClasses` of a `cowork.task` payload, never the capability of a command. There is no click, type or capture operation. A hub, or an account token thief, cannot move the mouse.
2. A `cowork.task` whose `toolClasses` contains `computer_use`, on a desktop with `Cowork:ComputerUse:Enabled` and `Cowork:ComputerUse:AllowDispatchSessions` (default false; this is the `computer_use` capability `enabled` flag of ADR-0036 D2) both on, registers the `computer_*` tools. Every other session registers none, and a `code.prompt` session never does, so the Dispatch capabilities that need no local command prompt can never acquire screen control.
3. Approvals of Computer Use can only be answered on the desktop. ADR-0036 refuses `approval.decide` for them; this record adds that the in-session prompts (grants, sensitive actions) have no remote channel either. The command-level approval of ADR-0036 (every `cowork.task` naming `computer_use`, no stored allow, `Dispatch:CommandApprovalTimeout` default 5 minutes) is separate from the per-application and per-action prompts of D5 (120 seconds): both happen, the first before the session starts, the others during it. With no local user present (screen locked, no desktop interaction within the timeout) the answer is `NoLocalApprover`, the controller sees "waiting for approval on the desktop" and may cancel. The ceiling rule of `services/Autonogrammer.Api/Endpoints/ToolApprovalEndpoints.cs` (an allow above the request ceiling is 403) is not a substitute for any of this.
4. Grants created in a Dispatch-origin session have origin `Dispatch`, end with the command and in any case after 30 minutes (the Anthropic figure of report 06 C17 and S22, adopted as a ceiling by ADR-0036 D7) and never carry `AutoApproveTyping`; every sensitive class in D5 asks again. Revoking the device or pausing Dispatch withdraws them at once (ADR-0036 D8).
5. The indicator shows the controller device name; frames never leave the desktop except to the user's configured model provider, which the opt-in dialog names with its residency from the provider catalogue (ADR-0019) [INFERENCE: field names not re-read]. The controller may receive an audit-profile thumbnail only when the user turned on "show progress thumbnails on my other devices" (default off, OQ-389).
6. A queued `cowork.task` naming `computer_use` follows the 5 minute offline expiry of ADR-0036 D6; on delivery the local approvals still happen.

### D13. Reuse: Cua Driver, omp's native `computer` session, or own code

Default is own code. Cua Driver was evaluated per directory (`legal/LICENSING.md` and `libs/cua-driver/README.md` on `trycua/cua` main, read 2026-10-28): the root `LICENSE.md` is MIT and `libs/cua-driver/` has no licence file of its own (the raw URL `libs/cua-driver/LICENSE` returns 404), so it is MIT; the Rust workspace `libs/cua-driver/rust/Cargo.toml` states version 0.38.0 and `license = "MIT"`; the optional `cua-perception` extension bundles an AGPL-3.0-only OmniParser model and is a separate install; `libs/cua-driver-bench` and Cua Spaces are FSL-1.1-MIT; `libs/python/som` is AGPL-3.0-or-later. The release feed shows nightly tags (`nightly-cua-driver-rs-v0.38.1-nightly.20261028...`). Reasons against adoption now: on macOS the README requires the driver to run inside its own `CuaDriver.app` for a stable TCC identity (raw `cua-driver serve` is unsupported), which is a second signed and notarised application holding the grants instead of Autonogrammer; its background input without taking focus conflicts with the visible-pointer takeover model of D6; its MCP and permission-mode surface sits outside our gate unless it is wrapped as a backend, at which point we still write the gate, indicator and audit; only nightly builds were seen, which weakens pinning and provenance; and its Windows and macOS behaviour cannot be compiled or run on this host while our X11 path can. It stays an option behind `IComputerUseBackend` (a future `CuaDriverBackend` adapter, MIT, nothing from the FSL or AGPL directories; OQ-383). omp's native `computer` prelude (report 07 section 3.0) is disabled in Cowork sessions (D8) so one governed path exists.

## Threat model

| Threat | Effect | Mitigation | Residual |
| --- | --- | --- | --- |
| Prompt injection through screen content (a page, document or notification tells the agent to act) | The agent clicks, types or reads data for an attacker | Screen text is wrapped as untrusted in every result and tool description; only granted applications are visible (masking); tiers, denylist, forbidden chords and sensitive-action confirmation bound what an injected instruction can do; rate and step limits; kill switch; audit | A granted application with `Full` tier can still be misused inside its own scope; classifiers are not used. Rule of Two (report 07 section 5): do not combine this session with secret access; Cowork sessions that use Computer Use hold no workspace secrets (ADR-0032 to enforce) |
| Spoofing the approval UI (a fake dialog drawn on screen, or the agent clicking Allow) | The user or the agent approves an unseen action | No injection while a prompt is open; own windows hard-denied as targets and masked from frames; security phrase the model cannot read; prompt shows host-observed facts only | A user who ignores the phrase can be fooled; Wayland and some compositors may not honour top-most (Open risks) |
| Kill switch fails (hotkey taken, thread stalled, app hung) | Agent keeps acting | Registration verified before arming; separate thread and connection; Stop in three places; token checked between primitives; no arming without it | A hard hang of the whole process leaves the OS-level fallback: the user closes the application, which kills omp's process tree (existing harness behaviour, ADR-0020 D3) |
| Identity spoofing of an application (X11 `WM_CLASS` is client-chosen) | A hostile program inherits a granted application's tier | Prefer `/proc/<pid>/exe` basename; own and denied applications cannot be granted | A hostile local program is already inside the user's session; out of scope beyond this |
| TOCTOU between decision and click (window moves under the pointer) | Click lands on a different application | Re-resolve the window after the move and before button-down; abort on change | Races shorter than one resolve remain |
| Audit tampering or loss | No trace of an action | Hash chain, owner-only file, write-ahead record, deny on write failure | The user can delete the log; it is local by design |
| Remote hijack through the relay | Mobile or hub controls the desktop | D12: no relay primitive operation and no `computer.*` operation (Computer Use is a `cowork.task` tool class), local-only approvals, per-device opt-in, 30 minute Dispatch grants, indicator | Account token theft can queue a `cowork.task` naming `computer_use` but not approve it or its Computer Use |
| Secret leakage in frames or logs | Passwords or tokens reach the model provider or the log | Masking, credential-titled window redaction in audit view, no typed text or clipboard in logs, `type` into credential windows always asks | The model provider sees screens of granted applications; the opt-in dialog says so |

## Blocked, and what can be verified on this host

Verifiable here under a private Xvfb (display number chosen by `Xvfb -displayfd`, `-nolisten tcp`, never `DISPLAY` of the session; Xvfb 2:21.1.12-1ubuntu1.8): X11 capture and XTEST input against `xterm` and `xev` with `xdotool` 1:3.20160805.1-5build1 and `scrot` 1.10-1build2 as independent oracles, window listing with and without `xfwm4`, the hotkey, text typing including a scratch-keycode character, coordinate and pointer behaviour on one screen, plus every pure function (coordinate map, masking, downscale, PNG encoder, gate pipeline, rate limiter, audit chain, options validation) and the Avalonia dialog and indicator under `Avalonia.Headless` 12.1.4. Not verifiable here: Windows (SendInput, UIPI, GDI, secure desktop, `RegisterHotKey`), macOS (TCC, CGEvent, `screencapture` attribution, Carbon hotkey, Spaces), Wayland and portals, AT-SPI (no `at-spi2-registryd`), multi-monitor with real different DPI, non-US keyboard layouts, top-most behaviour over full-screen applications, model vision accuracy and cost, and the route `session/new.mcpServers` to a live omp turn (OD-07). Windows and macOS code is held to compile-checked status in the index and in the user-facing "experimental" label.

## Consequences

- Five new source projects and four test projects are registered entirely by the serialised scaffold step (slnx, slnf, `LayerMap.cs`, `ArchitectureTests.csproj` reference, lock files, project files, test projects); phase 73 units add code only and edit a registry file only for rows the scaffold manifest marks "per phase" (`docs/architecture.md` prose, parity audit rows); `THIRD-PARTY-NOTICES.md` is unchanged because no package is added. The NoProcess condition of `Directory.Build.props:52` keys on the `Harness.` prefix, which the rename tool renames (report 02 section 13, finding 6), so the five names above stay inside the exemption.
- The tool-result image contract (`ToolUpdateContent`) and transcript and export rendering must exist before frames are visible in Cowork (ADR-0032); until then Computer Use works but the user cannot review frames.
- `ICoworkToolProvider` placement decides one possible `SameLayerAllowed` entry.
- ADR-0036 must adopt D12; ADR-0034 may share `IComputerApprovalPrompt` through a generic Cowork approval service if ADR-0032 defines one, otherwise each keeps its own port.
- Cowork gets a Computer Use settings page (grants, denylist additions, kill chord, security phrase, audit, indicator test) and an opt-in dialog.
- No cloud or web Computer Use in v0.16.0.

## Candidate chosen

Own implementation, no new package: `IComputerUseBackend` and `IComputerActionGate` in `Autonogrammer.Harness.ComputerUse.Abstractions` and `Autonogrammer.Harness.ComputerUse`, with P/Invoke backends for X11 (libX11, libXtst, libXrandr from the system), Windows (user32, gdi32, dwmapi) and macOS (ApplicationServices, CoreFoundation, the system `screencapture`); Wayland reported unavailable; Cua Driver and omp's native `computer` session not adopted (decisions D1 to D13 above).

## Open risks

- Title-pattern sensitivity detection is heuristic and English-first; with no focused-element inspection a credential field in an untitled window is only protected by the type-asks default (OQ-384).
- The always-visible indicator and approval dialog may be covered by full-screen applications or not honoured as top-most by some X11 window managers and macOS Spaces; the gate denies when the indicator is absent from the window list, which can make Computer Use refuse in those setups (OQ-386).
- Window geometry used for masking and hit-testing can disagree with what a compositor shows (shadows, fractional scaling), so masking is defence in depth and a window can leak a few pixels.
- Windows and macOS code is compile-checked only: SendInput, UIPI detection, GDI capture, `screencapture` TCC attribution, Carbon hotkeys and the permission flows are unmeasured, as ADR-0009 states for the browser pane (OQ-381, OQ-382).
- Wayland users (a growing share of Linux desktops) get no Computer Use until the portal route is built (OQ-380).
- The initial application catalogue identifiers for Windows and macOS products are unverified, so a denylisted product may be missed until a runner checks them (OQ-388).
- omp may or may not honour `computer.enabled=false` in an ACP session, and reaching the gateway from a live omp turn is unverified (OD-07, OQ-387); if the native prelude stays reachable it bypasses this gate.
- Screenshots of granted applications go to the configured model provider, which may be outside the user's region; the opt-in dialog and the provider catalogue must say where (ADR-0019), and the owner has not confirmed the wording.
- The analyzer set under `AnalysisLevel latest-all` may require `LibraryImport` (with `AllowUnsafeBlocks`) instead of `DllImport` at first build; the exemplar suggests it does not (OQ-391).
- Typing through scratch-keycode remapping briefly changes the user's keyboard map on X11; a crash between remap and restore leaves the map changed until the next `setxkbmap` or session start.
- Approval dialogs cannot tell injected input from hardware input (ADR-0036 asks for a trusted input event); the guarantee rests on serialisation and own-window denial, which are unit-tested but cannot be proven against a compositor or window-manager quirk on this host (OQ-392 covers the session rule that limits what a misled agent holds).
