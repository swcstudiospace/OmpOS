# ADR-0031: Data plane namespaces, schema, telemetry sink and resilience

- Status: Proposed 2026-10-28
- Date: 2026-10-28
- Owner: autonogrammer-maintainers
- Deciders: autonogrammer-maintainers
- Scope: the Autonogrammer data plane for milestone v0.16.0: the physical names of every Dragonfly key, PostgreSQL/TimescaleDB object and GreptimeDB database that the product owns; the new tables that accounts, Cowork, Dispatch and artifacts need; the migration tool; the telemetry sink; the timeouts, retries, circuit breaker and bulkheads around each store; the degraded states the heads show; secret handling; the careful-use rule for the Substrate event ledger; and the test strategy. The research is [04-data-plane.md](../plans/v0.16.0-research/04-data-plane.md) (read fully), with [03](../plans/v0.16.0-research/03-api-auth-backend.md), [08](../plans/v0.16.0-research/08-dispatch-relay-prior-art.md) and [09](../plans/v0.16.0-research/09-project-recipe-and-conventions.md). The record is written with post-rename names (OmpOS becomes Autonogrammer, so `OmpOS.Api` is `Autonogrammer.Api`); line numbers cite the files as they are on disk before the rename tool runs.
- Owner decisions applied (settled, not reopened): hard cutover of every name we own, no compatibility alias; the external omp names (`omp`, `omp acp`, `~/.omp`, `OMP_*`, `models.yml`) keep theirs; sign-in is not required for Code mode, so the data plane is never on the Code-mode path; extend `Autonogrammer.Api` instead of adding a service; the Cowork agent is local and Dispatch is the account-bound relay; live Supabase and Railway checks are blocked, so tests use fakes and throwaway local containers.
- Ordering decisions with the accounts record (ADR-0030, number reserved, file not yet written when this record was drafted): this record owns the `sessions` migration and the session repository changes (D4, M0003); ADR-0030 only consumes them.

## Context

Nothing of Autonogrammer (then named OmpOS) is deployed on Railway: the API was never created (`docs/runbooks/hosting.md:41`, `docs/runbooks/evidence/railway-ompos-api-2026-10-21.md:3,30-42`) and the schema `ompos` did not exist on the Railway TimescaleDB on 2026-10-21 (same file, lines 25-26). Report 04 therefore recommended keeping the `ompos` physical names as "cosmetic to change"; the owner has since decided to cut every owned name over now, which removes that cost: no hosted data has to move. What stays risky is the shared infrastructure around us.

- Three existing namespaces are in use and are renamed here: Dragonfly prefix `ompos:` (`src/OmpOS.Coordination.Dragonfly/DragonflyKeys.cs:10`), PostgreSQL schema `ompos` with search path `ompos,public` (`src/OmpOS.Sessions.Postgres/PostgresSessionSchema.cs:33`, `ServiceCollectionExtensions.cs:39,48`), and OTLP header `X-Greptime-DB-Name=public` with instruments `ompos.*` (`docs/runbooks/hosting.md:107`, `services/OmpOS.Api/Metrics/ApiMetrics.cs:24-27`, `services/OmpOS.Api/Cloud/CloudMetrics.cs:41-46`).
- The live Substrate server shares the same Railway services: its ledger is GreptimeDB database `public` by default (`docs/plans/agent-loop/dossier-substrate.md:70`), it has an optional Dragonfly cache that was connected on the dev host (`dossier-substrate.md:21`), and the fabric tool lists the resources "Dragonfly, the TimescaleDB index, GreptimeDB" (`xd://mcp__substrate_fabric_status`, description only, tool not called), which contradicts the dossier's "vanilla Postgres" (`dossier-substrate.md:88`). Treat the Railway TimescaleDB cluster as shared.
- There is no migration tool: schema is idempotent `CREATE ... IF NOT EXISTS` run at API start under `pg_advisory_xact_lock` (`PostgresSessionSchema.cs:29-124`, `PostgresCloudAgentSchema.cs`), runtime and DDL use one credential, and no retention exists (`grep add_retention_policy`: 0 hits).
- Process-local state breaks accounts: `SessionRegistry` and `SessionLifecycleStore` are in-memory, so `GET /sessions` and the board are wrong after a restart (`services/OmpOS.Api/Services/SessionRegistry.cs:9-22`, `SessionLifecycleStore.cs:9-38`; R3 finding 2). `ISessionRepository` has no list-by-owner (`src/OmpOS.Sessions/ISessionRepository.cs`, `ListSessionIdsByStatusAsync` only).
- No resilience library is pinned: `Directory.Packages.props` has no Polly or `Microsoft.Extensions.Resilience`, and no `packages.lock.json` contains Polly. The repo hand-writes jittered backoff (`src/OmpOS.Sandbox/SandboxLifecycle.cs:181-299`) and a reconnect schedule (`src/OmpOS.EngineHost/ReconnectPolicy.cs:11-40`).

### D3. Dragonfly: a dedicated service, not an ACL user

Decision: Autonogrammer runs its own Dragonfly service `autonogrammer-dragonfly` on Railway (and its own container locally), with its own `DFLY_requirepass`, the image pinned by digest (`docker.io/dragonflydb/dragonfly:v1.27.1@sha256:385cb73078f4dabe43d536766842eab444f3d791b0fcf86951decdcbcda37917`, the digest already used by `deploy/compose.yaml:29` and `scripts/test-services.sh:12`), no volume (all state is reconstructible), and an explicit `--maxmemory` (flag and value verified in the throwaway container before use). Eviction stays off (no `--cache_mode`), because evicting a lease key would break mutual exclusion.

Why not an ACL user on the shared service: the Dragonfly ACL documentation describes key (`~`, `%R~`, `%W~`) and channel (`&`) patterns, but the same page says an `aclfile` "must not contain any keys or pub/sub DSL's because these yet are not supported" (https://www.dragonflydb.io/docs/managing-dragonfly/acl, read 2026-10-28; the page tracks the current release, not v1.27.1), the Railway Dragonfly runs the unpinned `latest` (Q-HOST-DFLY-PIN), and the Substrate prefix is unknown. An ACL user is allowed later as hardening only if `DragonflyAclTests` passes on the pinned image (OQ-341); it is not the isolation boundary.

Key grammar (one helper, `DragonflyKeyspace`, builds every key and channel):

```
autonogrammer:v1:<domain>:<tenant>:<entity>[:<id>]       tenant = 32 lowercase hex chars
```

| Domain | Key | TTL | Fail mode when Dragonfly is down |
| --- | --- | --- | --- |
| `lease` | `autonogrammer:v1:lease:run:{sessionId}` (renamed from `ompos:lease:run:`) | 30 s, renewed every 10 s (`CoordinationDefaults.cs:7,10`) | closed: the run is refused with 503 `data_plane_unavailable` (`component` Dragonfly, `reason` per D8), because a run without the lease can double-execute |
| `idem` | `autonogrammer:v1:idem:{sha256hex(scope\nkey)}` (renamed) | pending 60 s, completed 24 h (`CoordinationDefaults.cs:13,16`) | closed for prompt and command POSTs (503 `data_plane_unavailable` with `Retry-After`) |
| `presence` | `autonogrammer:v1:presence:{tenant}:{deviceId}` | 45 s, heartbeat every 15 s | open: the socket stays up, presence reads become `unknown` |
| `rl` | `autonogrammer:v1:rl:{policy}:{tenant}:{window}` | window plus 5 s | degrade to the in-process limiter of the replica, never to unlimited |
| `auth` | `autonogrammer:v1:auth:nonce:{sha256hex}` (device-hello challenge, ADR-0036) | 10 min | closed: the hello is refused and the device backs off |
| channel | `autonogrammer:v1:sig:session`, `autonogrammer:v1:sig:dispatch`; payload is an id only | n/a | open: signals are a hint, the poll is the safety net (`ISessionSignals.cs:7-18`) |

Rules (enforced by the helper and by a guard test): every write carries its TTL in the same command (`SET ... PX`, never `SET` then `EXPIRE`); a TTL above 24 h or no TTL is an `ArgumentOutOfRangeException` at the helper; every Lua script declares each touched key in `KEYS` (`DragonflyScripts.cs:4-17`); never `FLUSHDB`, `FLUSHALL`, `KEYS` or `SELECT` as isolation; the only scan is `SCAN MATCH autonogrammer:v1:*:<tenant>:*` for account erasure. Dragonfly holds only reconstructible state: Dispatch commands, accounts and devices live in PostgreSQL and Dragonfly only wakes readers (`ISessionSignals` rule, R4 section 8.1). `<tenant>` is the first 16 bytes of HMAC-SHA256 keyed with the secret `DataPlane:TenantHashPepper` over the account id, never an email or token. Config name: the existing `Coordination:Dragonfly:ConnectionString` now points at the dedicated service; no second connection string exists.

### D4. PostgreSQL and TimescaleDB

One database `autonogrammer`, one schema `autonogrammer`, reached by one `NpgsqlDataSource` per role (runtime `autonogrammer_app`, migration `autonogrammer_migrator`, optional support `autonogrammer_ro`). Roles and the extension are created by an operator-run bootstrap, not by the application: `deploy/data-plane/bootstrap.sql` (database, extension `timescaledb` in `public`, roles, `REVOKE CONNECT ON DATABASE autonogrammer FROM PUBLIC`, schema grants, `ALTER DEFAULT PRIVILEGES`), passwords read from psql variables set from the environment, never from the file. The runtime role has DML only (no DDL); append-only tables (`dispatch_audit`) grant it INSERT and SELECT only. Roles are cluster-global, so the `autonogrammer_` prefix keeps them apart from any Substrate role; our roles can still `CONNECT` to databases that grant it to PUBLIC but hold no object privilege there (checked by `has_database_privilege` and a cross-schema query in the role test). Row-level security is not used in v0.16.0: the API scopes every query by owner (the `FindOwnedSessionAsync` pattern, `SessionEndpoints.cs:417-431`, a foreign row reads as 404) and a contract test per store method proves it; RLS needs a per-connection setting on pooled connections and a hypertable performance check (OQ-342).

Tables. Existing tables keep their names (`sessions`, `session_events`, `session_tool_approvals`, `cloud_agents`); new tables use one flat naming scheme because the schema is now ours alone. Hypertables are marked H.

Phase 68 U3 authors M0001 to M0009; phase 74 U2 authors M0010 and adds it to the runner list. The runner applies every step up to the compiled head.

Ordering keys follow the repo's rule that a sequence is assigned under a row lock (`PostgresSessionRepository.cs:66`): the per-device `seq` under the `dispatch_devices` row, the per-account feed `id` under the `accounts` row (`feed_seq`), so a reader that resumes from `id > last` never skips a late commit. Dispatch commands are a regular table, not a hypertable, because the state machine updates rows and a hypertable unique key must contain the time column.

Repository changes owned here (phase 68, one unit, so the briefs stay file-disjoint): `ISessionRepository` gains `ListByOwnerAsync(string ownerId, SessionSurface surface, bool includeClosed, int limit, SessionCursor? cursor, CancellationToken cancellationToken)` (the surface is required: there is no unfiltered list, so a caller makes one typed call per surface; keyset on `(updated_at, id)`) and `SetClosedAsync(string sessionId, bool closed, CancellationToken cancellationToken)` (true when the flag changed); the in-memory twin and `PostgresSessionRepository` implement both. `Session` carries `Surface` and `ClosedAt`; `SessionSurface` {Code, Cowork} is created in `Autonogrammer.Contracts.Sessions` by this phase and reused by ADR-0030 (it is not `SessionKind`, which already means Chat or Terminal). The accounts phase (67) only calls the methods and deletes `SessionRegistry` and `SessionLifecycleStore` with the call-site migration.

Retention and erasure. Telemetry-class data has a limit now: `dispatch_events` 30 days, `dispatch_audit` 400 days (`DataPlane:Retention:*`, the audit floor is 90 days, validated), command bodies are nulled 7 days after a terminal state (`body_purged_at`), `ledger_outbox` rows 7 days after `sent_at`. User content (`session_events`, `cowork_events`, `artifact_versions`, `artifact_grants`) has no automatic limit in v0.16.0 because that is a product and legal decision (R4 D6, OQ-344); it is removed by user deletion and by account erasure. Erasure is one batched transaction per table family keyed by owner: dispatch tables, `cowork_events`, `artifact_grants`, `artifact_versions`, `artifacts`, `session_events` through the owner's session ids, `sessions`, `cloud_agents`, then `accounts`; the Dragonfly keys of the tenant are deleted by the scan above and expire within 24 h anyway. `dispatch_audit` stores `account_id_hash` (the same keyed hash as the tenant), not the account id, and is kept: after erasure no table maps the hash back to a person unless the pepper and an account id are both known.

Erasure addendum (ADR-0037 tables): the family `cowork_memory_entries`, `cowork_memory_settings`, `cowork_instructions`, `cowork_projects` is deleted by owner in that order (entries reference projects) in the same transaction group as `cowork_events`, before `sessions`. Hard deletes; nothing of these tables goes to Dragonfly, GreptimeDB or the ledger.

`add_retention_policy` is a Timescale License feature at 2.13.1 (`tsl/src/bgw_policy/retention_api.c` carries the Timescale License header; `drop_chunks` in `src/chunk.c` is Apache-2.0 but needs the table owner, which the runtime role is not). M0008 therefore checks `current_setting('timescaledb.license')` and fails with the named error `retention_requires_timescale_license` when it is not `timescale`; the alternative if the Railway template is the Apache edition is a one-shot service running `Autonogrammer.Api retention` with the migrator role (OQ-345). Compression is not used in v0.16.0.

### D5. Migrations: additive, reversible, run by a separate credential

No new package. The repo's own pattern (numbered idempotent C# steps next to the store, one transaction, advisory lock) is kept and given a ledger; the alternatives DbUp (MIT), FluentMigrator (Apache-2.0), EF Core migrations and Flyway (JVM) each add a dependency, a notice entry and a vulnerability-audit surface for a runner of about 300 lines.

- `autonogrammer.schema_migrations(version int PK, name text, checksum text, applied_at timestamptz, applied_by text)`; checksum is SHA-256 of the step's up SQL; a checksum that differs from the recorded one stops the run (`MigrationChecksumMismatch`).
- `IMigrationStep { Version, Name, UpSql, DownSql }` as C# raw strings; each step runs in one transaction under `pg_advisory_xact_lock(AdvisoryKey("autonogrammer.schema.migrations"))` (the key cannot equal a session id key because it contains dots and no session id does; the unit adds a test that generated session ids never contain `.`).
- Rules: up steps only `CREATE ... IF NOT EXISTS` and `ADD COLUMN IF NOT EXISTS`; no `DROP`, no `ALTER ... TYPE`, no `CREATE EXTENSION`, no `DROP SCHEMA` in an up step (guard test scans the step sources); `NOT NULL` columns only with a constant default. Each step ships a down step that drops only what it created. Down steps run by an operator (`Autonogrammer.Api migrate --down <version>`), never automatically and never in the release that shipped the up step; a destructive "contract" step ships one release after the code stopped using the object (expand then contract).
- Who runs it: a Railway one-shot service `autonogrammer-migrate` built from the API image with start command `dotnet Autonogrammer.Api.dll migrate` and restart policy never; it alone holds `Sessions:Postgres:MigratorConnectionString`. A Railway pre-deploy command was considered and rejected: it runs in a separate container but "has access to your application's environment variables" (https://docs.railway.com/deployments/pre-deploy-command.md, read 2026-10-28), so the migrator secret would sit in the API's variable set. Because the two services deploy independently, the API waits up to `DataPlane:Postgres:SchemaWaitSeconds` (default 120) for `schema_migrations` to reach the compiled head, then fails fast naming the key. A schema newer than the code is accepted (expand/contract keeps old code working) and reported as `SchemaAhead`.
- Development and tests: `Sessions:Postgres:AutoMigrate=true` runs the same runner with the runtime connection string; the option defaults to false and the validator refuses it in Production. The old `EnsureCreatedAsync` classes are deleted (clean cutover).

### D6. GreptimeDB telemetry sink

- Path: the existing OpenTelemetry SDK 1.20.0 with `OpenTelemetry.Exporter.OpenTelemetryProtocol` 1.20.0 over `http/protobuf` (`Program.cs:205-224`); no new package and no GreptimeDB client library. Endpoint `OTEL_EXPORTER_OTLP_ENDPOINT=http://greptimedb.railway.internal:4000/v1/otlp`; headers `OTEL_EXPORTER_OTLP_HEADERS=X-Greptime-DB-Name=autonogrammer,X-Greptime-Pipeline-Name=greptime_trace_v1,X-Greptime-Trace-Table-Name=autonogrammer_traces` (all three in the general variable, as `docs/runbooks/evidence/smoke-backend-local-2026-10-21.md:43-46` found for the pipeline header; the `Authorization` Basic header is added only in the hosting environment). The header names are those of https://docs.greptime.com/user-guide/ingest-data/for-observability/opentelemetry/ (read 2026-10-28).
- Database: `CREATE DATABASE IF NOT EXISTS autonogrammer WITH (ttl='30d')`, run by `scripts/data-plane/bootstrap-greptime.sh` (the `ttl` database option is documented at https://docs.greptime.com/reference/sql/create.md; checked against the pinned `greptime/greptimedb:v1.1.4` in the live test). It never touches `public`.
- Names: source and meter `Autonogrammer.Api`; instruments `autonogrammer.<area>.<name>` with a unit: the renamed `autonogrammer.sessions.count`, `autonogrammer.stream.latency`, `autonogrammer.parser.fallback.rate`, `autonogrammer.sandbox.provision.time`, `autonogrammer.cloud.*`, plus this record's `autonogrammer.dataplane.call.duration` (ms), `.retry.count`, `.breaker.transitions`, `.bulkhead.rejected`, `.dependency.state` (observable gauge) and `autonogrammer.ledger.outbox.depth`. Feature instruments (`autonogrammer.dispatch.latency`, `autonogrammer.auth.sign_in.count`, ...) are named by their ADRs under the same rule. Tags are bounded enumerations (`component`, `operation_class`, `result`, `reason`); never an account id, email, device name, session id or command body. GreptimeDB translates metric names to table names by its default `UnderscoreEscapingWithSuffixes` strategy (dots become `_`, unit suffixes are added), so `autonogrammer.dataplane.call.duration` lands in a table whose name starts `autonogrammer_dataplane_call_duration` [INFERENCE for the suffix]; the live test lists the real table names into the runbook.
- Delivery never blocks a request: the SDK batch processor drops the oldest data when its queue is full. The export state is observed by an `EventListener` on the exporter's event source counting failures (event source name verified in the unit) and by a 30 s `GET /health` probe with a 2 s timeout; the state means "reachable and not failing", not "accepted" (the SDK exposes no acknowledgement).
- Not renamed: nothing is written to `public` any more, so the Substrate ledger stays alone there. Whether static users can be limited per database is not verified (Q-HOST-GREPTIME-AUTH): the separate database is a namespace, not an access boundary, until `static_user_provider` is checked on v1.1.4 (OQ-346).

### D7. Resilience

A new L1 library `Autonogrammer.Resilience` (BCL plus `Microsoft.Extensions.Logging.Abstractions`; no package added) with four small types: a deadline wrapper (`CancelAfter` on a linked token), a retry with decorrelated jitter on an injected `Random`, a consecutive-and-ratio circuit breaker, and a semaphore bulkhead, all on an injected `TimeProvider`. Polly.Core 8.9.0 (BSD-3-Clause, https://github.com/App-vNext/Polly, version checked on NuGet 2026-10-28) was considered and rejected for now: the surface needed is four types, the repo already hand-writes jittered backoff, and a new package adds a notice, audit and lock-file surface; the switch condition is a feature that needs hedging or rate-limit strategies, which would be a superseding ADR. A pipeline is built once per dependency by the store registration; it never runs on a UI thread because stores exist only in the API process (the heads speak HTTPS to the API, with their own `CancellationToken` deadlines and no blocking calls).

| Setting (`DataPlane:*`, validated at start, keys named in errors) | PostgreSQL | Dragonfly | Ledger sink |
| --- | --- | --- | --- |
| Connect or op timeout | `Timeout=5` s connect, `Command Timeout=5` s interactive, 30 s background | 250 ms per op, 2 s connect (`connectTimeout`, `asyncTimeout`) | 10 s (the gateway's own limit, `SubstrateGateway.cs:12-16`) |
| Retry | 2 retries, only for reads and idempotent statements and only when `NpgsqlException.IsTransient`; delay 100 ms to 2 s decorrelated jitter; 8 s total budget | 1 retry, 20 to 80 ms jitter, only for reads and the idempotent Lua scripts | outbox attempts: 8, delay 5 s doubling to 10 min, jittered |
| Writes | never retried unless guarded by a unique key (idempotency key, `(device_id, seq)`); a serialisation failure retries the whole transaction once | `SET NX` claims are not retried after a reply | the outbox row is the retry state |
| Breaker | opens at 5 consecutive failures or 50 % of the last 20 calls within 30 s; open 15 s; one half-open probe | same thresholds, open 10 s | same thresholds, open 60 s |
| Bulkhead | pools `interactive` (16) and `background` (4) inside `Maximum Pool Size=20` | one multiplexer, `interactive` 64 in flight | 2 in flight |

Values are the shipped defaults of options classes; the validator bounds them (for example the retry budget may not exceed the command timeout times 2). Cancellation is never swallowed: an `OperationCanceledException` from the caller's token passes through, a deadline expiry becomes `DataPlaneTimeoutException` with the component, never the connection string.

### D8. Health and the degraded states the heads show

`GET /health/live` stays anonymous and data-plane free; Railway's healthcheck path is `/health/live`, so a store blip cannot fail a deploy. `GET /health/ready` stays anonymous and boolean: unhealthy when PostgreSQL is unreachable, the schema is behind the compiled head, or Dragonfly is unreachable while `Coordination:Store=Dragonfly`. A new authenticated `GET /status/data-plane` returns a `DataPlaneStatus` (contract in `Autonogrammer.Contracts.DataPlane`, additive; the scaffold step bumps `ContractVersion` to 1.6.0 and no phase edits it): one row per component {Postgres, Dragonfly, Telemetry, Ledger} with `State` {Healthy, Degraded, Unavailable, Disabled} and a closed `Reason` {None, CircuitOpen, Timeout, AuthFailed, NotConfigured, SchemaBehind, SchemaAhead, RetentionUnsupported, ExporterFailing, LedgerBacklog}; it carries no host name, port, version or message text. The same states travel in the 503 problem `data_plane_unavailable` (`component`, `reason`, `retryAfterSeconds`) so a head that is mid-request can name the cause. It is the only 503 problem type for a store outage: a refused run (lease down), a refused idempotent POST, PostgreSQL, Dragonfly and schema-behind all use it with the closed `reason`; there is no separate coordination problem type.

| Situation | What works | What the head shows (text and icon, never colour alone) |
| --- | --- | --- |
| PostgreSQL unavailable | Code mode (local, no sign-in); a signed-in head keeps its cached lists, marked stale | Account, Cowork history and Dispatch show "Your account service is not reachable. Code mode is unaffected. Retrying." with the retry time; no new Cowork chat or Dispatch command is accepted |
| Dragonfly unavailable | reads, stored sessions; runs (lease down) and command POSTs are refused with 503 `data_plane_unavailable`, `component` Dragonfly (fail closed, D3) | Cowork send and Dispatch send show "Starting work is paused while the coordination service recovers"; device presence shows "unknown", never "offline" |
| Schema behind (deploy window) | nothing signed-in | "The service is being updated" with retry; Code mode unaffected |
| Telemetry failing | everything | nothing for users; the operator view shows `ExporterFailing` |
| Ledger enabled, backlog | everything | nothing for users; the operator view shows `LedgerBacklog` with the count |
| Ledger disabled (default) | everything | "Disabled" row in the operator view only |

### D9. Secrets and reachability

- Hosted: the API reaches PostgreSQL, Dragonfly and GreptimeDB only over `*.railway.internal`, which Railway documents as encrypted WireGuard tunnels ("use `http://`, traffic is already encrypted", https://docs.railway.com/networking/private-networking/how-it-works.md, read 2026-10-28); PostgreSQL still uses `SSL Mode=Require` (`hosting.md:101`) as a second layer. No TCP proxy and no public domain is created for `autonogrammer-dragonfly` or the new database; the existing TimescaleDB TCP proxy and the public GreptimeDB domain are exposures this milestone does not depend on (OQ-347 asks the owner to close them).
- Credentials: set only as Railway service variables of the service that needs them: `autonogrammer_app` password in `autonogrammer-api`, `autonogrammer_migrator` password in `autonogrammer-migrate` only, `DataPlane:TenantHashPepper` in `autonogrammer-api`. The template superuser (`PGUSER`, `PGPASSWORD`) is used once by the operator for the bootstrap and is no longer referenced by the API (this amends the variable table of `hosting.md:96-111`). No credential, connection string or pepper is in any client build, the desktop, the web bundle or the mobile head: heads hold only the Supabase publishable key and the user's own tokens (ADR-0030). Startup and the validators name the configuration key, never the value (`CoordinationStartup.cs:61`).
- Desktop and mobile never speak PostgreSQL, Redis or GreptimeDB protocols; a desktop that is dispatched to holds an outbound authenticated connection and the API never dials it (ADR-0036).
- Compose and tests bind to `127.0.0.1` with random or env-required passwords (`deploy/compose.yaml:6`).

### D10. The ledger: careful use

Evidence. The repo contains no Solana code, cluster, RPC URL, signer or program id; the only mention is "Solana anchor" in a list of optional Substrate planes that are "all off when unset" (`dossier-substrate.md:80`). The one statement about the cluster is the description of the mounted tool `substrate_checkpoint_verify`: a `session.checkpoint` event is "inside an hourly Merkle root that was written to Solana devnet", with an `unverified` status for "a devnet reset", and "Read-only: no transaction is ever sent" (read 2026-10-28 through `xd://mcp__substrate_checkpoint_verify`, tool not called). So: the ledger is Substrate's append-only, hash-chained GreptimeDB event ledger (`dossier-substrate.md:83`); the Solana part is an optional hourly Merkle-root anchor on devnet, not a ledger and not durable (devnet can reset). Whether the anchor is enabled on the live host is unknown. Mainnet has no supporting evidence anywhere.

Rule. Autonogrammer MUST NOT hold a Solana key, send a transaction, or configure an RPC URL, and MUST NOT write to the ledger's database or tables; the only write path is Substrate's own `POST /events` through the existing `SubstrateGateway.EmitEventAsync` (`SubstrateGateway.cs:168`) under its endpoint rules (https or loopback http, 10 s, 1 MiB, no redirects, bearer in the header only, `SubstrateEndpoint.cs:20-45`). The sink is optional and off by default (`DataPlane:Ledger:Enabled=false`). Design:

- Source of truth stays PostgreSQL: `dispatch_audit` and the account audit rows are written in the same transaction as the state change; the ledger is a notarisation copy fed by `ledger_outbox` and a hosted pump with the D7 pipeline. A ledger failure never fails or delays a user request.
- Event shape: kind `note` (the closed `EVENT_KINDS`, `dossier-substrate.md:105,197`), `payload.action = "autonogrammer.audit.v1"`, `payload.item` = the audit id (a ULID), `payload.outcome`, a short fixed `summary`; no email, device name, command body, prompt, account id or IP. The account appears only as the keyed tenant hash. Because the ledger is append-only and cannot be scrubbed (`dossier-substrate.md:83,196`), anything written is permanent: the field list is a closed type with a test that fails on any new field.
- The closed `surface` list has no Autonogrammer entry (`xd://mcp__substrate_events_emit`), so the surface is whatever the token's surface is; adding one is a Substrate change (OQ-348).
- Development and tests never use the live instance on `127.0.0.1:7410` (`docs/plugins.md:186`, `dossier-substrate.md:196`): tests use a fake `SubstrateGateway` handler; the live-gated test needs `AUTONOGRAMMER_LIVE_SUBSTRATE=1` and a scratch instance URL and refuses port 7410.
- Verification only: Autonogrammer may call `checkpoint_verify` through `POST /mcp` (`SubstrateGateway.cs:142`) to show an audit entry's anchor status, labelled "devnet" and never described as permanent or legally binding.

### D11. Test strategy

- Gate (no live service beyond the two throwaway containers): resilience types on `ManualTimeProvider` with a seeded `Random`; migration runner and grants against a throwaway TimescaleDB 2.13.1 container (the existing `PodmanPostgresContainer` pattern, container names `autonogrammer-test-pg-<guid>`, test schemas `t_<guid>`, never `autonogrammer` itself); Dragonfly keyspace and fail-mode tests against `scripts/test-services.sh`; the OTLP sink against an in-process HTTP listener that records the request path, `X-Greptime-DB-Name` and the instrument names; the ledger against a fake handler.

A new `DataPlaneGuardTests` in `Autonogrammer.ArchitectureTests` asserts: the Dragonfly prefix constant is `autonogrammer:v1:`; the schema constant is `autonogrammer`; no first-party source uses `FLUSHDB`, `FLUSHALL`, `KEYS `, `CREATE EXTENSION` (outside `deploy/data-plane/bootstrap.sql`), `DROP SCHEMA`, or a Dragonfly write outside `DragonflyKeyspace`; no migration up step contains `DROP` or `ALTER ... ## Blocked, and by what

- Every hosted action (create `autonogrammer-dragonfly`, `autonogrammer-migrate`, the database, the roles, the Greptime database; set variables; any deploy): Railway deploys are paused (hosting Known blocker 5; `docs/runbooks/evidence/railway-ompos-api-2026-10-21.md:42,80`) and OQ-73 is unresolved. No Railway mutation is made by the implementation of this record.
- Public exposure of the API: the identity provider authority for the deployed API (OD-03, `docs/runbooks/hosting.md:45`; ADR-0030 supplies the Supabase settings and the owner actions).
- Private reachability of the three data services from the API: Q-HOST-PRIVNET, unverified until a deploy.
- Retention policy on the Railway template: depends on the Timescale edition of `timescale-postgis-ssl:pg16-ts2.13` (OQ-345) and Q-DATA-TSDB-VERSION (hypertable DDL never run on that image).
- Substrate prefix, table names and anchor status: `plugins/agent-substrate` is absent here (OQ-340).
- Greptime per-database authorisation and the `ttl` option on v1.1.4 outside the throwaway container: Q-HOST-GREPTIME-AUTH.
- Railway inventory conflict between 2026-10-21 and 2026-10-28 (`04` section 6): a read-only re-inventory must precede any provisioning (OQ-349).

## Consequences

- The runtime stops using the template superuser; the hosting runbook variable table and `.env.example` change, and a second service (`autonogrammer-migrate`) and a third data service (`autonogrammer-dragonfly`, one more Railway cost line) exist.
- `PostgresSessionSchema` and `PostgresCloudAgentSchema` as `EnsureCreated` classes, `SessionRegistry` and `SessionLifecycleStore` are deleted in the same milestone (the first two by phase 68, the last two by phase 67 after 68 lands).
- New projects: `src/Autonogrammer.Resilience` (L1, one `LayerMap` line, `Autonogrammer.slnx`, `Autonogrammer.Linux.slnf`, `ArchitectureTests` reference, locks) and its test project. `services/Autonogrammer.Api` gains a `ProjectReference` to `Autonogrammer.Harness.AgentLoop` (L2) for the optional ledger sink; `Autonogrammer.Sessions.Postgres` and `Autonogrammer.Coordination.Dragonfly` (L2) reference the new L1 library, so no same-layer exception is added.
- `docs/api/openapi.json` gains `GET /status/data-plane` and the 503 problem; the Web Demo handler needs a fixture.
- The ADR-0020 worker stays out of the data plane: it still has no database, telemetry or outbound call.

## Candidate chosen

Dedicated Dragonfly service with the keyspace `autonogrammer:v1:`; one `autonogrammer` database and schema in the shared TimescaleDB cluster with four roles, a hand-written numbered migration runner executed by a one-shot service, and additive tables for sessions, accounts, Dispatch, Cowork and artifacts; the existing OpenTelemetry SDK and OTLP exporter sending to a GreptimeDB database `autonogrammer`; a hand-written L1 resilience library; and an optional, default-off, outbox-fed use of Substrate's `POST /events` as the only ledger path. No new third-party package is introduced.

## Open risks

- The Substrate Dragonfly prefix and the location of its PostgreSQL index are unknown; the design avoids depending on them, but a shared TimescaleDB cluster still means a superuser mistake or a platform incident can reach both.
- `add_retention_policy` may be unavailable on the Railway template (Apache edition); until checked, hosted retention is unverified.
- A hand-written circuit breaker and retry are our own code to keep correct; the tests are deterministic but have no field experience.
- The separate migrate service and the API deploy independently; a failed migrate leaves the API waiting then failing fast, which is a visible but recoverable outage.
- The Railway private network, the Dragonfly `--maxmemory` flag behaviour and the Greptime `ttl` option are verified only in throwaway containers, not on Railway.
- The ledger is append-only and unscrubbable; a mistake in the audit event shape is permanent, hence the closed field type and the default-off switch.
- Greptime static users may not be restrictable per database, so the `autonogrammer` database is a namespace, not an access boundary.
- The tenant-hash pepper is a new secret whose loss or rotation changes every presence and rate-limit key and unlinks audit hashes; rotation needs a dual-key window that this record does not specify (OQ-350).
