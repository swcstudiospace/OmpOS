# ADR-0036: Dispatch relay: control of the user's desktops through an account-bound relay

- Status: Proposed 2026-10-28
- Date: 2026-10-28
- Owner: autonogrammer-maintainers
- Deciders: autonogrammer-maintainers
- Scope: how a signed-in client (a phone app, the web app or another desktop) sends tasks to one of the user's registered desktops through a relay hosted in `Autonogrammer.Api` (requirement group AG-74, milestone v0.16.0): the device registry and pairing, the device credential, the relay hub, the command envelope and its signature, ordering, acknowledgement, expiry, local approval, revocation, reconnect, presence, limits, audit, the client surfaces and the threat model. The research is [08-dispatch-relay-prior-art.md](../plans/v0.16.0-research/08-dispatch-relay-prior-art.md), with [03](../plans/v0.16.0-research/03-api-auth-backend.md), [04](../plans/v0.16.0-research/04-data-plane.md), [05](../plans/v0.16.0-research/05-supabase-auth-reference.md), [06](../plans/v0.16.0-research/06-cowork-parity-and-references.md) (row C18) and [09](../plans/v0.16.0-research/09-project-recipe-and-conventions.md). Out of scope: a full mobile app, push notifications, streaming of a screen or a browser, mirroring a desktop transcript into the API session log, and the Computer Use and Browser Use implementations themselves (ADR-0034, ADR-0035).
- Defaults taken 2026-10-28, none blocking: the transcript of a dispatched task is not mirrored to the API (only bounded progress text and a result summary are relayed); the audit ledger sink is off; the first launch runs one API replica; commands are signed by the hub only (no controller end-to-end signature yet).
- Naming: every name below is the post-rename spelling (OmpOS becomes Autonogrammer; for example `Autonogrammer.Api`). The repository on disk still uses the old names, so a cited path such as `services/OmpOS.Api/...` is written here as `services/Autonogrammer.Api/...` with the line numbers of the file as read on 2026-10-28.

## Context

Nothing in the repository is a relay, a device registry, a presence service or a signed command channel (08 section 1; OQ-68). About eighty percent of the mechanisms exist as parts: ES256 token issue and validation (`services/Autonogrammer.Api/Cloud/Workers/WorkerTokenIssuer.cs:10-18`, `services/Autonogrammer.AgentWorker/Security/WorkerJwtValidator.cs`), a one-JSON-object frame guard (`services/Autonogrammer.AgentWorker/Bridge/AcpFrameGuard.cs`), a WebSocket client with a bearer provider called on every connect and a 20 second keep-alive (`src/Autonogrammer.Harness.Acp/AcpWebSocketTransportOptions.cs:13,18-23`), resumable SSE with `Last-Event-ID` and a 200 ms poll fallback (`services/Autonogrammer.Api/Sse/SessionEventStreamer.cs:24`, `Endpoints/EventStreamEndpoints.cs:89`), the 15 second heartbeat and three-miss staleness rule of `HerdrHeartbeatMonitor` (`src/Autonogrammer.Harness.Herdr/HerdrHeartbeatMonitor.cs:13-19`), and a disabled-feature middleware (`services/Autonogrammer.Api/Cloud/CloudDisabledMiddleware.cs`).

The direction differs from ADR-0020. The cloud worker is a WebSocket server that the API dials (`AcpBridgeEndpoint.cs:13-14`); Dispatch is the inverse: a desktop is behind NAT and dials out. Browsers cannot set `Authorization` on a WebSocket, and the web head has only SSE code (08 section 1), so a controller never opens a socket. `Program.cs` does not call `UseWebSockets` today (only `services/Autonogrammer.AgentWorker/WorkerApp.cs:53` does). All API rate limits are one global bucket (03 section 6), `ISessionSignals` carries no payload (03 section 4), and `SessionRegistry`, `CatalogEventHub` and the webhook replay cache are process-local, so anything keyed to a socket must be routed through the store.

Owner decisions that bind this record and are not reopened: any signed-in client controls one of the account's registered desktops through the relay; desktops connect outbound only; the relay extends `Autonogrammer.Api` instead of adding a service; offline commands queue with a 5 minute expiry; Computer Use commands always need local approval on the desktop; sign-in is required for Dispatch; the Cowork agent is local (omp over ACP) plus this relay.

## Decision

### D1. Topology and placement

```
Controller (phone / web / other desktop)      Hub: services/Autonogrammer.Api/Dispatch/           Desktop connector (Native head)
 POST /dispatch/devices/{id}/commands ------>  validate, own-check, rate limit, sign, store row
 GET  /dispatch/events (SSE, Last-Event-ID) <-- status, presence and result feed                  outbound only, dials the hub
                                                command rows (Postgres, per-device seq) ---WS--> wss://<hub>/dispatch/devices/{id}/connect
                                                presence key + wake signal (Dragonfly)  <--WS--- ack / evt / res / hb
```

- The hub is a new module `services/Autonogrammer.Api/Dispatch/` in the existing API, laid out like `Cloud/` (registration, endpoints, options plus validator, metrics, hosted sweeper, `DispatchDisabledMiddleware`, `DispatchRouteMarker`). The module is the only code that signs a command. A separate service is not justified: the hub holds no secret the API does not already hold, the trust boundary (browser or phone, hub, desktop) is the same with or without a second process, and a new service costs a Containerfile, a LayerMap entry and a Railway service (09 section 2, decision D6). The condition to revisit is a scaling need that the API's replicas cannot meet.
- Routes (all behind the fallback policy, owner = `sub`, a foreign or absent device is the same 404 as in `FindOwnedSessionAsync`): `POST /dispatch/devices` (pair), `GET /dispatch/devices`, `GET /dispatch/devices/{id}`, `PATCH /dispatch/devices/{id}` (rename), `DELETE /dispatch/devices/{id}` (revoke), `GET /dispatch/devices/{id}/connect` (WebSocket, desktop only, device credential), `POST /dispatch/devices/{id}/commands`, `GET /dispatch/commands`, `GET /dispatch/commands/{id}`, `POST /dispatch/commands/{id}/cancel`, `GET /dispatch/events` (SSE).
- One more route, `DELETE /dispatch/devices` (revoke every device of the account), exists for "Sign out everywhere" and account deletion (D8). The module registers an `IAccountFeature` with key `dispatch` (ADR-0030 D8) so the account surface lists Devices.
- `app.UseWebSockets()` is added with `KeepAliveInterval` 20 seconds (the value of `AcpWebSocketTransportOptions.DefaultKeepAliveInterval`). Liveness is decided by the application heartbeat (D10), not by the framework's keep-alive timeout.
- The feature is off by default (`Dispatch:Enabled=false`): routes stay mapped so the OpenAPI document describes them, and `DispatchDisabledMiddleware` answers 404 `dispatch_disabled` after authorization, exactly like `CloudDisabledMiddleware`.
- The controller leg is HTTPS `POST` plus SSE only, with `Authorization: Bearer` on every request, as `SseEventStream` already does (03 section 5).

### D2. Device registry, pairing and the device credential

- A desktop pairs while the user is signed in. `POST /dispatch/devices` carries the account access token and requires a recent full sign-in. ADR-0030 D7 delegates the freshness rule to this record: the hub reads the claims of the already authenticated principal (it does not validate the token again; the fallback policy and the `services/Autonogrammer.Api/Accounts/` module do) and takes the newest `amr` entry whose method is not `token_refresh`; its timestamp must be no older than `Dispatch:Pairing:MaxSignInAge` (default 10 minutes). The access token's `iat` is not used because every refresh issues a new one. The `session_id` claim is stored on the device row (`paired_session_id`) for the audit trail. A token without a recent sign-in gets 403 `recent_sign_in_required` and the client runs the sign-in again, so enrolment is never possible with only a stolen access token that has aged. Whether Supabase keeps the original `otp` or `magiclink` entry across refreshes is [INFERENCE] and is checked in the first live run (05 section 2.1). Dispatch validates exactly one thing of its own, the device credential below, so no user-token validation is duplicated. Computer Use approvals need no token freshness: they are answered on the desktop (ADR-0035 D12).
- The desktop generates a P-256 key pair at pairing. The private key never leaves the machine and is stored only through `ISecretStore` under the name `autonogrammer.dispatch.device-key.<deviceId>` (the credential under `autonogrammer.dispatch.device-credential.<deviceId>`), using the operating system store of `Autonogrammer.Harness.Secrets.Os` (ADR-0030 D6). ADR-0030 D6 rule 4 applies: the owner-only file fallback is never used for a device key; when the operating system store is unavailable, denied or locked, Dispatch reports `KeyStoreUnavailable`, pairing is refused and an already paired desktop does not connect. The store implementation is composed in the Native head and handed to the connector, which sees only the abstraction. The request carries `name` (1 to 64 characters, trimmed), `platform`, `appVersion`, `protocolVersions`, the capability list and the public key as a JWK.
- The reply carries `deviceId` (UUID), the **device credential**, `hubOrigin`, the hub's command verification keys (`kid`, ES256 public JWK, validity window) and the limits the device must honour. The credential is an API-signed ES256 JWT with its own key variable (`Dispatch:Credentials:SigningKeyPem`, distinct from the command signing key `Dispatch:CommandSigning:KeyPem`): `iss` `Dispatch:Credentials:Issuer`, `aud` `autonogrammer-dispatch-device`, `sub` the device id, `own` the account id, `cnf.jkt` the SHA-256 thumbprint of the device public key, `jti`, `iat`, `exp`. Lifetime 30 days (`Dispatch:Credentials:Lifetime`, validator refuses more than 90 days). The hub stores the current `jti` per device; a renewal changes it, which invalidates every older copy of the credential. The hub sends a renewed credential in `welcome` when fewer than 7 days remain.
- Why a new audience and key: `ompos-worker` tokens (now `autonogrammer-worker`) authorise a worker bridge; reusing that audience or key would let one token class be presented as the other. The Supabase access token has `aud` `authenticated` and is accepted on every other route; the credential is accepted only by the named authentication scheme `DispatchDevice` on the connect route, and an access token is refused there. The connect route is therefore not under the bearer scheme: the OpenAPI transformer lists it with security scheme `DispatchDevice`, beside the anonymous operations and the other-scheme routes named in ADR-0030 D7 (`/auth/config`, `/source`, the webhook, `/cowork/artifact-render/{ticket}`).
- Validation uses the `WorkerJwtValidator` parameter set (algorithm allow-list ES256 only, issuer, audience, `exp` and `iat` required, lifetime cap, injected `TimeProvider`, header-only token). That class is internal to the worker service, so the parameter set is copied into `Dispatch/Devices/DeviceCredentialValidator.cs` (extraction into a shared library is OQ-422).
- Registry row (`dispatch_devices`, schema `autonogrammer`, created by migration M0005 of ADR-0031: `id`, `account_id`, `name`, `platform`, `public_key`, `created_at`, `last_seen_at`, `revoked_at`, `command_seq`). This record adds one additive step after M0009 (`cowork_projects_memory`, ADR-0031 D4), M0010 `dispatch_device_state`, file-owned by phase 74 unit 2 and registered in the migration runner's compiled list by that unit, with `ADD COLUMN IF NOT EXISTS` for `credential_jti`, `credential_expires_at`, `capabilities jsonb`, `app_version`, `protocol`, `revoke_reason`, `paired_session_id` and `last_source_prefix` (coarse: IPv4 /24 or IPv6 /48, kept only on the device row, never in the audit table), and a unique `(id, account_id)` so command rows can carry a composite foreign key. Rename and revoke are account-scoped. Caps: 20 devices per account (`Dispatch:Limits:MaxDevicesPerAccount`), enforced atomically in the insert. The account id is the Supabase `sub` (text), written `userId` in the envelope.
- Capability list: each entry is `{id, version, enabled}` with `id` one of `sessions`, `code`, `cowork`, `browser_use`, `computer_use`. The desktop sends it at pairing and in every `hello`; the hub stores the newest snapshot and shows it in the Devices list. `browser_use` and `computer_use` report whether those tool classes may be used by a dispatched task on this desktop (for `computer_use`: `Cowork:ComputerUse:Enabled`, `Cowork:ComputerUse:AllowDispatchSessions` and the earlier local opt-in of ADR-0035 D12 all hold); they are never the capability of a command. A command whose capability is not `enabled` on the desktop is refused at the device with `capability_disabled`, and the hub refuses to enqueue a command whose capability the snapshot lacks or disables (409 `capability_unavailable`).

### D3. Connect handshake and frame set

1. The desktop opens `wss://<hub>/dispatch/devices/{id}/connect` with `Authorization: Bearer <credential>`, read by `AcpWebSocketTransport` through `BearerTokenProvider` on every connect. Before the upgrade the hub answers plain HTTP: 400 not a WebSocket request, 401 credential missing, invalid, expired or superseded (body `credential_invalid`), 401 `device_revoked`, 403 device not owned by the credential's account or account unavailable, 426 unsupported protocol, 429 connect rate exceeded, 503 hub not ready. A request that carries an `Origin` header is refused with 403 (a browser must never reach this route).
2. The hub sends `challenge` (`nonce` 128-bit random, `serverTime`, `origin`, `protocols`). The nonce is stored as `autonogrammer:v1:auth:nonce:{sha256hex}` with `SET NX PX` (10 minutes, the `auth` domain of ADR-0031 D3) and deleted when the `hello` is verified, so a challenge is single use across replicas; with Dragonfly unreachable the hello is refused and the socket closes with 1013 (the `auth` domain fails closed). The desktop answers `hello` with a signature by the device private key over `autonogrammer-dispatch-hello-v1`, `nonce`, `deviceId`, the hub origin the desktop believes it reached and `lastAppliedSeq`. The hub verifies against the registered public key; a failure closes with 4002. Binding the origin means a hostile relay cannot reuse a handshake against the real hub.
3. The hub sends `welcome` (`serverTime`, heartbeat interval, current `kid` set, optional renewed credential, `resumeFromSeq`). The desktop computes `clockOffset = serverTime - localTime`; only hub time decides `expiresAt`.
4. Frame set, each a single JSON text frame of at most 1 MiB (the `AcpWebSocketTransportOptions.DefaultMaxFrameBytes` limit): hub to device `challenge`, `welcome`, `cmd`, `revoke`, `err`; device to hub `hello`, `ack`, `evt`, `res`, `hb`, `err`. Every frame carries `v` (the relay protocol version, 1) and `t`. The same rule as `AcpFrameGuard` applies in both directions: valid UTF-8, exactly one JSON object, no duplicate property names (checked in one pass with `Utf8JsonReader`), unknown `t` refused with `err{unsupported_frame}` and a close 1008 after three. Binary frames are ignored. The kind and operation sets are closed enums per `v`; an unknown `op` is never executed.
5. Newest wins: a second authenticated connection for the same device closes the older one with 4009. The worker bridge's 409 is wrong here because a half-open socket after a network change would block the reconnect until the TCP timeout (08 section 4.9).
6. Close codes (RFC 6455 application range, reserved 4000 to 4099 for Dispatch): 1000 normal, 1001 hub shutting down (reconnect), 1007 frame is not one JSON object, 1008 policy violation (replayed or out-of-order frame, repeated bad frames), 1009 frame over 1 MiB, 1011 internal error, 1013 try again later (PostgreSQL or Dragonfly unavailable; reconnect with jitter), 4001 device revoked (terminal), 4002 credential or proof invalid (terminal until re-pair), 4009 replaced by a newer connection, 4010 unsupported protocol version (reason lists the supported ones; terminal until update), 4011 account unavailable (disabled or deleted; terminal), 4020 rate limited (reason carries a retry delay).

### D4. Command envelope and signature

`cmd` carries: `v`, `t:"cmd"`, `commandId` (26-character ULID generated by the hub, equal to `dispatch_commands.id`; the device deduplicates on it), `seq` (per-device, hub-assigned), `userId` (the account id), `deviceId`, `capability`, `op`, `issuedAt`, `expiresAt` (Unix seconds, hub clock), `nonce` (128-bit random, base64url, new for each delivery), `payload` (base64url of the operation's JSON bytes, at most `Dispatch:MaxPayloadBytes` decoded, default 65 536, validator refuses more than 262 144), `payloadSha256` (hex of the decoded bytes), `kid`, `sig`. The hub signs at delivery, over the exact bytes it serialises from the stored `body`, so nothing about the signature is stored and a redelivery after a key rotation is signed by the current key.

- `sig` is a raw (IEEE P1363, 64 byte) ES256 signature, base64url, over these canonical bytes, UTF-8, LF line ends, fixed order, no other whitespace: `autonogrammer-dispatch-cmd-v1` then one line each `v=`, `commandId=`, `seq=`, `userId=`, `deviceId=`, `capability=`, `op=`, `issuedAt=`, `expiresAt=`, `nonce=`, `payloadSha256=`, `kid=`. Every signed value is restricted to `[A-Za-z0-9._:-]` before signing and before verification, so no escaping exists and the bytes cannot be made ambiguous. Hashing the decoded payload bytes (not a re-serialised JSON tree) removes any canonicalisation of the body. The canonicalisation lives in `Autonogrammer.Contracts/Dispatch/DispatchCanonical.cs` and a shared test vector file proves hub and device build the same bytes.
- Operations (closed per `v=1`), with the capability each requires: `session.list`, `session.steer`, `session.cancel`, `approval.decide` (capability `sessions`); `code.prompt` (`code`; starts or continues a session with `SessionSurface.Code`, the discriminator of ADR-0030); `cowork.task` (`cowork`; starts a session with `SessionSurface.Cowork`, ADR-0032; its payload may name `toolClasses`, a subset of `browser_use` and `computer_use`); `command.cancel` (any capability, targets a `commandId` of the same device). There is no `computer.*` operation and no operation that reaches the Computer Use executor (ADR-0035 D12 rule 1): a hub, or an account token thief, cannot move the mouse. Computer Use is a tool class of `cowork.task`: a `cowork.task` whose `toolClasses` contains `computer_use`, on a desktop with `Cowork:ComputerUse:Enabled` and `Cowork:ComputerUse:AllowDispatchSessions`, registers the `computer_*` tools (ADR-0035 D12); every other session registers none and `code.prompt` never does. `approval.decide` is refused with `policy_denied` for an approval of kind `computer` (ADR-0035 D12 rule 3) and for any request whose ceiling the remote decision would exceed (the rule of `ToolApprovalEndpoints.cs:12-20`). The payload schema of each operation is a source-generated record validated by the hub before signing and by the device before execution; unknown members are an error.
- What the signature does and does not give: it makes a captured frame useless on another device, after `expiresAt`, with another body, with another `seq` or for another user, and it lets the device reject a forged frame. It does not protect against a compromised hub, which holds the key (D15, row 3).
- The device accepts a `kid` only from the set delivered at pairing or in a `welcome` whose new keys are signed by a key already pinned. Hub key rotation ships the new public key at least 24 hours before it signs.

### D5. Ordering, delivery, acknowledgement, idempotency

- The command log is per device, append-only in effect (rows only change state). `seq` is allocated in the insert transaction by `UPDATE dispatch_devices SET command_seq = command_seq + 1 ... RETURNING` under the device row lock (the rule of ADR-0031 D4, as `PostgresSessionRepository.cs:66`), so allocation is strictly monotonic and gap-free; `dispatch_commands` carries the unique `(device_id, seq)` of M0005. The queue cap (`Dispatch:Limits:MaxQueuedPerDevice`, default 100) is checked in the same transaction.
- Delivery is at-least-once. The delivery loop of a connection reads rows with `seq > deliveredSeq` in state `queued`, wakes on a signal and falls back to a 200 ms poll, writes each as a `cmd` frame in `seq` order and marks the row `delivered` after the write completes. `deliveredSeq` starts at `hello.lastAppliedSeq`, so a reconnect redelivers everything the device never durably received. Sequence numbers delivered are strictly increasing but may have gaps (an expired or cancelled command is never delivered); the device refuses `seq <= highWater` as a duplicate and never waits for a missing number.
- The device persists `highWater` and a bounded set of recent `commandId` values (1,024) atomically (the `AtomicFile` pattern of `Autonogrammer.Harness.Automations`) before it sends `ack received`, so a restart cannot execute a delivered command twice. At-least-once transport plus this idempotent apply is effectively once.
- Acknowledgement states reported by the device: `ack{state:"received"}` (verified, persisted), `evt{kind:"approval_pending"}` while a local prompt is open, `ack{state:"accepted"}` (policy passed and approval granted), `ack{state:"running"}`, then `res{state:"completed"|"failed"|"cancelled"}`; `ack{state:"duplicate"}` answers a re-delivery. Hub-side states: `queued`, `delivered`, `received`, `awaiting_approval`, `accepted`, `running`, `completed`, `failed`, `cancelled`, `expired`. Every transition is a compare-and-set against the allowed table; an out-of-table frame (a replayed `res`, a `ref` that belongs to another device) is a no-op plus an audit row, never an error to the peer. The hub marks a command `delivered` on socket write and never marks it completed without a `res`.
- Failure reasons are a closed enum shown to the user: `expired`, `revoked`, `signature_invalid`, `unsupported_version`, `unsupported_operation`, `capability_disabled`, `approval_denied`, `approval_timeout`, `policy_denied`, `payload_invalid`, `payload_too_large`, `device_busy`, `device_restarted`, `execution_error`, `timeout`, `cancelled_by_user`, `internal`. A `res` text field is bounded to 4,096 characters and passed through the redactor; `evt` text to 1,024.
- Controller idempotency: the `Idempotency-Key` header (1 to 128 visible ASCII, the rules of `IdempotencyKeyHeader`) is stored in `dispatch_commands.idempotency_key`, and the unique `(account_id, device_id, idempotency_key)` of M0005 is the authority. The same key with the same SHA-256 fingerprint of the canonical request returns the original 202 body with the same `commandId`; a different fingerprint is 409 `idempotency-key-reused`. The Dragonfly `idem` domain is not used, because its completion is best-effort (`IdempotencyCompletion.cs`, 08 risk 9).

### D6. Expiry and the offline queue

- `expiresAt = issuedAt + Dispatch:QueueTtl`, default and maximum 5 minutes (the validator refuses a larger value, the pattern of ADR-0020's 15 minute cap). It is the delivery deadline: a command that the device has not acknowledged as `received` by then is `expired` and is never delivered. A command for an offline device is queued and carries the same 5 minutes. A controller may send `queueIfOffline:false`, which turns an offline device into 409 `device_offline` at once.
- A sweeper (hosted service, injected `TimeProvider`, every 15 seconds) moves overdue `queued` and `delivered` rows to `expired`, appends the feed event and the audit row. Command bodies are nulled by the retention rule of ADR-0031 D4 (`body_purged_at`, 7 days after a terminal state, `DataPlane:Retention:*`). The device also refuses a command whose `expiresAt` (corrected by `clockOffset`) is more than `Dispatch:ClockSkew` (default 30 seconds, at most 2 minutes) in the past, and a command whose `expiresAt - issuedAt` exceeds the hub's announced `queueTtl`. An expired approval or cancel can therefore never be approved later.
- After `received` the run is not bounded by the 5 minutes: a per-operation run limit (`Dispatch:RunLimits`, default 4 hours for tasks, 60 seconds for `session.*` and `command.cancel`) ends it with `failed(timeout)` and a `command.cancel`. A local approval wait is bounded by `Dispatch:CommandApprovalTimeout` (default 5 minutes) and ends with `failed(approval_timeout)`.
- A device that disconnects while a command runs keeps that command `running` with the device shown offline (never "completed", the `Lost` rule of Herdr). On reconnect `hello` lists the ids it still runs (at most 32); a command the hub believes running that the device neither runs nor reports is set `failed(device_restarted)`.

### D7. Local approval policy

Policy lives on the desktop and cannot be raised remotely; the hub and the controller can only ask. In this record "mode" means only `CoworkPermissionMode` (Manual, Auto shown as "Auto (rules)", Skip; ADR-0032, ADR-0037): the table below is a per-capability command policy, not a mode, and a dispatched task never changes the mode. `Skip` needs `FilesystemIsolated` or a per-session acknowledgement (ADR-0032); a dispatched task can supply neither.

| Capability | Default | Can the user relax it? |
| --- | --- | --- |
| `sessions` read operations (`session.list`) | accepted without a local prompt | yes |
| `sessions` control (`session.steer`, `session.cancel`, `approval.decide`) | accepted without a local prompt, bounded by the existing tool approval ceiling | yes |
| `code`, `cowork` | disabled until the user turns it on at the desktop; once on, accepted without a local command prompt, under the desktop's existing `CoworkPermissionMode` and tool approvals, which a dispatched task never changes or raises | yes |
| `toolClasses` `browser_use` in a `cowork.task` | refused (`capability_disabled`) unless Browser Use is enabled for dispatched sessions on the desktop; the policy of ADR-0034 then applies and Dispatch only supplies the origin label (OQ-427) | per ADR-0034 |
| `toolClasses` `computer_use` in a `cowork.task` | refused unless `Cowork:ComputerUse:Enabled`, `Cowork:ComputerUse:AllowDispatchSessions` (default false) and the earlier on-desktop opt-in all hold; then **a local approval at the start of every such task**, and every action is decided by the local gate and prompt of ADR-0035 (`IComputerActionGate`, `IComputerApprovalPrompt`); no stored allow, no remote decision; with no local user present the controller sees "waiting for approval on the desktop" (`NoLocalApprover`) and may cancel | no: the floor is hard-coded and has no setting |

- A local approval prompt shows the device name of the controller, the operation, the capability, the requested `toolClasses` and the first 200 characters of the task text as plain text, never markup. Approve once, Deny, or Deny and pause Dispatch. The integrity of the prompt rests on ADR-0035 D3 and D5: no input is injected anywhere while a prompt is open, own-process windows are hard-denied as targets and masked from every frame the model sees, so the agent cannot approve its own task.
- While any dispatched command is accepted or running, the desktop shows a persistent "Remote task running" strip naming the controller device and offering Stop; a task that uses Computer Use additionally gets the on-screen indicator of ADR-0035 D6 labelled "Remote (Dispatch): <device>". Computer Use grants created in a Dispatch-origin session have origin `Dispatch`, last 30 minutes and never carry `AutoApproveTyping` (ADR-0035 D12 rule 4; the Anthropic figure in 06 row C18).
- A global switch "Pause Dispatch" on the desktop stops accepting commands without revoking the pairing; the device reports `status:"paused"` in `hb` and the hub fails queued commands with `policy_denied`.

### D8. Revocation

`DELETE /dispatch/devices/{id}` (and `DELETE /dispatch/devices`, which revokes every device of the account and is what "Sign out everywhere" of ADR-0030 D5 calls first, best effort, before the global logout; account deletion does the same) sets `revoked_at` and clears the credential `jti` in one transaction, sets every `queued` and `delivered` command to `cancelled` (reason `revoked`) and every running one to `failed(revoked)`, deletes the presence key, publishes a revoke signal for other replicas, sends `revoke`, and closes the socket with 4001. The next connect is refused before the upgrade with 401 `device_revoked`. On `revoke`, 4001 or that 401 the desktop stops accepting commands, cancels every session it started for Dispatch, withdraws every Computer Use and Browser Use grant derived from a dispatched command, deletes the device credential and private key, and shows a persistent notice. A revoked device never reappears: re-pairing creates a new device id. A plain sign-out on the desktop does not revoke: the connector stops (state `SignedOut`), pairing and key stay, and a later sign-in as a different account is refused with `PairedToAnotherAccount` until the desktop is unpaired. A hub that cannot reach Postgres refuses to connect any device (fail closed). Revocation latency target: the socket is closed within 2 seconds on the same replica; a revoked offline desktop learns at its next connect.

### D9. Reconnect

The connector owns an unbounded reconnect loop with full jitter: delay = uniform(0, min(30 s, 1 s x 2^attempt)), counter reset after a connection stays up for 60 seconds. `ReconnectPolicy` (`src/Autonogrammer.EngineHost/ReconnectPolicy.cs:10-11`) is bounded at 100 attempts, has no jitter and lives in a same-layer library, so it is not reused; its doubling shape is. Time and randomness are injected (`TimeProvider`, `IJitterSource`) so the loop is tested without sleeping. The loop obeys the close code table of D3: 1001, 1013 and network errors retry with jitter; 4020 waits the advertised delay; 4009 waits 60 seconds and shows "another Autonogrammer instance is connected as this device"; 4001, 4002, 4010 and 4011 stop and surface a specific state. A hub deploy closes every socket with 1001, so the jitter is what prevents a reconnect storm; the hub additionally limits connects per device (`Dispatch:RateLimit:ConnectsPerMinutePerDevice`, default 12).

### D10. Presence, heartbeat and replicas

- The desktop sends `hb` every 15 seconds with `lastAppliedSeq`, the number of running commands and a coarse status (`idle`, `busy`, `approval_pending`, `paused`). The hub treats three missed beats (45 seconds) as stale. WebSocket control-frame keep-alive stays at 20 seconds.
- Online = the presence key exists: `autonogrammer:v1:presence:{tenant}:{deviceId}` (ADR-0031 D3; `tenant` is the keyed HMAC of the account id from `ITenantHasher`), value `<instanceId>:<connectionId>`, written with `SET ... PX 45000` (never `SET` then `EXPIRE`), refreshed by a Lua compare-and-set that declares its key in `KEYS`, deleted on close. Keys are built only by `DragonflyKeyspace`; the presence helper is the one ADR-0031 adds to `Autonogrammer.Coordination.Dragonfly`. `last_seen_at` is persisted at most every 60 seconds.
- Wake: a command insert publishes the device id (an id, never the command) on the channel `autonogrammer:v1:sig:dispatch` through a new `IDispatchSignals` (interface in `Autonogrammer.Coordination`, Dragonfly implementation next to it); the replica that holds the socket wakes its delivery loop. The store is the queue, the signal is a hint, the poll is the safety net (the model of `SessionEventStreamer`). A dropped signal costs at most 200 ms.
- First launch is one replica (`Dispatch:ReplicaMode=Single`). The path to several replicas is configuration, not a redesign: `ReplicaMode=Multi` starts the signal subscriber on every replica, and the options validator refuses it unless `Coordination:Store=Dragonfly` with a configured connection and the Postgres store. Outside Development the validator requires Dragonfly in both modes (the `auth` nonce and presence live there); the in-memory coordination store is allowed only in Development with `Single`. The user-level feed never uses `CatalogEventHub`: its event ids come from `accounts.feed_seq` under the account row lock (ADR-0031 D4), so a position from any replica resumes without skipping a late commit.
- Failure behaviour follows ADR-0031 D3 and D8. Dragonfly unreachable: established sockets stay up, presence reads become `unknown` (never "offline"), new hellos are refused (1013), command POSTs are refused with 503 `data_plane_unavailable` and `Retry-After` ("Starting work is paused while the coordination service recovers"), and rate limits degrade to the in-process limiter. PostgreSQL unreachable: every Dispatch write and connect fails closed.

### D11. Limits

Per-account token bucket partitioned by `sub` on every Dispatch route (policy `DispatchCommands`, default 30 commands per minute, burst 10; `DispatchPairing` 5 per hour; `DispatchRead` 120 per minute), because the existing policies are one global bucket (`SessionRateLimiterPolicy.cs:33-48`). Per-device queue cap 100, devices per account 20, payload 64 KiB, frame 1 MiB, result text 4,096 characters, progress text 1,024 characters and at most 50 progress events per command. 429 uses `RateLimitRejection.Handler` with `Retry-After`. Failed device connects are rate limited per source address and per device id; the source address comes from the forwarded-header configuration of the Railway edge [INFERENCE: not verified].

### D12. Audit

- Append-only hypertable `dispatch_audit` (M0005: `account_id_hash`, `id`, `occurred_at`, `device_id`, `command_id`, `op`, `outcome`, `corr`). `account_id_hash` is the keyed tenant hash, not the account id; `corr` is `x-correlation-id`; `op` is the operation or empty; `outcome` is `<event>` or `<event>:<reason>` from the closed lists below; the runtime role has INSERT and SELECT only, retention is 400 days with a 90 day floor (M0008, ADR-0031 D4). A row never holds a payload, a prompt, a token, a device name, an email or an address. It is written in the same transaction as the state change it records. Events: `device.paired`, `device.renamed`, `device.revoked`, `device.connected`, `device.disconnected`, `device.connection_replaced`, `command.queued`, `command.delivered`, `command.received`, `command.awaiting_approval`, `command.accepted`, `command.running`, `command.completed`, `command.failed`, `command.cancelled`, `command.expired`, `auth.rejected` (with the reason `credential_invalid`, `proof_invalid`, `device_revoked`, `replay`, `rate_limited`), and every failure reason of D5 as a reason.
- Optional tamper-evident copy: this record adds no sink. ADR-0031 D10 owns it: with `DataPlane:Ledger:Enabled` (default false) each audit write also inserts a `ledger_outbox` row in the same transaction, and a hosted pump sends it through `SubstrateGateway.EmitEventAsync` (`POST /events`, `src/Autonogrammer.Harness.AgentLoop/Substrate/SubstrateGateway.cs:168`) as kind `note`, `payload.action` `autonogrammer.audit.v1`, `payload.item` the audit id and a closed field set with no personal data. Dispatch passes only the closed `AuditLedgerEvent` fields (`IAuditLedger`, brief 68 unit 5). Autonogrammer holds no Solana signer, configures no RPC URL and sends no transaction; the ledger anchors Merkle roots on Solana devnet on its own schedule, devnet can reset, and no text may call the anchor permanent or mainnet (04 section 8.4). The `Surface` value is Substrate's closed set (ADR-0031 OQ-348). Tests never call a live ledger: it is append-only and unscrubbable and development traffic would reach production (`dossier-substrate.md:196`).

### D13. Data classification and retention

Command payloads are user prompts: private. They sit in `dispatch_commands.body` (jsonb), are nulled 7 days after a terminal state by the retention rule of ADR-0031 D4 (`body_purged_at`; the SHA-256 is not stored, the device holds the only copy of what it ran), are never logged and never copied into the audit table or the ledger. The result text (at most 4,096 characters) lives in `dispatch_commands.result` and in the feed payload; this record asks ADR-0031 to purge `result` text together with the body (OQ-423). The feed `dispatch_events` (hypertable `(account_id, id, occurred_at, kind, ref, payload)`, 30 day retention) holds state changes, failure reasons, progress text and result summaries; its `id` is assigned under the account row (`accounts.feed_seq`), so `Last-Event-ID` resumes by `id > last`, and an id older than the retention horizon is answered with a `resync` event, like `CatalogResyncEvent`. Payloads are not encrypted at the application layer in v0.16.0 (OQ-425). No transcript, screenshot or file leaves the desktop through the relay; a result is text. Streaming of a screen or a browser is not built until Railway answers the acceptable-use question in writing (OQ-73; `docs/runbooks/cloud-terminals.md:35,42`).

### D14. Client surfaces

- `Autonogrammer.Presentation/Dispatch/` (L2, framework-free): `IDispatchHost` (controller: list devices, rename, revoke, send, cancel, watch the feed; `FakeDispatchHost`, `NotConfiguredDispatchHost`, `DispatchHostException` with a failure kind, the pattern of `ICloudAgentsHost`), `IThisDeviceHost` (desktop only: pairing, status, per-capability policy, pending approvals), `DevicesViewModel`, `DeviceRowModel`, `DispatchViewModel`, `DispatchCommandRowModel`, `PairThisDeviceModel`, `DispatchApprovalModel` and the phase enum `DispatchPhase`: `NoDevices`, `DeviceOffline`, `Queued`, `PendingApproval`, `Running`, `Failed` (with the typed reason), `Completed` (with the summary), `Cancelled`, `Expired`, plus the screen-level states `SignedOut`, `Disabled`, `Unreachable` and `Loading`.
- Views are written once per renderer from those models: `Autonogrammer.Native.Views/Views/Dispatch/` (Avalonia; shared by the desktop and Android heads through `ViewMapping`) and `Autonogrammer.UI/Components/Dispatch/` (Razor; the web head). Required behaviour: every phase has its own text, never colour alone; a running command shows Cancel as a real button reachable by keyboard and named for assistive technology; status changes are announced through a polite live region and a failure through an assertive one; focus moves to the new row or the dialog heading and returns afterwards; the Android target size override (44) applies; all motion honours reduced motion.
- Hosts: Native desktop and Android use `HttpDispatchHost` from a new L3 library `Autonogrammer.Dispatch.Client` (POST plus SSE with the `Last-Event-ID` and `SeqTracker` rules; the access token comes from `IAccountSession.GetAccessTokenAsync` of `Autonogrammer.Accounts` (L2, ADR-0030 D5) adapted to a `Func<CancellationToken, ValueTask<string?>>`, the shape of `ApiCloudAgentsHost`). The web head implements `IDispatchHost` in `apps/Autonogrammer.Web/Services/Dispatch/` over its existing `ApiHttp` and `SseEventStream` with the token provider of the accounts record, because the web head must stay free of process-spawning references (`ProjectGraphTests.cs:36-41`) and keeps its own HTTP stack. The desktop connector is the L3 library `Autonogrammer.Dispatch.Desktop` (references `Autonogrammer.Harness.Acp` for the transport, `Autonogrammer.Harness.Secrets` for `ISecretStore`, `Autonogrammer.Accounts` for `IAccountSession`, Presentation for the approval models); `Autonogrammer.Accounts.Desktop` (L3) and the `Autonogrammer.Harness.Secrets.Os` store are composed in the Native head, and the operation handlers are implemented in the Native head, which owns the engine. Dispatch registers an `IAccountFeature` with key `dispatch` (ADR-0030 D8), which makes `GET /account` list it and the account menu show Devices; the Devices page and the pairing dialog belong to this record. The signed-out state of Dispatch is the account state of `Autonogrammer.Accounts`, not a second copy.
- Scope: contracts, API, desktop connector and these surfaces. The Android build, a push provider, offline notification and a store-published mobile app are not part of this record.

### D15. Threat model

| # | Threat | Vector | Controls | Residual |
| --- | --- | --- | --- | --- |
| 1 | Stolen device credential | File or memory theft on the desktop, or from a backup | PoP: the credential is useless without the private key (`cnf.jkt` plus signed `hello`); credential `jti` rotation; 30 day life; revoke; failed-connect rate limit; a `device.connection_replaced` event and a "connected from a new network" flag when the source prefix changes | A thief with credential and key is that device until revoked, can receive that device's commands and can send false results; commands never run on the victim because the hub routes to the thief's connection |
| 2 | Command replay | A recorded `cmd` frame re-sent to the device, to another device or later | Signature binds device, seq, commandId, nonce, expiry, payload hash; device high-water and commandId set persisted before `received`; `expiresAt` with clock offset; unique `commandId` and `seq` in the store; `res`, `ack` and `evt` are compare-and-set so a replay is a no-op | None known beyond the 30 second skew window |
| 3 | Malicious or compromised relay | Hub bug, stolen hub key, operator error | Device pins hub keys (rotation signed by a pinned key); no `computer.*` operation exists on the device allow-list, so a forged command cannot move the mouse; a forged `cowork.task` naming `computer_use` still meets the local start approval and the per-action gate of ADR-0035; `approval.decide` refuses Computer Use; the closed operation set; "Remote task running" strip and indicator; ledger notarisation for detection; `hello` signs the hub origin | A hub that holds `Dispatch:CommandSigning:KeyPem` can forge `code.prompt` and `cowork.task` (without Computer Use) for devices that enabled them; controller end-to-end signing (OQ-426) is the later layer; the hub and its key are therefore the most sensitive secret of the deployment |
| 4 | Confused deputy between users | A valid Supabase token of user B naming user A's device; a shared Supabase project where any website user holds a valid token | Every route authorises `dispatch_devices.account_id == sub`; foreign reads as 404; composite foreign key `(device_id, account_id)` on commands; the device refuses `userId` different from the account stored at pairing; the Accounts module of ADR-0030 (the `accounts` row of ADR-0031 M0004) decides that a token is an Autonogrammer account (05 finding F7); the feed is filtered by account in SQL | A bug in a new query; covered by cross-owner tests on every route |
| 5 | Prompt injection through a dispatched task | Hostile text in a task or in a page the task visits steering the desktop agent | Dispatch adds no tool; the desktop's run mode and tool approval ceiling apply unchanged; Computer Use and Browser Use rules of ADR-0034 and ADR-0035 apply; task text shown as plain text in prompts | The desktop agent can still be misled within the permissions the user granted |
| 6 | Account takeover | Stolen access token or passwordless link | Pairing needs a full sign-in no older than 10 minutes; revocation is by device and by "Sign out everywhere"; Computer Use always needs the person at the desktop; the token's revocation gap (JWTs valid until `exp`, ADR-0030 D7) is accepted for controller commands and bounded by the token lifetime, and narrowed by an `IAccountStatus` check against `accounts.status` and `deleted_at` (ADR-0031 M0004), cached 60 seconds, whose vocabulary OQ-424 confirms | An attacker with a live token can queue `code` and `cowork` commands for devices that enabled them until the token expires, the account is marked unavailable or the devices are revoked |
| 7 | Denial of service | Command flood, connect flood, a half-open socket, a huge frame | Per-`sub` token buckets, queue cap, payload and frame limits, newest-wins connection policy, connect rate limits, bounded outbound channel (256) per connection | A shared edge is outside this record |
| 8 | Self-approval | Computer Use agent clicks Approve on its own prompt | ADR-0035 D3 and D5: serialised actions so nothing is injected while a prompt is open, own windows hard-denied as targets and masked from frames, host-observed facts in the prompt | Depends on ADR-0035 and cannot be verified on this host |
| 9 | Information leak | Payload, token or device name in a log, metric or exception | `LoggerMessage` with event ids and no body; bearer tokens and signatures never logged; `ToString` on credential holders prints no key; metric tags are bounded (`result`, `reason`); the existing redactors apply to relayed text | Operator access to the Postgres table |

### D16. Degraded and error states

Each is a distinct state in the models and a distinct, specific message in the views: `SignedOut` (sign-in needed), `Disabled` (relay off on this server), `Unreachable` (hub not reachable; offline queue unavailable), `NoDevices`, `DeviceOffline` (shows how long ago it was seen; a queued command shows its expiry countdown), `PresenceUnknown` (Dragonfly unavailable: never shown as offline), `CredentialExpired` (re-pair), `DeviceRevoked`, `ReplacedByOtherInstance`, `UpdateRequired` (4010), `AccountUnavailable` (4011), `RateLimited` (with the retry delay), `PayloadTooLarge`, `CapabilityUnavailable`, `PausedByUser`, `CoordinationPaused` (command sends refused while Dragonfly recovers, ADR-0031 D8), plus every `DispatchFailureReason`.

Added by the account integration (ADR-0030 D6 rule 4 and D8): `KeyStoreUnavailable` (no usable operating system store, so no pairing and no connection; there is no file fallback) and `PairedToAnotherAccount` (the desktop is paired to an account other than the one now signed in).

## Blocked, and by what

- Live checks of anything here: Railway deploys are paused and `Autonogrammer.Api` was never created (`docs/runbooks/hosting.md:15,41`); sign-in authority for the deployed API (OD-03) and the Supabase project are the owner's; tests use fakes and throwaway local containers.
- Behaviour of a long-lived WebSocket through the Railway edge (idle limits, restarts) and whether the API service ever runs Serverless (ADR-0020 line 105 question): unverified.
- OS credential stores for the device key (Linux Secret Service, macOS Keychain, Windows DPAPI): `Autonogrammer.Harness.Secrets.Os` of ADR-0030 D6 builds them; Windows and macOS code is compile-checked only on this Linux host, and the Linux store has a live test only where a keyring is unlocked.
- Android build and a real phone: no Android SDK here.
- Screen and browser streaming: paused until Railway answers OQ-73.
- Owner actions: generate the two P-256 keys (`Dispatch__CommandSigning__KeyPem`, `Dispatch__Credentials__SigningKeyPem`) and set them as Railway variables, unpause deploys, create the API service, and set `Dispatch__Enabled` only after the sign-in authority works.

## Consequences

- `Autonogrammer.Api` gains WebSocket hosting, a second authentication scheme (`DispatchDevice`) used only on the connect route, a hosted sweeper and partitioned rate-limit policies; The change is additive; the scaffold step bumps `ContractVersion.Current` to 1.6.0 and no phase edits it (the scaffold step also checks that no type in `Contracts/Plugins` references `Contracts/Ui` types) and `docs/api/openapi.json` is regenerated.
- Two new L3 libraries (`Autonogrammer.Dispatch.Client`, `Autonogrammer.Dispatch.Desktop`) and their test projects are registered entirely by the serialised scaffold step (solution, filter, LayerMap, ArchitectureTests reference, lock files, project files, test projects); phase 74 units add code only and edit a registry file only for rows the scaffold manifest marks "per phase" (OpenAPI, notices when a package lands, `docs/architecture.md` prose, parity audit rows).
- `Autonogrammer.Api` already gains its reference to `Autonogrammer.Harness.AgentLoop` from ADR-0031 (ledger sink); Dispatch adds none. `Autonogrammer.Dispatch.Desktop` and `Autonogrammer.Dispatch.Client` need no `SameLayerAllowed` entry: both are L3 and reference only L0 to L2 projects. Dispatch store calls use the pipelines of `Autonogrammer.Resilience` (ADR-0031 D7) and add no retry code of their own.
- `ReconnectPolicy` is not extended; the connector has its own loop. `AcpWebSocketTransport` is reused unchanged as the desktop transport.
- Desktop heads gain a "Dispatch" settings page and a persistent remote-task indicator; the Android head gains a controller composition that is compile-checked only.

## Candidate chosen

A hub in the existing `Autonogrammer.Api` (module `Dispatch/`) with a durable per-device command log in Postgres, a wake-only Dragonfly signal and presence key, an outbound-only WebSocket per desktop reusing `AcpWebSocketTransport`, ES256 device credentials with proof of possession, ES256-signed commands over a restricted canonical byte string, and HTTPS POST plus SSE for controllers. No new third-party package is adopted: signing and verification use the .NET base class library (`ECDsa`, `SHA256`, `RandomNumberGenerator`) and the already-referenced `Microsoft.IdentityModel.JsonWebTokens` for the credential. Alternatives rejected: an ssh reverse tunnel (browsers and phones cannot ssh, 08 section 2.4); a separate relay service (no trust-boundary reason); Dragonfly-only queueing (durability unverified, 04 decision D11); SignalR or another socket library (a new dependency with no gain over the existing transport); JWS per command (the owner's envelope asks for a signature over canonical bytes, and the detached form binds the payload hash without JSON canonicalisation).

## Open risks

- The hub holds the command signing key, so a hub compromise can forge commands for every device that enabled `code` or `cowork` (D15 row 3); only controller end-to-end signing removes it and it is not built.
- Railway's treatment of long-lived WebSockets, deploy restarts and the first request after a deploy is unverified; a reconnect storm is limited by jitter and the connect rate limit only.
- The device private key is only as protected as the `Autonogrammer.Harness.Secrets.Os` implementation of ADR-0030 D6 (the Linux Secret Service has no per-application isolation, DPAPI does not stop malware running as the same user); there is no file fallback, so a desktop without a usable store cannot use Dispatch.
- Revocation reaches an offline desktop only at its next connect; until then its local state is still paired.
- The controller-supplied `Idempotency-Key` is scoped to one account and device; a client that reuses a key for a different request gets 409 `idempotency-key-reused` and must generate a new one.
- Command bodies stay readable in PostgreSQL for 7 days after a terminal state and result text until OQ-423 is settled; there is no application-layer encryption (OQ-425).
- The credential validator and the frame guard are copied from the worker service (OQ-422); the copies can drift.
- The Computer Use self-approval defence is the gate of ADR-0035, which cannot be tested on this host; Dispatch adds no code path to it.
