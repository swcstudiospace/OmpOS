# ADR-0017: Web head Demo mode: an in-browser API handler, no tunnel to the dev API

- Status: Accepted 2026-10-28. Default for the "visible web application" goal of milestone v0.15.0; the Demo build is deployed at https://ompos-web.vercel.app (Vercel production alias of the `ompos-web` project) and was checked with headless Chrome from the live URL; the owner can still choose the hosted API path (see Open risks).
- Date: 2026-10-27
- Owner: ompos-maintainers
- Deciders: ompos-maintainers
- Scope: how the Blazor WebAssembly head (`apps/OmpOS.Web`) is shown to people before a hosted API with sign-in exists: the typed API client, the Demo build, the Content-Security-Policy, and why a production bundle holds no demo code. It does not choose the hosted API topology (ADR-0020, `docs/runbooks/hosting.md`).

## Context

Facts read on 2026-10-27:

- G-WEB (ADR-0004 decision 2) asks the browser build to expose role and accessible name for the prompt input, the send control and the transcript. Avalonia.Browser 12.1.4 (the newest release; NuGet lists 12.1.0 to 12.1.4) failed it three times with the same result: one `<canvas>`, no element with a `role`, no textbox in the accessibility tree (`docs/runbooks/evidence/gweb-remeasure-2026-10-24/`). **G-WEB stays failed.** The web head stays Blazor WebAssembly over the shared Presentation layer. Re-measure on the next Avalonia release, as ADR-0004 criterion 5 says.
- The API refuses the development principal and the InMemory harness outside Development (`ApiAuthOptionsValidator`, `Program.cs`), and `docs/runbooks/hosting.md` says the API has no public domain until sign-in (OD-03) exists. A public endpoint with the development principal would be one shared, unauthenticated account that can run omp.
- The web head already talks to the API through `HttpClient`, so every route can be answered by an `HttpMessageHandler` without changing a component.
- `docs/api/openapi.json` is regenerated by the API build; it is the one contract both the API and a fake can be checked against.

## Candidate chosen

Ship a **Demo build** of the unchanged web head whose `HttpClient` is backed by an in-browser `DemoApiHandler`, labelled as simulated everywhere, and keep the real client for every other build.

1. **One typed client.** `IOmpApiClient` has one method per route the web head uses (catalogue, create, get, prompts, steer, tool approvals, session events, stages, context, config options, commands, changes, board, card details, close, reopen, resume, workspace, source, health) and `IUserEventFeed` carries the user-level stream with `Last-Event-ID` resume and resync. A problem response becomes `ApiProblemException` with a kind (400, 401, 403, 404, 409, 413, 415, 422, 429, 5xx), the problem code and a bounded detail; no prompt, body or credential is put in a message. `IApiTokenProvider` is the seam sign-in plugs into (default: none).
2. **One composition.** `WebWorkbench` (scoped) builds the Presentation view models (`AgentPanelViewModel`, `KanbanBoardModel`, `SettingsWindowModel`) over web implementations of the host and source interfaces. A feature the API cannot serve (live steering between runs, an omp terminal, option changes during a turn) shows its reason through the Presentation unavailable states; none throws into the UI. `LocalWorkspaceFileSystem` is never used in the browser: the Changes bar reads an API-backed mirror.
3. **Demo mode.** MSBuild property `OmpOSDemo=true` compiles `apps/OmpOS.Web/Demo/**`, defines `OMPOS_DEMO`, and sets the application environment to `demo` so `appsettings.demo.json` (`Demo:Enabled`) loads. `DemoApiHandler` answers every client route from typed fixtures through the Contracts source-generated contexts: the workspace `acme-shop` with six sessions (running with a scripted answer that streams markdown, code, a tool call and a diff; waiting for a tool approval; completed with three changed files; failed with a retryable error; closed; an omp terminal), the four plugin connections connected, a stage timeline, 20 engine commands, a model list whose provider ids come from the provider catalogue, a board over the ten columns, and source info (`AGPL-3.0-or-later`, repository URL, revision `demo`). Mutating calls change in-memory state so the UI reacts. Streaming runs on an injected `TimeProvider`. The shell shows a permanent Demo banner (`WebWorkbench.IsDemo`).
4. **Content-Security-Policy.** `OMPOS_DEMO=1` makes `scripts/vercel/render-csp.sh` print `connect-src 'self'` and ignore `OMPOS_API_ORIGIN`; any other value of `OMPOS_DEMO` is a normal build and still fails closed without an origin. `vercel.ts` adds `-p:OmpOSDemo=true` to the publish. `scripts/vercel/build-demo.sh` writes a static bundle with a `vercel.json` (same CSP, revalidated `_framework` cache (plain file names, no import map), SPA rewrite); `scripts/web-demo/serve-demo.sh` serves it on 127.0.0.1.
5. **Production exclusion.** With `OmpOSDemo=false` (the default) the Demo folder is `<Compile Remove>` and `appsettings.demo.json` is not published. The assembly carries `AssemblyMetadata("OmpOSDemo", ...)`; `DemoExclusionTests` checks that the Demo types exist exactly when it says `true`, and `PublishSmokeTests` greps the published assemblies for the type name `DemoApiHandler`.
6. **No tunnel.** A tunnel from a hosted page to the local dev API is rejected: the `?apiBaseUrl=` override accepts loopback only, and the tunnel would publish the development principal.

The Demo is honest because every answer starts with a Demo label, the source revision is `demo`, and nothing typed leaves the page.

## Verification route

- `dotnet test tests/OmpOS.Web.Tests` runs the client route tests (every route answered, every problem status mapped), the user stream resume and resync tests, the workbench tests over the Demo on a manual clock, the strict fixture round trips through the Contracts contexts, `OpenApiCoverageTests` (every operation the client uses exists in `docs/api/openapi.json`), `DemoExclusionTests` and `RenderCspScriptTests` (`OMPOS_DEMO`).
- `dotnet publish apps/OmpOS.Web -c Release` must hold no `DemoApiHandler`; `dotnet publish apps/OmpOS.Web -c Release -p:OmpOSDemo=true` must hold it. `PublishSmokeTests` runs the first.
- `scripts/vercel/build-demo.sh && scripts/web-demo/serve-demo.sh`, then `scripts/web-smoke/run-smoke.sh` style checks against `http://127.0.0.1:5190/` (axe, every screen).
- The Demo's behaviour is documented in `docs/runbooks/web-demo.md`.

## Open risks

- The Demo shows scripted behaviour. A reader could mistake it for the product; the banner, the answer label and the `demo` revision are the mitigation, and a Demo URL must never be presented as a hosted service.
- The Demo handler and the API can drift. `OpenApiCoverageTests` and the strict round trips catch missing routes and members; behaviour (for example the 409 rules of option changes) is mirrored by hand and needs a test per rule when the API changes.
- The API starts one engine session per prompt, so model, mode and thinking cannot change between turns, and live steering exists only while a run holds an engine session. The Demo mirrors the 409 of a change during a turn but allows it between turns, which the real API does not yet (ApiSurface report, limit 1).
- The hosted path (Railway API with sign-in) is blocked on OD-03 and paused deploys; the same components and the same client serve it once `IApiTokenProvider` has a real implementation.
- Browser behaviour (layout, axe, contrast of the Demo screens) is not verified by this record; it needs the smoke run named above.
