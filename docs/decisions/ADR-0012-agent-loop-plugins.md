# ADR-0012: Agent loop plugins

- Status: Accepted 2026-10-26
- See Update 2026-10-26 (at the end of this record).
- Date: 2026-10-26
- Owner: autonogrammer-maintainers
- Deciders: autonogrammer-maintainers
- Scope: how the Ultrathink, Swarm, Substrate and GSD-Core plugins are obtained, launched, observed and degraded in the Autonogrammer agent loop (milestone v0.14.0, phases 44 to 46). The full design is [agent-loop-design.md](../plans/agent-loop/agent-loop-design.md); the evidence is in [docs/plans/agent-loop/](../plans/agent-loop/README.md).

## Context

Autonogrammer drives omp over ACP. Three sibling projects already ship as omp plugins: `claude-ultrathink` (prompt planning), `agent-swarm` (a 30-agent subagent orchestrator) and `agent-substrate` (cross-session state, steering record, ledger). GSD-Core is installed on the host but has no omp runtime upstream. The program goal is a default Agent Panel that shows these stages without Autonogrammer owning their code.

Observed facts that constrain the design:

- Under `omp acp`, extensions see `ctx.mode` `rpc` with a no-op UI context: widgets mount nowhere and `ui.notify` never reaches the client.
- omp silently ignores a nonexistent `-e` or `--plugin-dir` path and unknown flags.
- omp fails `session/new` if any MCP server in the request is unreachable.
- Substrate on its default branch has no live steering delivery.
- The substrate repository is private; two of the three siblings have no LICENSE file and the third is AGPL-3.0-or-later.

## Decision

- **D1. The plugins run inside omp.** Autonogrammer resolves them from pinned submodules, launches `omp acp` with explicit loading flags, observes them through files and HTTP, and renders them. No sibling source is copied or edited. Evidence: `dossier-omp-loading.md` sections 1 to 5, `dossier-ultrathink.md`.
- **D2. Layout.** `plugins/claude-ultrathink`, `plugins/agent-swarm` and `plugins/agent-substrate` are git submodules with remote https URLs and `branch = main`, pinned to commits that exist on the remotes. `plugins/gsd-core-omp` is a tracked Autonogrammer-owned thin plugin, because GSD-Core upstream has no omp runtime. Evidence: `dossier-git-ci.md`, `dossier-gsd-omp.md` section 3.
- **D3. Steering is Autonogrammer-owned.** Operator text is queued over ACP (queue after the turn, through the existing run input scheduler). Autonogrammer only records a steering action in Substrate (`events_emit`, kind `note`, `payload.action` `steer`) when it is reachable, and never claims Substrate delivered it. Evidence: `dossier-substrate.md`, `dossier-autonogrammer-seams.md`.
- **D4. Stage events are data in `Autonogrammer.Contracts.Agents`.** No `StreamEvent` kind is added and `ContractVersion` does not change. Evidence: `dossier-autonogrammer-seams.md` section 2.4, option A.
- **D5. One `omp acp` child per session.** `InProcessEngineHost` binds one session; the native head owns N engines through `SessionEngineSet`. Evidence: `dossier-autonogrammer-seams.md`.
- **D6. Substrate is reached twice.** The omp child reaches it through an HTTP entry in `session/new.mcpServers`; the host reaches it through `SubstrateGateway` (`GET /healthz`, `POST /brief`, `POST /mcp`, `POST /events/query`). The host health-checks first and omits an unhealthy Substrate, surfacing a Degraded stage. Tokens travel only as environment variable names. Tests never target the live server on `127.0.0.1:7410`. Evidence: `dossier-substrate.md`.
- **D7. Launch is hermetic and explicit.** `omp acp --no-extensions`, then one `-e` per extension in composition order (Ultrathink directory, Swarm `omp/`, the two substrate projector files, `plugins/gsd-core-omp`). `-e` only, never `--plugin-dir`. Autonogrammer validates every path and tests assert exact argv and per-session environment. Evidence: `dossier-omp-loading.md` sections 2, 3 and 5.
- **D8. Degradation is a stage event, never a crash.** Ultrathink off: original prompt flows. Swarm missing: single-agent run. Substrate unavailable: no steering record, no shared memory. GSD missing: phase unknown. Uninitialised submodule: a typed exception naming the plugin, path and fix. Evidence: [agent-loop-design.md](../plans/agent-loop/agent-loop-design.md) section 1.
- **D9. The panel shows only what exists.** There is no live Ultrathink progress: that stage is Running from prompt send until its session file appears. Swarm state comes from `live.json` and `events.jsonl`. Substrate panels show only timestamp, surface, kind, actor and `payload` action, item and outcome, never ledger summary or payload text. Memory and lesson bodies are untrusted plain text, length capped. Evidence: `dossier-ultrathink.md` sections 3 and 5, `dossier-swarm.md` section 4, `dossier-substrate.md`.

## Consequences

- Cloning needs `--recurse-submodules`. The private substrate submodule needs read access locally and the `SUBMODULE_TOKEN` secret in CI ([OQ-63](../open-questions.md)). Without it the substrate plugin is Unavailable and the build still passes.
- A pin bump is a commit in Autonogrammer. Sibling changes land in the sibling repository first ([plugins guide](../plugins.md)).
- The architecture layer map gains `Autonogrammer.Harness.AgentLoop` (L2) and the Contracts `Agents` types ([architecture](../architecture.md)).
- Stage visibility depends on files and HTTP the plugins write. A plugin that changes those formats degrades its stage until the observer is updated; unknown fields are ignored and malformed files yield a Degraded event.
- Open items: licence of Autonogrammer and AGPL interplay ([OQ-62](../open-questions.md)), symlinked agents ([OQ-64](../open-questions.md)), intermittent outbound connection ([OQ-65](../open-questions.md)), Substrate Phase 53 adoption ([OQ-66](../open-questions.md)), live Ultrathink progress ([OQ-67](../open-questions.md)).
- Note on evidence: the design file records an earlier Ultrathink pin; the pin in the Autonogrammer tree and in [plugins.md](../plugins.md) is authoritative.

## Alternatives considered and rejected

- **Copy the plugin code into Autonogrammer.** Rejected: it forks three projects, drops upstream fixes and mixes an AGPL-3.0-or-later codebase into the repository. Pinned submodules keep one source of truth.
- **Reimplement the plugins on the host side.** Rejected: the behaviour (planning, 30 agents, ledger) already exists as omp plugins and would diverge from the originals.
- **Load with `--plugin-dir`.** Rejected: it provides skills, commands and agents but runs no extension code (no `/swarm`, no `swarm_*` tools), and combined with `-e` it double-registers commands. Evidence: `dossier-omp-loading.md` section 3, runs c, d, f.
- **A fourth submodule for GSD-Core.** Rejected: upstream GSD-Core has no omp runtime, and the installed copy under `~/.agents` is what omp skills already use. A thin tracked plugin that copies nothing is enough.
- **Substrate-delivered steering.** Rejected for now: live delivery (Phase 53) is unmerged on the pinned commit. Autonogrammer delivers over ACP and records only. Revisit under [OQ-66](../open-questions.md).

## Update 2026-10-26

Source: the user's direction of 2026-10-26 (decisions DR-1, DR-2, DR-4, DR-5 and DR-6 of the TODO revision). The accepted text above is unchanged. Where this section and the accepted text disagree, this section governs; the affected sentences are named below.

- **DR-1. There is no additional Agent Panel.** The default Cursor-style Agent Panel is the agent panel, and the work is to keep it a faithful Cursor clone, not to build a second surface. The accepted sentence "The program goal is a default Agent Panel that shows these stages" (Context) and D9 ("The panel shows only what exists") are read with this limit: the panel shows no stage panels of its own and has no inspector. Kept: the session rail (Cursor's Agents sidebar), the thread, the composer, the header chips and the one-line plugin connection row directly under the header. They belong to the default panel header, they are not a panel. The task context and the steering history that the design placed in an inspector move to the Kanban tab card (Phase 39). The facts in D9 about what the plugins expose (no live Ultrathink progress, Swarm files, Substrate fields, untrusted note bodies) still hold for every place that shows them.
- **DR-2. Plugins run in every omp process the application starts, exactly once.** D1 and D7 describe the launch of `omp acp`. The target now covers both the engine session behind the Agent Panel (over ACP) and the omp terminals the application starts. Each plugin is loaded from the pinned submodules once per process, even when the user's own omp configuration (global `config.yml` extensions, extension symlinks) is present. This is a verification target, not a recorded fact: it is closed only by one recorded run per plugin and one end-to-end run without a model turn (Phase 48). D44-8 of the Phase 44 context records that the same launch planner plans the terminal launch.
- **DR-4. Steering facts and the open delivery mechanism; D3 is amended.** D3 said operator text is queued over ACP after the turn. That stays as the fallback only. Live delivery into a running turn is the requirement. Facts that matter, each from the repository or the installed omp:
  - omp's ACP agent cancels a running turn when a new `session/prompt` arrives (`acp-agent.ts`, `prompt`), so a prompt cannot deliver live over ACP.
  - omp extensions can deliver a message into a running session with `sendUserMessage(text, { deliverAs: "steer" | "followUp" | "aside" })`.
  - omp RPC mode has `steer`, `follow_up` and `steer_subagent` commands. The Autonogrammer RPC client already carries the intent as `PromptOptions.Steer` (`src/Autonogrammer.Harness.Abstractions/PromptOptions.cs`, `src/Autonogrammer.Harness.Rpc/OmpRpcSession.cs`), and `RunInputScheduler` (`src/Autonogrammer.Presentation/Runs/RunInputScheduler.cs`) already separates steers from follow-ups. `AcpAgentSession.SubmitPromptAsync` throws `NotSupportedException` when `PromptOptions.Steer` is set ([OQ-59](../open-questions.md)).
  - Substrate on the pinned commit has no live delivery (draft PR #110, [OQ-66](../open-questions.md)). D3's rule stands: Autonogrammer records the steering action in Substrate and never attributes delivery to it.
  The delivery mechanism is therefore an open question, [OQ-81](../open-questions.md), with a recommended default: an omp extension inbox that calls `sendUserMessage` with `deliverAs`. Alternatives: switch the engine to omp RPC mode and use `steer` and `steer_subagent`, or adopt Substrate Phase 53 once merged. The steering requirement is written as an outcome (a running session takes the message into account before its turn ends; delivered, queued and failed are shown truthfully), not as a mechanism. Evidence: `docs/plans/agent-loop/dossier-substrate.md` and `dossier-autonogrammer-seams.md` (the existing seams); the `acp-agent.ts` and `sendUserMessage` facts come from the installed omp and are to be re-confirmed in the Phase 49 recorded run.
- **DR-5. Defaults for three open product questions** (non-blocking; the user may change them): (a) the Kanban columns mirror the session lifecycle status, with the Phase 39 context defaults ([OQ-78](../open-questions.md)); (b) closing or ending a session moves its card to its terminal column (Completed, Failed or Archived) and never removes it silently ([OQ-79](../open-questions.md)); (c) the four plugins are always on, so no enable or disable settings item is added, while the launch planner keeps its per-plugin switches for operators and tests ([OQ-80](../open-questions.md)).
- **Scope of plugin registration** ([OQ-82](../open-questions.md)): the default is per-process `-e` flags for app-started omp. Writing the registration into omp's own configuration, for terminals the user starts elsewhere, is an optional later step blocked on a probe of how omp merges `extensions` overlays with the global configuration.
- **DR-6 (for reference).** The Settings window follows the Cursor Settings structure with per-provider fields in its Models section. Phase 40 carries it. It does not change this ADR.

Consequences: the Kanban tab (Phase 39) is the only product addition besides provider settings; Phase 48 verifies the plugins in app-started omp terminals; Phase 49 delivers live steering. No accepted decision other than D3 changes, and D3 keeps its queue-after-turn behaviour as the fallback.

## Update 2026-10-26 (implementation of Phases 44 to 49)

Source: the code and the recorded runs of 2026-10-26 (`.planning/phases/44-*` to `48-*`, `docs/runbooks/evidence/phase-48-omp-plugins-2026-10-26/`). Where this section and the text above disagree, this section governs.

- **Steering mechanism (settles the default of OQ-81; amends D3 and the DR-4 paragraph above).** Chat (ACP) sessions steer through omp's own extension request `_session/steering`, which omp advertises as `_meta.steering.supported` in its `initialize` answer. Its outcomes are `injected` (a live run takes the message at its next tool-batch or model-call boundary), `promptRequired` (the session is idle, so nothing was consumed and the host sends the text through `session/prompt`) and `failed`; omp never starts a detached turn from it. Omp terminals have no ACP, so they steer through the Autonogrammer inbox, an omp extension feature of `plugins/gsd-core-omp` (`AUTONOGRAMMER_STEER_DIR`: directive files, acknowledgements, a 5 s heartbeat) that calls `sendUserMessage` with `deliverAs` `steer`, `followUp` or `aside`. The inbox is also the fallback for an omp whose `initialize` lacks the capability. Queue after the turn stays the last fallback. Substrate only records the steering note and delivery is never attributed to it (D3, OQ-66). Evidence: `acp-auth-and-steering.md` (the wire contract, read from the installed omp 18.12.6 and probed without a model turn), `FileSteeringChannelTests`, `AcpSteeringTests`, `AgentSessionRuntimeNativeSteeringTests`. Not verified: an `injected` delivery into a running turn, which needs a model turn (OD-07).
- **The ACP authentication method is set.** omp's `initialize` always lists `authMethods` (`agent`, "use existing local credentials"), and the Autonogrammer ACP client refuses to continue when the list is not empty and no method is configured. The head sets `AuthMethodId` to `agent` (found by running the real application, `docs/runbooks/evidence/phase-40-settings-2026-10-26/`).
- **`SWARM_GSD_STATE_FILE` is a per-session path (amends D7).** The value is `<session>/swarm/gsd-state.md`, never empty. The pseudo-terminal backend removes a variable whose value is empty, and the swarm would then write its `swarm:` lines into the workspace `.planning/STATE.md`. `SWARM_AGENT` and `SWARM_TASK_ID` stay unset.
- **Terminals use the same launch (DR-2, built).** The launch planner derives an interactive omp launch from the same plan (`OmpLaunchPlan.ForTerminal`): the same `-e` arguments after `--no-extensions`, never `acp` and never `--plugin-dir`, the same per-session environment, no MCP server, an optional `--resume`. The PTY backend no longer lets the child inherit the host environment: it passes only `PATH`, `HOME`, `LANG`, `TERM`, `PI_CODING_AGENT_DIR` and `OMP_PROFILE` from the host plus the variables the caller names, and unsets the rest by name through `/usr/bin/env -u`.
- **Connection is observed, not assumed.** The `gsd-core-omp` plugin loads into every app-started omp and writes the names of the tools and commands omp has registered to `AUTONOGRAMMER_CONNECTION_FILE`; the host owns the table of expected names per plugin and shows each plugin's state in the one-line connection row. Verified without a model turn on Linux against the real omp 18.12.6: the engine session (mode `rpc`) and the interactive omp in the PTY (mode `tui`) each showed all four plugins connected, with a fresh heartbeat. Not verified: one application run that shows all four connected in the row, a live model turn, Windows, macOS, Android and the hosted deployments. The Substrate extension files load only when a Substrate endpoint is configured and healthy (D6); without one the row shows Substrate off with its reason.
- **The Inspector is gone (DR-1, built).** The default Agent Panel has a session rail, a thread, a composer, the header chips and the one-line connection row. `AgentPanelLayoutTests.TheDefaultPanelHasNoRegionBesideRailThreadAndComposer` pins that no inspector control exists. Task context and steering history belong on the Kanban card (Phase 39). Phase 47 (web head) is deferred (`.planning/phases/47-agent-panel-on-the-web-head/47-DEFERRED.md`).

Consequences: D3 now reads "chat sessions steer through omp's native `_session/steering`, terminals and the fallback through the Autonogrammer inbox, Substrate records only". OQ-81 stays open until an `injected` delivery is recorded. No other accepted decision changes.
